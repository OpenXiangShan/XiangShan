## S1 Access Fault 被 RM 错误叠加为 Page Fault

**问题类别**：RM  
**责任子类型**：PMA/PMP 与 TLB fault 期望合并  
**版本/分支/核验 commit**：V2 / `mem_ut_uvm_v2` / `6646f8f53c8e37791fbbf5b854427a452292d17a`  
**发现时间**：仿真 `7706.6ns`，现实日期 `2026-09-21`  
**测试用例**：`tc=basicTest`，`ts=memblock_dispatch_real_mmu_sv39_pbmt0_non_nc_vseq`，seed `710006`，100000 请求  
**配置选项**：`+MEMBLOCK_L2TLB_S1_AF_1_WT=5`、`+MEMBLOCK_L2TLB_S1_PF_1_WT=0`、`+MEMBLOCK_CHECK_TRIGGER_EN=0`、`+MEMBLOCK_HARD_XZ_CHECK_EN=0`、`+MEMBLOCK_SFENCE_CONTROL_ENABLE=0`  
**日志绝对路径**：`/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/mem_ut/ver/ut/memblock/sim/safe_nocross16_run2_timeout1g_20260921/log/tc=basicTest_ts=memblock_dispatch_real_mmu_sv39_pbmt0_non_nc_vseq_cfg=tc_dispatch_real_mmu_sv39_pbmt0_non_nc_100k_safe_nocross16_seed=710006_rtl.log`  
**波形绝对路径**：`/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/mem_ut/ver/ut/memblock/sim/safe_nocross16_run2_timeout1g_20260921/wave/tc=basicTest_ts=memblock_dispatch_real_mmu_sv39_pbmt0_non_nc_vseq_cfg=tc_dispatch_real_mmu_sv39_pbmt0_non_nc_100k_safe_nocross16_seed=710006_rtl.fsdb`

### RM/测试框架问题描述

UID17/59/61/77/87 等 fault load 中，DUT 均返回 `exception=0x20`，即 Load Access Fault；RM 却期望
`0x2020`，多出的 bit13 是 Load Page Fault。V2 TLB 的 S1 permission 逻辑在有效 S1 AF 时屏蔽同阶段 PF；
`S1_AF_1_WT=5` 且 `S1_PF_1_WT=0` 时，S1 AF 是唯一注入 fault。RM 在
`observer_build_commit_item()` 中同时使用 `fault_effective_s1_af` 和 PTE permission 推导
`observer_stage_permission_fault()`，把随机 fault entry 的权限字段再次合并为 PF。该错误只改变 RM
期望，不改变 DUT 激励，责任归 RM。

### 源码定位

- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/mem_ut/ver/ut/memblock/env/src/memblock_rm/memblock_rm.sv:551-560`：S1/S2 fault 期望构造。
- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/mem_ut/ver/ut/memblock/env/src/memblock_rm/memblock_rm.sv:669-676`：最终异常位生成。
- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/cache/mmu/TLB.scala`：S1 PF 带 `!af` 屏蔽条件。

### RM 修改方案

当某阶段已经有 response-visible 的明确 fault 时，该阶段只保留注入的架构 fault，不再执行 PTE permission
推导：

```systemverilog
entry_stage_one_fault = entry.fault_effective_s1_pf ||
                        ((!entry.fault_effective_s1_pf &&
                          !entry.fault_effective_s1_af) &&
                         observer_stage_permission_fault(entry, tlb_context,
                                                         store_access, 1'b1)) ||
                        pbmt_force_s1_pf;

entry_stage_two_fault = entry.fault_effective_s2_gpf ||
                        ((!entry.fault_effective_s2_gpf &&
                          !entry.fault_effective_s2_gaf) &&
                         observer_stage_permission_fault(entry, tlb_context,
                                                         store_access, 1'b0)) ||
                        pbmt_force_s2_gpf;
```

`access_fault` 仍保留 effective S1/S2 AF；因此 S1 AF 只生成 bit5，S1 PF 只生成 bit13，不再错误合并为
`0x2020`。

### Review 门禁与状态

独立 review：`/root/review_rm_fault_exception_mismatch` 与 `/root/cross16_fault_second_review`，日期
`2026-09-21`。两轮最终结论一致：该组 mismatch 是 RM 期望构造错误，不是 RTL。状态：**已 review，待 RM coding 与复测**。

### 修复后复测

RM 已按上述最小逻辑修改并完成重新编译。seed `710006` 复测中，UID59/61/77/87 的
`expected=0x2020/actual=0x20` 错误不再出现，说明 S1 AF 与 PTE permission PF 的错误叠加已解除。
本次 RM 修改未触碰 RTL。

## PMA C 属性被 RM 错误建模为“等待 DCache 确认”，并误报非对齐异常

**问题类别**：RM  
**责任子类型**：PMA/PMP profile 与 cacheability 归因  
**版本/分支/核验 commit**：V2 / `mem_ut_uvm_v2` / `6646f8f53c8e37791fbbf5b854427a452292d17a`  
**发现时间**：仿真 `4306.6ns`，现实日期 `2026-09-21`  
**测试用例**：同上，UID23，VA `0x83e9c1fb`，4B misaligned load  
**日志绝对路径**：同本文件第一节  
**波形绝对路径**：同本文件第一节

### RM/测试框架问题描述

UID23 的 DUT 正常返回数据且 `exception=0`；RM 却期望 `0x10`（Load Address Misaligned）。日志显示
PBMT=00、`hdMisalign=1`，但 RM 的 `allNormalCacheable=0`。当前 RM 将 PMA 命中 C=0 与 PMA C 属性模型
未完成混为 `dcache_fact_needed_for_c`，再据此保守推导非对齐异常。非 PBMT 模式下 V2 RTL 由 PMA/PMP
直接决定 C 属性，DCache 不负责二次确认；该误报属于 RM。

### 源码定位

- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/mem_ut/ver/ut/memblock/seq/base_seq_help/memblock_pma_pmp_model.sv:21-23, 118-119, 876-891`：`PMA_PMP_DCACHE_FACT_*` 与 `dcache_fact_needed_for_c`。
- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/mem_ut/ver/ut/memblock/env/src/memblock_rm/memblock_rm.sv:623-675`：C 属性和非对齐期望生成。
- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/system/SoC.scala:61-77`、`src/main/scala/xiangshan/backend/fu/PMA.scala:147-174`：V2 PMA 配置和 RTL PMA 表构造。

### RM 修改方案

删除 RM 中不存在于 RTL 架构的 DCache C 属性确认状态：

1. 删除 `PMA_PMP_DCACHE_FACT_*`、`dcache_fact_needed_for_c` 和 `finalize_cache_path_af()`。
2. PMA 命中后直接使用 `pma_entry.c`：C=1 为普通 cacheable，C=0 为 non-cacheable，`af_decided=1`。
3. PMA/PMP 未命中或权限拒绝时直接生成对应 Load/Store Access Fault。
4. 只有明确 PMA 命中 C=1、PBMT=00、无 translation/access fault 且 `hdMisalign=1` 时，才抑制 RM 的
   Address Misaligned 期望；不再把模型未完成状态当作非 cacheable。
5. 先核对 `PMAConfigs` 的 source-order/reverse 映射和 CSR 写入 snapshot，确保测试地址
   `0x80000000..0x90000000` 的 C 属性与 V2 RTL 一致，再重新运行 UID23。

### Review 门禁与状态

## batch 收尾 redirect 选择器误调用非 redirect 事件

**问题类别**：测试框架
**责任子类型**：monitor batch 仲裁/事件生命周期
**版本/分支**：V2 / `mem_ut_uvm_v2`
**发现时间**：仿真 `369813.1ns`，现实日期 `2026-09-21`
**测试用例**：`tc=basicTest`，`ts=memblock_dispatch_real_mmu_sv39_pbmt0_non_nc_vseq`，seed `710006`，100000 请求
**日志绝对路径**：`/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/mem_ut/ver/ut/memblock/sim/rm_pma_c0_misalign_fix_run_20260921/log/tc=basicTest_ts=memblock_dispatch_real_mmu_sv39_pbmt0_non_nc_vseq_cfg=tc_dispatch_real_mmu_sv39_pbmt0_non_nc_100k_safe_nocross16_seed=710006_rtl.log`

### 问题描述

RM 前序比较全部通过，收尾时框架报：

```text
[DISP_MON_BATCH] redirect_from_event requires redirect event
```

`select_oldest_redirect()` 使用 `!found || redirect_event_is_older(...)`，依赖逻辑表达式短路；比较 helper
又直接把尚未选中的空 `selected` 事件送入 `redirect_from_event()`。最后一批事件实际是普通 issue/fault
反馈，没有有效 redirect，导致框架自身的 redirect 保护触发 fatal。该问题不涉及 RTL 输出。

### 修改方案与验证

在 `dispatch_monitor_batch_handler.sv` 和同型的 `exception_redirect_replay_handler.sv` 中，将首次选中
redirect 与后续 older 比较拆成显式分支；`event_is_redirect()` 使用严格 `redirect.valid === 1'b1`，
`redirect_event_is_older()` 对 candidate/best 先做合法性检查。这样普通或空事件只会被跳过，不会进入
redirect payload 解包。

修复版本已重新编译并重跑 seed `710006`。截至当前观察约 `2.31ms` 仿真时间，`UVM_FATAL=0`、
`UVM_ERROR=0`，原 fatal 未再出现，仿真仍在自然运行。

### 首 seed 长跑结果与后续测试框架修复

首 seed 最终在仿真 `10000000ns` 触发：

```text
[PH_TIMEOUT] Explicit timeout of 10000000.000ns hit, indicating a probable testbench issue
UVM_ERROR : 0
UVM_FATAL : 1
```

截至超时已完成约 68374 笔 RM compare，所有 `RM_LS_COMPARE` 均为 PASS；没有 RM mismatch，也没有 RTL
异常证据。根因是 `basicTest.sv:106` 固定设置 `uvm_top.set_timeout(10000us,1)`，对 100000 请求的真实
fault/redirect/replay drain 不足，测试框架在合法事务尚未全部终态时提前终止。

最小修改是将 basicTest 安全超时提高到 `100000us`，只扩大框架等待上限，不改变 DUT 激励、RM 期望或
redirect 行为。该修改后需重新编译并重跑首 seed，再继续随机回归。
