### RM/测试框架问题描述

这是测试框架问题，不是 RTL 比较失配。`uid=15` 的 scalar halfword store 使用 `ROB=0/15`、`SQ=0/9`，地址低四位为 `0xf`，属于当前 cfg 明确开启的 `CROSS_16B_SAME_LINE` 场景。首次 TLB miss 后，DTLB 已在波形中给出有效命中响应；但 StoreUnit 的 `feedbackSlow.hit` 仍会因 cross-16B misalign replay 为 `0`。该接口没有把 TLB miss 与 misalign replay 的原因拆开，测试框架必须接受连续的 `hit=0` replay。

现有 `capture_sta_late_fault_tombstone()` 把每一个不同的 `(dynamic_epoch, issue_epoch, replay_seq)` 都加入同一 UID 的 history。replay recovery 每次递增 `replay_seq`，于是 UID15 在 `1867.7ns` 至 `3222.7ns` 连续累积到 56 条，随后在 `3247.7ns` 触发：

```text
UVM_FATAL ... [STA_LATE_TOMBSTONE] tombstone history overflow
uid=15 dynamic_epoch=0 size=56 max=56
```

该 fatal 阻断了合法的 replay 流程，也改变了测试框架驱动的后续行为；它不是 RM 对 DUT 结果的误判。

排除 RTL 的证据如下：

- 波形中 `top_tb.U_MEMBLOCK._inner_dtlb_st_tlb_st_io_requestor_0_resp_bits_miss` 在 `1885.2ns` 后已经为 `0`，而 `top_tb.U_MEMBLOCK._inner_StoreUnit_0_io_feedback_slow_bits_hit` 仍出现 `0`。
- `build/rtl/StoreUnit.sv` 明确将 `feedback_slow_bits_hit` 定义为 TLB hit 与 `~s2_misalignNeedReplay` 的合取，因此 cross-16B replay 输出 `hit=0` 是该 RTL 已定义的接口语义，而不是无来源或 X 态传播。
- 临时仅将 `MEMBLOCK_BOUNDARY_CROSS_16B_SAME_LINE_WT=0` 后，同一 seed 的诊断运行在 `4957.7ns` 通过，且 `UVM_ERROR=0`、`UVM_FATAL=0`。该运行只用于确认触发条件，不是正式修复，因为不能通过删除原用例的 cross-16B 覆盖来规避问题。

### RM 修改方案

保留 tombstone 的“最早可归属 late fault”语义，但把同一 active dynamic instance 的后续 replay 合并到既有 record：

1. 继续先严格检查完全相同的 `(dynamic_epoch, issue_epoch, replay_seq)` 重复项；ROB、SQ 或 flush identity 不一致仍报 fatal。
2. 如果 record 的 `dynamic_epoch`、`rob_key`、`sq_key` 已与当前 active STA 相同，而 issue/replay identity 已变化，则只允许当前 `target_flush_epoch` 不小于该最早 record 的 epoch；满足时不新增 history，也不覆盖已有的最早 record。该判断不要求两个 epoch 相等，因为同一存活 UID 可以跨无关的年轻 redirect；epoch 回退仍是 framework 状态损坏，必须 fatal。
3. 保留首条 record 的 `issue_epoch`、`replay_seq`、`target_flush_epoch` 和 `create_cycle`。这与现有 fallback “选择最早 compatible record”的规则一致，因此不会把迟到 fault 静默丢弃，也不会把它转为新的 generation。
4. 保持 `mark_replay_pending()`、issue queue、fault writer、reset/redirect/terminal cleanup 和容量 fatal 不变；不增加 plusarg，不修改 cross-16B 权重，不修改 RTL。

该方案只扫描当前 UID 的有界 tombstone queue，最坏仍是 `MEMBLOCK_DUT_SQ_SIZE=56`，不引入主表扫描。正式实现计划为：

### RM/测试框架问题描述

这是测试框架问题，不是 RTL 问题。`uid=5` 的 STA fault 已由正确临时 RTL 正常输出，monitor 以 `exception_vec=24'h80` 归属到 `ROB=0/5`，并由既有 fault terminal 路径在 `1747.7ns` 完成 non-success retire。此后测试框架没有发送 `io_redirect_valid`，所以 fault 之后的年轻 UID 仍保留在 DUT 的 LSQ/issue 状态中；其中 UID11 的 replay 被旧 SQ 状态阻塞，UID15 持续 STA replay，最终 `terminal_done_uid` 长期停在 11。

fault 已成为 modeled ROB head 时，`io_ooo_to_mem_isStoreException=1` 只用于 DUT 选择 store exception address；它不是 redirect，也不会取消年轻的 StoreQueue/LoadQueue entry。当前 `handle_fault_event()` 仅消费 recovery queue，`mark_fault_rob_commit_uid()` 也仅建立 fault token 和该 sideband，因此二者之间没有建立“fault head -> redirect driver -> DUT cancel sample -> framework flush/reissue”的闭环。

### RM 修改方案

在 `sync_modeled_head_after_fault_terminal()` 确认 fault token 已完成 `isStoreException` 驱动和 non-success terminal 后，构造一次 `flushAfter` redirect：`valid=1`、`rob_key=fault head ROB`、`level=0`、`flush_itself=0`、`is_vls_exception=0`。该 redirect 保留已经 terminal 的 fault UID，只覆盖其后的年轻 UID。

必须通过已有 `request_redirect_flush() -> push_redirect_drive() -> memblock_redirect_dispatch_base_sequence -> redirect monitor anchor -> apply_redirect_flush()` 闭环执行，禁止直接删除 issue queue、强制释放 LQ/SQ map、伪造 `lqDeq/sqDeq` 或改动 RTL。当前 auto main-table 场景把 UID 表示为待完成的 MemBlock 请求工作集；既有 redirect owner 对被覆盖年轻 UID 的定义是 cancel 后重新 admission。该行为保留 100-request 压力测试覆盖，且不把 fault UID 重新发射。若未来需要建立完整前端 trap/program-stream 模型，应另设计划实现“年轻指令终止、不重发”的架构语义，不能混入本最小修复。
