### Bug 现象

正常情况下，SBuffer 对一拍前有效的 forwarding query 产生 slow response；没有对应 query 的拍，
其 `forwardMask`、`forwardData` 和 sideband 不能参与 LoadUnit 的控制计算。实际设计没有表达独立的
slow-response valid，SBuffer 内部仅在 `forward.valid` 为高时更新候选寄存器。无效 query 或启动后未被
覆盖的寄存器值仍可能通过 `Mux1H` 到达输出，LoadUnit 又无条件合并三路 forwarding mask。

波形中约 `580ns`，`LoadUnit_2` 的 `io_sbuffer_valid=0`，但
`io_sbuffer_forwardMask[15:0]=X`；同拍 LSQ/UBuffer forwarding mask 都是已知 `0`，
`io_lsq_forward_dataInvalid=0`，待执行 load 的 `s2_in_r_mask=16'h8000`。因此该 X 不是 RM 或
测试框架生成的数据，而是已进入 DUT 内部的 `SBuffer -> LoadUnit_2` forwarding 接口。

LoadUnit 将 LSQ、SBuffer、UBuffer 三路 mask 直接按位 OR，令 `s2_fwd_mask` 和 `s2_full_fwd` 变为 X；
后者继续参与 DCache miss、bank-conflict、RAW/RAR query、replay 和安全写回控制。约 `690.6ns`，DUT
顶层 `io_mem_to_ooo_writebackLda_2_valid` 变为 X，硬检查依次报告：

```text
RM writeback valid is X/Z: source_kind=1 lane=2
LDA2 valid is X/Z
```

这两条报告都只是 monitor/observer 对同一 DUT 输出的采样，不是 `RM_LS_COMPARE`，也不是 RM 反向驱动
了 DUT。仿真随后在 `720.6ns` 因累计 10 个 `UVM_ERROR` 结束。

同一 FSDB 在约 `565.6ns` 还观察到 `LoadUnit_2.s0_rep_stall=X`，原因是
`io_replay.valid=0` 时组合逻辑仍读取 `io_replay.bits.uop.lqIdx`。这是无效 payload 未隔离的独立风险，
需要一并修复；但当前证据不把它声明为本条 SBuffer forwarding 致命链的唯一首因。

### RTL 修复方法

修复目标不是在顶层 LDA2 valid 或 DCache E 通道把 X 强制改成 `0`，而是恢复 SBuffer forwarding 的
request/response 时序合同：S1 的 `forward.valid` 发起 query，S2 只能消费该 query 在下一拍产生的
slow response。以下代码为建议修改逻辑的源码级示意；实现时应沿用当前参数化宽度和类型，不应把示意中的
零值宽度机械复制。

#### 1. 增加 SBuffer 专用的 slow-response valid 接口

**建议修改位置**：

- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/Bundles.scala:185-214`
- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/sbuffer/Sbuffer.scala:198`
- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/pipeline/LoadUnit.scala:141`
- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/pipeline/HybridUnit.scala:65`

**建议源码修改逻辑**：不要直接给通用 `LoadForwardQueryIO` 增加字段。该 bundle 还被 StoreQueue/LSQ 和
Uncache 使用；把 SBuffer 的时序语义写入通用接口会无谓扩大改动面。建议从它派生 SBuffer 专用 bundle，只有
SBuffer、LoadUnit 的 `sbuffer` 端口和 HybridUnit 的 `sbuffer` 端口使用该子类：

```scala
// Bundles.scala
class SbufferForwardQueryIO(implicit p: Parameters) extends LoadForwardQueryIO {
  // 1 表示本拍的慢响应属于前一拍有效 query，可由 load S2 消费。
  val forwardRespValid = Input(Bool())
}

// Sbuffer.scala / LoadUnit.scala / HybridUnit.scala
val forward = Vec(LoadPipelineWidth, Flipped(new SbufferForwardQueryIO)) // Sbuffer
val sbuffer = new SbufferForwardQueryIO                                  // LoadUnit/HybridUnit
```

`/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/MemBlock.scala:923`
和 `:1070` 的现有 `<>` 连接可保留；两端改为同一个专用 bundle 后，新字段会随连接贯通。

**修改逻辑说明**：`forwardRespValid` 不是命中位，也不是当前拍的 S1 request valid。它只回答一个问题：
“本拍的 `forwardMask`、`forwardData`、`dataInvalid`、`matchInvalid` 和 `addrInvalid` 是否属于前一拍的
有效 query？”这样可区分“前一拍有 query，S2 可以消费 response”和“前一拍没有 query，所有 slow-response
payload 必须不可消费”两种状态，同时不改变 LSQ/Uncache 现有接口及其独立时序。

#### 2. SBuffer 生产端生成 valid，并消除无效 response 的 X/旧值

**建议修改位置**：

- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/sbuffer/Sbuffer.scala:783-851`

**建议源码修改逻辑**：在每个 `io.forward` port 内，使用与现有 candidate 寄存器相同的寄存器边界保存
slow-response valid；candidate 寄存器增加确定初值；随后所有 slow-response 输出先赋确定默认值，只在
`slowRespValid=1` 时选择原有候选。

```scala
// 位于 for ((forward, i) <- io.forward.zipWithIndex) 内
val slowRespValid = RegNext(forward.valid, false.B)
forward.forwardRespValid := slowRespValid

// 取代原先未初始化的 RegNext(forward.valid) 门控；同一 valid 边界覆盖 sideband。
val tagMismatch = slowRespValid && VecInit(widthMap(w =>
  GatedValidRegNext(vtag_matches(w)) =/= ptag_matches(w) &&
  GatedValidRegNext(activeMask(w) || inflightMask(w))
)).asUInt.orR

// 原有 match/candidate 表达式保持不变，只补齐 reset 初值。
val validTagMatchReg = valid_tag_matches.map(
  RegEnable(_, false.B, forward.valid))
val inflightTagMatchReg = inflight_tag_matches.map(
  RegEnable(_, false.B, forward.valid))
val maskCandidateReg = RegEnable(mask_candidate,
  0.U.asTypeOf(mask_candidate), forward.valid)
val dataCandidateReg = RegEnable(data_candidate,
  0.U.asTypeOf(data_candidate), forward.valid)

forward.dataInvalid  := false.B
forward.matchInvalid := tagMismatch
forward.addrInvalid  := false.B
for (j <- 0 until VDataBytes) {
  forward.forwardMask(j) := false.B
  forward.forwardData(j) := 0.U
  when (slowRespValid) {
    // 保持原有优先级：active/valid entry 覆盖 inflight entry。
    when (selectedInflightMask(j)) {
      forward.forwardMask(j) := true.B
      forward.forwardData(j) := selectedInflightData(j)
    }
    when (selectedValidMask(j)) {
      forward.forwardMask(j) := true.B
      forward.forwardData(j) := selectedValidData(j)
    }
  }

  // fast response 是当前拍 S1 query 的结果，必须用当前 valid 门控。
  forward.forwardMaskFast(j) := Mux(forward.valid,
    selectedInflightMaskFast(j) || selectedValidMaskFast(j), false.B)
}
```

**修改逻辑说明**：原来的 `RegEnable(..., forward.valid)` 在 `forward.valid=0` 时保持旧值，且没有确定初值；
`Mux1H` 会继续看到这些延迟候选。原代码还把 `forwardData` 和 `addrInvalid` 赋为 `DontCare`，所以“没有有效
slow response”在硬件上没有明确表达，启动 X 或上一笔 query 的残留结果可进入 forwarding 通路。

上述修改不改变真实 query 的匹配、合并和 active-entry 高优先级，只增加边界：`slowRespValid=0` 时
`forwardMask=0`、`forwardData=0`、所有 sideband 为 `0`；`slowRespValid=1` 时才按原优先级输出真实结果。
特别地，`forwardMaskFast` 属于当前拍 S1 fast path，不能错误地使用一拍延迟的 `slowRespValid` 门控，否则连续
query 会错位一拍。

#### 3. LoadUnit 与 HybridUnit 在消费者侧按 response valid 合并

**建议修改位置**：

- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/pipeline/LoadUnit.scala:1356-1399`
- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/pipeline/HybridUnit.scala:985-990`
- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/pipeline/HybridUnit.scala:1168`

**建议源码修改逻辑**：在两个 consumer 的 S2 forwarding merge 前，将 SBuffer 的 payload 转为以
`forwardRespValid` 门控的局部信号；后续 mask、data mux 和 `matchInvalid` 只使用局部信号。

```scala
val s2SbufferRespValid = io.sbuffer.forwardRespValid
val s2SbufferMatchInvalid = s2SbufferRespValid && io.sbuffer.matchInvalid
val s2SbufferMask = Wire(Vec(VLEN / 8, Bool()))
val s2SbufferData = Wire(Vec(VLEN / 8, UInt(8.W)))

for (i <- 0 until VLEN / 8) {
  s2SbufferMask(i) := Mux(s2SbufferRespValid,
    io.sbuffer.forwardMask(i), false.B)
  s2SbufferData(i) := Mux(s2SbufferRespValid,
    io.sbuffer.forwardData(i), 0.U)
  s2_fwd_mask(i) := io.lsq.forward.forwardMask(i) ||
    s2SbufferMask(i) || io.ubuffer.forwardMask(i)
}
val s2_fwd_vp_match_invalid = io.lsq.forward.matchInvalid ||
  s2SbufferMatchInvalid || io.ubuffer.matchInvalid
```

HybridUnit 使用相同的四个局部信号，并在 `s2_fwd_mask`、`s2_fwd_data` 和 `s3_vp_match_fail` 中替换直接读取的
`io.ldu_io.sbuffer.forwardMask/forwardData/matchInvalid`。

**修改逻辑说明**：这里不能以当前拍 `io.sbuffer.valid` 门控。它表示 S1 正在发出的下一笔 query，而 S2 正在
消费的是上一拍 query 的 response；连续 query 时二者可同时为 1，query 后 bubble 时则可能一个为 0、另一个为 1。
只有 `forwardRespValid` 与当前 S2 payload 对齐。生产端的确定输出和消费者端的门控应同时保留：前者保证接口
本身无 X，后者确保未来即使 SBuffer 某个字段遗漏默认赋值，`s2_full_fwd`、DCache miss/bank-conflict、RAW/RAR
query、replay 和 writeback 控制也不会消费无效 payload。

#### 4. 独立隔离 replay 的无效 payload

**建议修改位置**：

- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/pipeline/LoadUnit.scala:307-319`
- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/pipeline/HybridUnit.scala:207-217`

**建议源码修改逻辑**：将所有 `replay.bits.uop.*` 的控制比较置于对应 `replay.valid` 的控制域内。

```scala
// LoadUnit.scala
val s0_rep_stall = io.replay.valid && (
  (io.ldin.valid && isAfter(io.replay.bits.uop.lqIdx, io.ldin.bits.uop.lqIdx)) ||
  (io.vecldin.valid && isAfter(io.replay.bits.uop.lqIdx, io.vecldin.bits.uop.lqIdx))
)

// HybridUnit.scala
val s0_rep_stall = io.ldu_io.replay.valid && io.lsin.valid &&
  isAfter(io.ldu_io.replay.bits.uop.robIdx, io.lsin.bits.uop.robIdx)
```

**修改逻辑说明**：`Valid` 接口只承诺 `valid=1` 时 payload 有语义，`valid=0` 时 `bits.uop.lqIdx/robIdx` 不承诺
为零或已初始化。原表达式即使 replay 无效仍读取 payload，因此波形中约 `565.6ns` 的 `s0_rep_stall=X` 是另一条
invalid-payload X 泄漏风险。它不能替代 SBuffer slow-response 修复，二者都应落地。

#### 5. 修改后的时序与验收边界

修改后第 `t` 拍 `forward.valid=1` 时产生当前拍 fast response；第 `t+1` 拍
`forwardRespValid=1`，LoadUnit/HybridUnit 才能消费第 `t` 拍 query 的 slow response。若第 `t` 拍没有 query，
则第 `t+1` 拍 `forwardRespValid=0`，slow-response 的所有控制字段均为确定非作用值，不能进入
`s2_fwd_mask`、replay、uarch drain、exception 或 writeback 控制锥。

修复后应保持 `+MEMBLOCK_HARD_XZ_CHECK_EN=1` 重跑本 seed，并至少覆盖“无 SBuffer entry、有 active entry、
有 inflight entry、连续 query、query 后 bubble、redirect/kill 后 bubble”六类 forwarding 时序，同时检查
LoadUnit 和 HybridUnit。不得以关闭 X/Z 检查、仅对 LDA2 valid 或 DCache E `sink` 强制为零、或只初始化顶层
输出作为通过标准；这些做法只能隐藏已经发生的 X，不能恢复 request/response 的时序合同。

### 关闭硬 X/Z 检查后的补充传播证据

为确认 `LDA2 valid=X` 不是 monitor 误报，曾对同一 seed 做过一次仅诊断用途的
`MEMBLOCK_HARD_XZ_CHECK_EN=0` 重跑。该运行在 `700.6ns` 已观察到 DUT 输出
`io_ooo_to_mem_issueLda_2_ready=X`，随后 X 进入 LoadPipe、DCache miss request 与 MissQueue；
`735.6ns` 顶层 E 通道出现 `valid=1, sink=00x`，最终在 `745.6ns` 被 responder 的 GrantAck owner
账本报告为无 owner 的 E 请求。TB 在该窗口只驱动确定的 D response 和 E.ready，不能向 DUT 的
E.valid/E.sink 注入 X。

独立 review 确认 E 通道报错也是 DUT X 传播的次生现象，而非 RM 或 responder 根因；但当前证据尚未
严格证明它与本章的 SBuffer invalid-forwarding 是同一个最初源头，也没有证明它是第二个独立根因。
因此按“独立根因才单列章节”的规则，本周不另建 DCache E 的重复 bug 章节。后续 RTL owner 应从
`LoadPipe` 的 `s2_miss_req_valid` 与 `issueLda_2_ready` 首次变 X 的时刻反向追踪，同时保留本章的
SBuffer response-valid 修复作为首要候选。
