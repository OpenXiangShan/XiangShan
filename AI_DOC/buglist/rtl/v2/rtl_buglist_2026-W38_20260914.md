### Bug 现象

UID517 对应 `ROB=1/150`、`SQ=1/49`，是一个地址为 `0x81b70fff`、大小为 4 byte 的 scalar store。
它同时跨 16B 与 4KB page，最终发生 store page fault (`exceptionVec=0x8000`)。它是 cacheable
访问：`nc_49=0`，因此**不是**已经登记的 NC 跨 16B `rdataPtrExt` 双计数/跳项缺陷。

此 store 在 fault 后被 StoreQueue 按 `pendingPtr` 合法标记为内部 `committed`，所以精确 exception
redirect 不再取消它。正确行为应为：异常 entry 即使没有 STD data，也形成不写 SBuffer 数据的
exception-drain，最终置 `completed` 并产生 `sqDeq`，释放物理 SQ entry。

实际波形显示，SQ49 的异常、顺序授权和物理 read/deq 指针均已到位，但 DataBuffer 不接收该 entry：

| 仿真时间 | DUT 内部事实 |
|---|---|
| `128840.3ns` | `SQ49.allocated=1`，`unaligned_49=1`，`cross16Byte_49=1`。 |
| `128845.3ns` | `hasException_49=1`，STA page fault 已回填 SQ。 |
| `128850.3ns` | `committed_49=1`；这表示 SQ 内部不可再走 redirect cancel，不等同 fault 的正常架构 commit。 |
| fault 后至结束 | `addrvalid_49=1`，但 `datavalid_49=0`、`allvalid_49=0`、`completed_49=0`。 |
| fault 后至结束 | `rdataPtrExt(0)=deqPtrExt(0)=SQ1/49`；DataBuffer lane0/lane1 `enq.valid=0`，SBuffer `ready=1`，`io_mem_to_ooo_sqDeq=0`。 |

因此首个 RTL 异常不是测试框架的 `fault_head_waiting`，而是 StoreQueue 已在 SQ49 队头、下游没有背压时，
仍无法把一个已 `committed && hasException` 的 cross-16B scalar store 转为完成态。测试框架卡在
`WAIT_SQ_DEQ`、commit cursor 卡在 UID517，只是这个未释放 SQ entry 的后果。

### RTL 修复方法

#### 源码修改具体逻辑

- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/lsqueue/StoreQueue.scala:1209-1217`，`StoreQueue` 的 cross-16B DataBuffer qualification：
  - 修改位置：`misalignToDataBufferValid` 的 scalar 条件当前为 `!isVec(...) && allvalid(...)`。
  - 修改逻辑：对 scalar parent 改为 `!isVec(...) && (allvalid(...) || hasException(...))`；保持 vector 的
    `vecMbCommit(...)` 条件及 `canDeqMisaligned`、跨页 MAB gate 不变。
  - 伪代码：
    ```text
    scalar_ready = allvalid(parent) || hasException(parent)
    cross16_data_buffer_valid = allocated(parent) && committed(parent) &&
                                (scalar_ready || vecMbCommit(parent)) &&
                                canDeqMisaligned &&
                                (!cross4K || cross4KCanDeq || hasException(parent))
    ```
  - 保持边界：正常无异常 cross-16B store 仍必须等待地址和数据均有效；vector store 仍由 `vecMbCommit` 控制；
    跨页正常访问仍受 MAB high-PAddr readiness 限制；不可用此修改伪造 STD 或绕过 redirect cancel。

- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/lsqueue/StoreQueue.scala:1249,1329-1348`，异常 token 的无写完成语义：
  - 修改位置：保持现有 `toSbufferVecValid = ... && !exceptionValid` 与 `sqNeedDeq` 完成链。
  - 修改逻辑：不为 fault store 补发 STD；cross-16B exception token 入 DataBuffer 后保留 `vecValid=0`，
    使 SBuffer 不发实际内存写，同时由带 `sqNeedDeq` 的交接触发 `completed`。
  - 保持边界：不得把该异常 token 变成 NC、MMIO 或 CBO 的正常请求；不得绕过 `completed -> sqDeq` 的有序物理释放。

#### 自然语言修改说明

当前 cross-16B 优先分支错误地把“正常写数据的资格”与“异常 entry 可以释放的资格”合并为
`allvalid`。fault 后未发 STD data 是合法的，且异常 store 不应写入 SBuffer；因此该条件使 entry 同时失去
cancel 和 drain 两条出路。修复后，`hasException` 成为 scalar cross-16B 的 data-ready 旁路，与普通
DataBuffer 分支保持一致。异常 token 仍通过已有 `vecValid=0` 避免实际写内存，但可推进 `completed` 与
`sqDeq`，恢复 SQ 资源和后续 ROB progress。
