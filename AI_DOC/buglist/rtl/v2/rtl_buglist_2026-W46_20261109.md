### Bug 现象

预期：CMO 收到 denied/corrupt 后，以自己的 ROB/SQ 身份异常写回一次；后端随后发送异常 redirect。年轻 Store 被取消并恢复后，应走正常 cacheable Store 路径，最终排空并通过 Store-table 比较。

实际：CMO 异常写回在 SQ 内部握手后，状态机直接回到 idle，但旧启动资格仍为真。420.3 ns 状态机重入 req，再次保存旧 CMO 身份并清空已记录的异常；同拍 SQ 出队位置前进。之后实际请求的地址、数据和 ROB 字段取到年轻 Store，保存的完成身份却仍是旧 CMO，产生额外 Uncache 写请求及第二次旧 CMO 正常完成。

第二次完成把当前 SQ1 标为 completed，并将数据读取位置推进到 2。年轻 Store 经异常 redirect 恢复入 SQ1 后，`deqPtr=1`、`rdataPtr=2`；提交不能触发正常写入 SBuffer，排空持续不空。denied 与 corrupt 两个四项主表场景均保留为未通过，不能用 CMO 异常比较 PASS 或删去 Store/CHECK_STORE 的 isolated 用例 PASS 代替整体验收。

### RTL 修复方法

#### 源码修改具体逻辑

**功能职责**：在下游接受一次特殊请求时消费对应 SQ 项的启动资格，使后续等待响应、异常写回和返回 idle 的生命周期不再持有同一项的可启动状态。最小修复优先补齐 CMO 请求握手时的资格消费，不改后端反馈契约。

- `/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/XiangShan/src/main/scala/xiangshan/mem/lsqueue/StoreQueue.scala:1054`，`StoreQueue` 的 `pending(deqPtr)` 请求消费分支；关联 `:1019` 的 `io.cmoOpReq.fire`：
  - 现状：只有 `mmioDoReq` 清 pending，nonzero CMO 实际由 cmoOpReq 发出，没有命中该分支。
  - 建议：将清除条件扩展为 `mmioDoReq || io.cmoOpReq.fire`，仍只在实际握手时清除当前 deqPtr 对应资格；保留 `:1019` 原有 noPending=false/state=resp，以及响应和 WB 原控制。
  - 源码级伪代码：

    ```text
    // 原有 pending 初始化、STU 补充属性和其他优先级保持。
    when (mmioDoReq || io.cmoOpReq.fire) {
      pending(deqPtr) := false
    }
    // CMO 原 req -> resp -> wb -> idle/wait 流程保持。
    ```

  - 时序依据：E0 为 CMO request.fire 清 pending 并进入resp；最早E1才能response.fire并进入wb，此时启动资格RegNext已读到pending=0；最早E2才能WB.fire回idle。因此再次执行idle判断前旧资格已经消失。不能把该建议替换成仅在fault WB时清pending，因为WB同拍锁存的旧RegNext仍可触发下一拍重入。
  - 保持边界：`deqCanDoCbo` 不依赖 pending，消费资格不会关闭等待中的 CMO response.ready。valid但ready低不能清 pending；保持原请求payload与反压。普通 MMIO 的原消费分支保持。Uncache cbo.zero 的后续8B分段由resp直接回req，不经过idle，不能把pending门控扩展到每段req。正常CMO仍走wb->wait并等scommit，fault仍保留正确异常写回和后续redirect；不把fault伪装成正常提交。
  - 该清除分支保留在现有位置，其赋值优先级晚于同文件第574行的地址属性补写；同拍命中时消费资格的清零获胜。正常标量CMO依赖已完成的地址补写才可启动，未发现该动态实例在请求握手后重新补写pending的合法路径；不能为掩盖重复地址输入而把额外协议问题并入本缺陷。
  - 本次不强制修改 idle 组合关键路径或新增身份寄存器；如后续另加当前资格/completed/完整指针核验，应单独评估时序、取消及复用边界，不能把额外防御误写成已经验证的修复。

#### 自然语言修改说明

现在普通 MMIO 在请求交给下游时就消耗了“可以启动一次”的资格，CMO 却遗漏了同样的动作。异常响应虽然正确产生异常，但状态机回到空闲后仍认为这条 CMO 可以再次启动。

建议在 CMO 的真实请求被接受时同时清除资格。这样等待响应和写回的几拍时间足以让寄存的启动条件变成假；返回 idle 后不会再启动同一条 CMO，也就不会用年轻 Store 的地址配旧 CMO 的完成身份。清除的是启动资格，不是待返回请求或异常内容，已发出的请求仍须正常应答和写回，后端仍按原流程产生异常 redirect。

修复应阻断首个错误，不以强制回退读取指针、提前宣告排空、吞掉实际 Uncache 请求或屏蔽重复写回来掩盖问题。该方案仅供后续授权修复使用，本次未修改 RTL，尚无修复后验证结果。
