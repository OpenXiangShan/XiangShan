### Bug 现象

UID14 的 NC 返回已经离开 uncache entry，被输出寄存器接收；由于 LoadUnit 优先选择其他来源，
该返回长期受背压。随后 UID0 的 Load Access Fault 触发 ROB0/0、level=1 的 flush-itself redirect，
覆盖年轻的 ROB0/14。entry 内部取消逻辑不能再删除已交出的返回，而输出寄存器的 flush 固定为 false。
它在 redirect 及 LoadUnit 有限历史检查窗口过去后被接受，最终产生 `ROB0/14、LQ0/7、rfWen=1、pdest=15`
的旧 LDA 写回。框架活动 owner 已合法取消，因而报 `INT_WB_ATTACH no active uid for ROB key=0/14`。

这不是 NC 未等待 ROB 队首的激励问题：RTL 对 NC 允许投机发请求，只有 MMIO 等待 pending head。
也不是 monitor 延迟搬运旧事件：VCD 直接证明旧 payload 在 RTL staging 中跨过 redirect 后才进入 LoadUnit。
后端没有全历史取消表或 generation 保护；本 seed 未证明已污染复用后的物理寄存器，不能扩大为
“已观测到架构数据损坏”，但也不能把这种任意迟到写回认作可无条件忽略的合法行为。

### RTL 修复方法

#### 源码修改具体逻辑

修改目标仅为
`/nfs/home/lixiangrui/work/memblock_ut/XiangShan_V2/.codex_mother_integration_20261028/src/main/scala/xiangshan/mem/lsqueue/LoadQueueUncache.scala:493`
的 NC 输出 lanes。用局部单项 valid/data 寄存器替代该处固定 false flush 的 helper 调用。

功能职责：持有 NC 返回直到下游接受；若当前 redirect 覆盖已持有的完整 ROB pointer，则立即禁止
下游消费并取消该项；同拍合法的新返回仍能接替旧项。内部逻辑建议为：

```text
valid reset := false
killStored := valid && data.uop.robIdx.needFlush(io.redirect)
killIncoming := input.bits.uop.robIdx.needFlush(io.redirect)
output.valid := valid && !killStored
output.bits := data
input.ready := !valid || output.ready || killStored

if input.fire:                 // 合法同拍 replacement 优先
    data := input.bits
    valid := !killIncoming
else if output.fire || killStored:
    valid := false
```

边界约束：

- 使用完整 ROB pointer 和 `needFlush`，包括 flag、先后顺序及 flush-itself，不能只比较 value。
- stored stale 必须当拍屏蔽 output.valid，不仅在时钟沿清 valid。
- stored stale 与合法 incoming 同拍时保存 incoming，不能被旧项清除优先级误杀。
- incoming 自身被杀时消费并丢弃，不能反压等 redirect 消失后错误重放。
- stored 合法且下游背压时保持，未被覆盖的更老返回不能被清空。
- 无 redirect 时保持原一拍延迟、反压和每拍替换吞吐；reset、空项、连续 redirect 均需验证。
- 不修改共享 `AddPipelineReg`、MMIO lane、LoadUnit 过滤窗口、后端或 TB checker，不扩大该 Bug 范围。
- killStored 只依赖寄存器和 redirect；output.valid 不依赖 ready；input.ready 的下游 ready 依赖与原
  helper 相同。当前仲裁 valid 不依赖该 ready，未发现新增组合环。

#### 自然语言修改说明

返回从 entry 移入输出寄存器后，取消责任也必须移交给输出寄存器。修复在 redirect 出现的当拍按
寄存器保存的 ROB 身份判断：年轻且被覆盖的返回不再向 LoadUnit 表示有效，下一状态释放其占位；
更老的返回仍按原握手推进。如果同拍有另一条未取消的返回到来，就直接保存新返回，不因清旧项而丢新项。
这样不依赖背压持续时间，也不延长有限的 redirect 窗口，更不需要框架吞掉旧写回。
