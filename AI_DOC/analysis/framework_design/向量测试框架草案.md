# 向量测试框架草案

## 1. 文档定位

本文是 V2 MemBlock 向量访存测试框架的设计草案，讨论如何在已有标量 `lsqenq_agent`、
`lsq_ctrl_model` 和 `vecissue_agent` 基础上增加向量入队、发射和资源回收能力。

本文不是当前测试框架已实现功能的说明。当前框架仍会拒绝 vector `fuType`、vector issue、
vector writeback 和 VSTU feedback；本文描述后续 coding 时应遵守的状态关系和最小实现顺序。

本草案只讨论普通 non-segment 向量 load/store data-uop 的 LSQ 管理。segment load/store 在
DUT 中走 `VSegmentUnit` 专用路径，当前测试框架的最小方案暂时不支持它们，也不应把它们伪装成
普通 `enqLsq` range。FOF 尾 uop、whole-register、mask-register、向量 MMIO、异常、redirect、
partial replay 的完整实现属于后续扩展；其中与入队数量有关的边界规则仍在本文明确。

## 2. 核心思想

标量访存通常一条 uop 对应一个 LQ 或 SQ entry，因此现有测试框架可以把一个 `uid` 直接映射
到一个 `lqIdx` 或 `sqIdx`。向量访存不同：一个 vector data-uop 会被 VLSU 拆成多个候选
flow，需要在 Dispatch/LSQ 入队阶段一次预留一段连续 entry。

因此向量支持不能只把 `numLsElem` 从 `1` 改成 `2` 或更大。测试框架必须把“一个 uop 占用
一个 entry”的状态表升级为“一个 vector uop 占用一个连续 range”：

```text
vector uop identity
  = {dynamic_epoch, robIdx, vuopIdx}

一个 range
  = {owner identity, LQ 或 SQ 起始指针, numLsElem, 已完成状态, 尚未释放 entry 数}
```

每个物理 LQ/SQ entry 都属于这一个 range。即使其中某个候选 flow 因 `VL`、`vstart`、v0 mask
或 unit-stride 地址对齐而没有真正访问 memory，该 entry 也已经被预留，必须等到 DUT 的
实际 deq 或 redirect cancel 才能释放。

## 3. 需要保持一致的三个数量

同一个普通 vector data-uop 在不同模块里有三个容易混淆的数量：

| 名称 | 所在位置 | 含义 | 是否决定 LQ/SQ 预留 |
| --- | --- | --- | --- |
| `numLsElem` | `enqLsq.req.bits` | Dispatch 传给 LSQ 的保守连续 entry 数。 | 是。 |
| `flowNum` | `issueVldu` | 该 uop 进入 VLSU 的候选 flow 数。 | 是，必须等于同一 uop 的 `numLsElem`。 |
| `activeNum` | VSplit/merge buffer 内部 | 根据 VL、vstart、mask、地址计算得到的实际活动 flow 数。 | 否。 |

普通 vector data-uop 必须满足：

```text
enqLsq.req.bits.numLsElem == issueVldu.flowNum
```

但通常不满足：

```text
numLsElem == activeNum
```

例如普通 unit-stride store 的固定预留是 2。若 `VL=1` 且地址 16B 对齐，最终可能只有 1 个
实际 memory flow；若 `VL=0` 或所有元素被 mask-off，实际 flow 可以是 0。两种情况下
`numLsElem` 和 `flowNum` 仍然为 2，SQ range 仍然占两个 entry。

## 4. `numLsElem` 的生成

向量随机生成首先得到指令类型、`vsew`、`vlmul` 和 `veew`，之后构造器计算 `EMUL`，最后
计算 `numLsElem`。`numLsElem` 不能在 transaction 中当作与 VTYPE 无关的独立随机字段。

普通非 whole、非 mask-register 指令的基础量为：

```text
s       = vsew
l       = signed(vlmul)
w       = veew
EMUL    = 2^(l + w - s)
EEW_B   = 2^veew
SEW_B   = 2^vsew
```

`vlmul=3'b100` 是保留编码，不能生成；普通随机约束还应保证 EMUL 落在 `mf8..m8`。

对普通 vector data-uop，使用下列规则：

| 地址模式 | `numLsElem` 与 `flowNum` | 原因 |
| --- | --- | --- |
| unit-stride `vle/vse` | 固定 `2` | Dispatch 时不知道 base address 最终是否跨越 16B 边界，必须保守预留至多两个 block。 |
| strided `vlse/vsse` | `MulDataSize(EMUL) / EEW_B` | 每一个候选 flow 按 EEW 元素访问宽度拆分。 |
| indexed，`EMUL > LMUL` | `MulDataSize(EMUL) / EEW_B` | index 侧容量限制本 uop 的 flow 数。 |
| indexed，`EMUL <= LMUL` | `MulDataSize(LMUL) / SEW_B` | data 侧容量限制本 uop 的 flow 数。 |

`MulDataSize` 的取值为：

```text
mf8 / mf4 / mf2 : 2 / 4 / 8 B
m1  / m2  / m4 / m8 : 16 B
```

例如 `SEW=e32`、`EEW=e32`、`LMUL=m1` 时：

```text
unit-stride: 2
strided:     16B / 4B = 4
indexed:     16B / 4B = 4
```

### 4.1 不能直接套用普通公式的边界

| 场景 | 入队和 `numLsElem` 行为 |
| --- | --- |
| `VL=0`、`vstart>=VL`、全 mask-off | 仍按普通公式预留。它们只让 `activeNum` 变为 0。 |
| 普通 FOF 的 data-uop | 与普通 vector load 一样，需要 LQ range。 |
| FOF `fix-VL` tail | 它是 FOF 指令在普通 data-uop 之后生成的专用收尾 uop，用于根据 fault-only-first 的执行结果修正最终 VL。该 uop 不再表示任何地址访问，也没有需要在 VLSU 中执行的 data flow，因此 `flowNum=0`，不申请 LQ/SQ entry，且不发送普通 `enqLsq`。它仍须通过 FOF 专用完成/写回路径与原 FOF 指令关联。 |
| segment load/store | DUT 不走普通 LQ/SQ range，而由 `VSegmentUnit` 的专用状态机管理。当前测试框架的最小实现**暂时不支持** segment load/store：随机激励、`enqLsq` 构造、LSQ range model 和 issue scheduler 都应拒绝或跳过该类指令，不能按普通向量 load/store 公式生成 `numLsElem`。 |
| whole-register 或 mask-register | 两者都属于 unit-stride，因此每个实际访存 data-uop 固定 `numLsElem=flowNum=2`；不能使用普通 strided/indexed 的 `EMUL/EEW` 公式。whole-register 一条指令可拆成多个 data-uop，故整条指令占用的 entry 总数可能是 `2/4/8/16`。第一阶段仍不支持随机生成。 |
| partial replay | 保留原 uop 的 `numLsElem/flowNum` 和已分配 range；绝不重新入队，也不改为 replay mask 的 bit count。 |

### 4.2 whole-register 与 mask-register 的专用规则

这里的“每个 uop 固定为 2”是 LSQ 入队的保守预留，不表示该 uop 一定会形成两个实际 memory
flow。VSplit 在取得 base address 和实际 byte mask 后，仍可得到 `activeNum=0/1/2`；但已经分配的
两个 LQ/SQ entry 必须保留到 deq 或 redirect cancel。

whole-register 指令包括 `vl1r.v/vs1r.v`、`vl2r.v/vs2r.v`、`vl4r.v/vs4r.v` 和 `vl8r.v/vs8r.v`。
它传送的是完整 vector register，寄存器个数由指令的 `NF` 编码确定，不由普通 `VTYPE` 的
`LMUL/SEW/EEW` 换算决定。Decode 会将一个寄存器对应为一个实际访存 data-uop；因此测试框架必须
为每个 data-uop 分别建立 context、分配 range 和发送 `enqLsq`，不能只为整条指令入队一次。

| 指令 | 实际访存 data-uop 数 | 每个 data-uop 的 `numLsElem` | 整条指令合计预留 entry 数 |
| --- | ---: | ---: | ---: |
| `vl1r.v` / `vs1r.v` | 1 | 2 | 2 |
| `vl2r.v` / `vs2r.v` | 2 | 2 | 4 |
| `vl4r.v` / `vs4r.v` | 4 | 2 | 8 |
| `vl8r.v` / `vs8r.v` | 8 | 2 | 16 |

mask-register 指令仅指 `vlm.v` 和 `vsm.v`，并非普通向量指令的 `vm=0`。`vlm.v/vsm.v` 是将掩码位
作为内存数据读写的独立指令；它们各有一个实际访存 data-uop，故该 uop 固定预留两个 entry。
普通 `vm=0` 则仍是 `vle/vse/vlse/...` 等普通向量指令的谓词执行方式：`v0.t` 只影响元素/字节
是否实际活跃和最终 `activeNum`，不把该指令转换成 `vlm.v/vsm.v`，也不改变其既有的 `numLsElem`
公式。

## 5. 最小入队协议

顶层 `io_ooo_to_mem_enqLsq_<0..5>` 没有 `ready`。因此 standalone driver 的每一个有效
向量入队请求只能驱动一个时钟周期：

```text
有效拍：
  req.valid = 1
  needAlloc = 2'b01 (vector load) 或 2'b10 (vector store)
  req.bits  = 完整且自洽的 vector data-uop 元数据

下一拍：
  req.valid = 0
  needAlloc = 2'b00
  req.bits  = 0
```

保持 `req.valid=1` 多拍不是等待 backpressure，而是多次写入 LSQ。对于第一次实现，建议每拍
只驱动一个 vector enqueue slot，其余五个 slot 始终处于上述 idle 状态。

普通 vector load/store 的 payload 至少保持如下关系：

```text
load : needAlloc=01, fuType=vldu, lqIdx=lq_range_start
store: needAlloc=10, fuType=vstu, sqIdx=sq_range_start

enqLsq.robIdx       == issueVldu.uop.robIdx
enqLsq.uopIdx       == issueVldu.uop.vpu.vuopIdx
enqLsq.lastUop      == issueVldu.uop.vpu.lastUop
enqLsq.fuOpType     == issueVldu.uop.fuOpType
enqLsq.numLsElem    == issueVldu.flowNum
```

## 6. `lsq_ctrl` 应如何更新

### 6.1 分配阶段

当一个 vector data-uop 进入 admission 阶段，`lsq_ctrl` 先根据第 4 节算出 `count=numLsElem`。
它检查对应队列的 free count 是否不少于 `count`，以当前 enqueue pointer 作为 range 起点，
再将 pointer 前进 `count` 个物理 entry。

以 unit-stride vector store 为例，当前 SQ enqueue pointer 为 `S`：

```text
numLsElem = 2
sq_start  = S
实际占用  = S, S+1
新的 SQ enqueue pointer = S+2
新的 SQ free count      = old_free_count-2
```

这不是“每拍固定加 2”。只有该拍存在一个已接受的 vector store 入队请求时才加 2；strided、
indexed 或其他 vector uop 要加自身的 `numLsElem`。若同拍存在多个有效 slot，则每个后续
slot 的起始指针要累加之前同类队列的 `numLsElem`。

框架内部推荐采用以下自然的数据组织：

```text
vec_uop_by_key[vec_uop_key] = ctx

ctx:
  is_load / is_store
  lq_start 或 sq_start
  numLsElem
  remaining_entries
  range_complete
  原始 issue payload
  replay metadata

每个 entry 的反向索引：
  lq_owner[entry_key] = vec_uop_key
  sq_owner[entry_key] = vec_uop_key
```

必要的分配伪代码如下。这里的 `advance_lq/advance_sq` 必须沿用现有 LQ=72、SQ=56 的
环形指针算法，跨边界时 value 回到 0 并翻转 flag。

```text
allocate_vector_range(ctx):
  count = ctx.numLsElem
  require(count > 0)

  对 load：
    检查 lq_free_count >= count
    ctx.lq_start = lq_enq_ptr
    将 [ctx.lq_start, ctx.lq_start+count) 的每个 entry 指向 ctx.key
    lq_enq_ptr 前进 count
    lq_free_count 减 count

  对 store：
    检查 sq_free_count >= count
    ctx.sq_start = sq_enq_ptr
    将 [ctx.sq_start, ctx.sq_start+count) 的每个 entry 指向 ctx.key
    sq_enq_ptr 前进 count
    sq_free_count 减 count

  发送一拍 enqLsq，然后保存 ctx，等待下一采样边界确认该 range 已对 DUT 可见。
```

### 6.2 为什么不能沿用一个 UID 一个 entry

假设 `numLsElem=2` 的 unit-stride vector store 实际只执行一个 active flow。第二个 SQ entry
可能没有收到真正的数据写入，但它仍然是同一动态 vector uop 的预留资源。若框架只记录
`sq_owner[S]` 而遗漏 `sq_owner[S+1]`，后续 SQ deq 或 redirect cancel 会找不到 owner，
free count 和队列指针将从此偏离 DUT。

所以一个 `uid` 可以拥有多个物理 entry；同时也不能只用 `uid` 作为唯一键。一个宏指令可能
被拆成多个 vector data-uop，必须使用 `{dynamic_epoch, robIdx, vuopIdx}` 分辨每一个 range。

## 7. 实际执行、完成与回收

VSplit 对 `flowMask` 和地址对齐的计算只决定哪些候选 flow 实际进入 memory pipeline。merge
buffer 的完成表示该 vector uop 的所有实际工作已结束，之后该 uop 的整段 LQ/SQ entry 才可
被提交或释放。

测试框架在 merge/writeback 事件到来时只更新：

```text
ctx.range_complete = 1
```

不能在这一步修改 LQ/SQ pointer 或 free count。真正的资源回收必须严格跟随 DUT 输出的
`lqDeq/sqDeq` 物理 entry 数。每观察到一个 deq entry，就通过 `lq_owner/sq_owner` 找到
`vec_uop_ctx`，删除这一条反向索引，减少 `remaining_entries`，并将对应 queue 的 free count
加一。

```text
on_dequeue_one_entry(queue, entry_key):
  ctx = owner_map[entry_key]
  删除 owner_map[entry_key]
  ctx.remaining_entries 减一
  对应 queue 的 free_count 加一

  若 ctx.remaining_entries 为零：
    删除 vec_uop_by_key[ctx.key]
```

一个 range 的多个 entry 可以在同拍被 deq，也可以跨多拍 deq。只有最后一个 entry 被释放，
该 vector uop 的 range 生命周期才结束。

## 8. redirect、异常和 replay 的资源原则

第一阶段可暂不生成 redirect、异常和 partial replay，但 state model 必须预留正确边界：

- redirect 命中尚未完成的 vector range 时，取消数按 `numLsElem` 计算，而不是按实际
  `activeNum` 或已发出的 flow 数计算。
- FOF 的 data-uop 与普通 load 一样拥有 LQ range；只有 `fix-VL` tail 没有 range。原因是前者
  仍需发出实际访存并保存 load 的顺序/完成状态，后者只承担 FOF 最终 VL 修正，不对应任何访存地址
  或数据 flow，因而不得生成 `enqLsq`。
- segment load/store 不建立普通 LQ/SQ range；当前测试框架暂不支持该专用路径。后续单独支持时，
  应建立 segment context 来跟踪 `VSegmentUnit` 的 DTLB、cache/sbuffer、异常、redirect 与完成状态，
  而不是复用本章的 `lsq_ctrl` range owner map。
- partial replay 重发时复用原来的 LQ/SQ range、`flowNum`、source 和 uop identity；不能再
  发 `enqLsq`，否则会重复占用资源。
- 一个 vector uop 的完成事件应按 `{robIdx, vuopIdx}` 匹配，不能假设 issue lane、
  writeback lane 或 feedback lane 是事务 identity。

## 9. 建议的最小实现范围

第一轮 coding 推荐只支持一个能够验证连续 range 的闭环：

```text
普通 unit-stride vector store：vse32.v
SEW=e32, EEW=e32, LMUL=m1
vm=1, vstart=0, VL=1..4
numLsElem=flowNum=2
一次仅一个 data-uop、一个 enqLsq slot、一个 issue lane
暂时不支持 segment、FOF、whole/mask、strided/indexed、redirect、异常、partial replay
```

这个范围能验证最关键的事实：一次向量入队会把 SQ pointer 前进 2、两个物理 SQ entry 都有
owner、实际只执行一个 flow 时 range 不提前释放、最终 deq 后 free count 能回到正确值。

在这一最小闭环稳定后，推荐按如下顺序扩展：

1. unit-stride vector load：验证 LQ range 和 load writeback。
2. strided store/load：验证 `numLsElem` 为 `1..16` 的可变 range。
3. indexed store/load：验证 EMUL/LMUL 比较分支。
4. vector writeback、VSTU feedback 和 partial replay。
5. FOF、segment、whole-register、mask-register、异常和 redirect。

## 10. 主表改造：`vec_static` 与向量形态派生

### 10.1 目标和主表粒度

向量支持后，主表仍是所有静态测试输入的唯一入口。每一个 `main_table[uid]` 表项对应一个可独立
入队、发射和完成的 vector data-uop；它不是一个 flow，也不必等同于一整条宏指令。一个
whole-register 指令或 FOF 指令可以派生多个主表表项，这些表项可共享 `robIdx`，但必须有不同的
`vuopIdx`。

主表不应把所有向量字段平铺到 `main_control_transaction` 顶层。建议只增加以下三类字段：

```text
op_class:
  原有标量分类之外增加 V_LOAD / V_STORE

v_mode:
  NONE / unit_stride / strided / indexed_unordered / indexed_ordered

v_form:
  NONE / normal / whole_register / mask_load / fof / fof_vl_tail

vec_static:
  一个嵌入主表的结构体，保存本 uop 的不可变向量输入
```

`NONE` 是标量表项的中性取值。标量表项必须满足 `v_mode=NONE`、`v_form=NONE`，且
`vec_static.valid=0`；向量表项必须满足 `v_mode!=NONE`、`v_form!=NONE`，且
`vec_static.valid=1`。这样旧标量 flow 不需要读取向量结构体，也不会把随机残留值误解为向量语义。

`op_class` 只回答“该表项是向量 load 还是向量 store”；它不承担 unit-stride、FOF、whole 或
mask-register 的细分。所有细分语义由 `v_mode` 与 `v_form` 的正交组合表达。

### 10.2 `vec_static` 保存的内容

`vec_static` 只保存建表后不应随 issue、flow 拆分、writeback 或 replay 改变的输入。推荐分组如下：

| 分组 | 建议字段 | 说明 |
| --- | --- | --- |
| 有效和 uop 身份 | `valid`、`vuopIdx`、`lastUop`、`numUops` | 用于构造 `issueVldu.uop.vpu` 字段和区别同一 ROB 下的 data-uop。 |
| 向量配置 | `vl`、`vstart`、`vsew`、`vlmul`、`veew`、`vm`、`vma`、`vta`、`nf` | 是 VSplit、`numLsElem` 和元素有效范围的静态输入。 |
| 向量源操作数 | `src_1`、`src_2`、`src_3` | 分别承载 stride/index、store data、`v0` mask。`src_0` 继续使用主表已有字段，且是唯一的 base address 真源。 |
| 写回和掩码元数据 | `pdest`、`vecWen`、`v0Wen`、`vlWen`、`uop_vpu_vmask` | 由 issue builder 转换为 DUT 的 uop payload；具体字段可随 interface 适配补齐。 |

`src_4` 不建议以一个独立的原始 128-bit 字段同时保存。`vec_static` 中的语义化 VConfig 字段是
唯一真源，issue builder 按 DUT `VConfig` 编码将其打包到 `issueVldu.src_4`。同样，`fuType`、
`fuOpType`、`numLsElem`、`flowNum` 和 FOF 标志是派生结果，不在 `vec_static` 中复制保存。

向量表项固定使用：

```text
main_table.src_0 = x[rs1] 的实际值 = baseAddr
main_table.imm   = 0
main_table.vaddr = baseAddr
```

这里的 `vaddr` 只保留为主表/TLB 兼容的基地址快照，不能被解释为每个 flow 的实际访存地址。每个
flow 的地址、byte mask、active 状态和 replay 状态都属于运行期信息，应保存在
`vec_runtime[{uid, dynamic_epoch}]`，而不是 `vec_static`。

```text
main_table[uid].vec_static
  静态输入，redirect/replay 后保持不变

vec_runtime[{uid, dynamic_epoch}]
  LQ/SQ range、active/issued/done/replay flow mask、每个 flow 的实际地址和完成状态
```

### 10.3 随机和回填顺序

`fuType`、`fuOpType`、`lsq_flow`、`numLsElem` 不能与 `op_class`、`v_mode`、`v_form` 同时作为
独立随机字段。正确流程是先选择语义，再随机其输入，最后唯一地回填派生字段：

```text
1. 使用 op_class 权重选择标量类、V_LOAD 或 V_STORE。
2. 若选择 V_LOAD/V_STORE，枚举该 op_class 下所有合法的 {v_form, v_mode} 组合；
   `fof_vl_tail` 只允许在已有 FOF 组内成为候选，不能出现在普通独立表项的候选集中。
3. 用 form_weight * mode_weight 作为组合权重，从合法组合中选择一个。
4. 按选中组合随机 vec_static 的合法输入。
5. 由 {op_class, v_form, v_mode, vec_static} 回填 fuType、fuOpType、lsq_flow、
   numLsElem、flowNum、isVleff 和写回使能。
6. 执行一致性检查；不允许再修改任一选择字段来“修复”派生结果。
```

第 2 步必须先过滤非法组合，再进行加权选择；不能先独立抽取 `v_form` 和 `v_mode`，遇到非法
组合后丢弃或重抽。后者会使最终概率偏离 plus 配置，也会在合法组合权重全零时进入不可控循环。

对于普通 form 的可选组合 `c={form, mode}`，有效权重为：

```text
weight(c) = get_v_form_weight(form) * get_v_mode_weight(mode)
```

FOF 组内的两个 form 使用互补权重：

```text
FOF_DATA_WT    = MEMBLOCK_VEC_FORM_FOF_WT
FOF_VL_TAIL_WT = 100 - MEMBLOCK_VEC_FORM_FOF_WT
```

其中 `MEMBLOCK_VEC_FORM_FOF_WT` 专指会实际访存的 FOF data-uop，不包含 `fof_vl_tail`。
`FOF_VL_TAIL_WT` 是派生的有效权重，不能由另一个 plus 参数独立覆盖。两者用于已有 FOF 组内的
成员选择/优先级；无论哪一类先被选中，构造器都必须维持“至少一个 FOF data-uop 加唯一一个 tail”
的完整组关系，绝不创建孤立 tail。

只有 `weight(c)>0` 的合法组合可以进入普通候选集。若 `V_LOAD` 或 `V_STORE` 的 op-class 权重非零，
但该类不存在任何非零权重的合法组合，配置必须立即报错。

### 10.4 合法组合和 opcode 回填

当前阶段不支持 segment，因此候选集中绝不出现 `VSEGLDU/VSEGSTU`，也不提供 segment 的
`v_mode` 或 `v_form`。

| `op_class` | `v_form` | 允许的 `v_mode` | 回填 `fuType` | 回填 `fuOpType` | 特殊规则 |
| --- | --- | --- | --- | --- | --- |
| `V_LOAD` | `normal` | 四种模式 | `VLDU` | `vle` / `vlse` / `vluxe` / `vloxe` | 按 mode 选择对应 opcode。 |
| `V_STORE` | `normal` | 四种模式 | `VSTU` | `vse` / `vsse` / `vsuxe` / `vsoxe` | 按 mode 选择对应 opcode。 |
| `V_LOAD`、`V_STORE` | `whole_register` | 仅 `unit_stride` | `VLDU` / `VSTU` | `vlr` / `vsr` | 一条宏指令可派生多个 data-uop；每个 data-uop 固定预留两个 entry。 |
| `V_LOAD` | `mask_load` | 仅 `unit_stride` | `VLDU` | `vlm` | 仅表示 `vlm.v`。未来支持 `vsm.v` 时，应将 form 重命名为 `mask_register`，不能把它混入 `mask_load`。 |
| `V_LOAD` | `fof` | 仅 `unit_stride` | `VLDU` | `vleff` | 是会实际访问内存的 FOF data-uop，建立普通 LQ range。 |
| `V_LOAD` | `fof_vl_tail` | 固定 `unit_stride` | `VLDU` | `vleff` | FOF 组内的收尾 uop；有效权重为 `100-FOF_DATA_WT`。只修正最终 VL，`flowNum=numLsElem=0`，不发送普通 `enqLsq`。 |

`normal + unit_stride` 的 `numLsElem=2`；`normal + strided/indexed` 使用第 4 节的公式；
`whole_register` 和 `mask_load` 的每个实际访存 data-uop 固定为 2。`fof_vl_tail` 是唯一的
向量 form，其 `numLsElem` 和 `flowNum` 均为 0。

### 10.5 plus 权重和默认值

向量分类使用测试框架公共 plus 参数，遵循：

```text
env/plus.sv
  -> seq_csr_common 的合法性检查和 getter
  -> 主表构造器的加权选择
```

建议新增以下 plus 输入，并在 `seq_csr_common` 中生成一个派生有效值：

```text
MEMBLOCK_OP_CLASS_V_LOAD_WT
MEMBLOCK_OP_CLASS_V_STORE_WT

MEMBLOCK_VEC_MODE_UNIT_STRIDE_WT
MEMBLOCK_VEC_MODE_STRIDED_WT
MEMBLOCK_VEC_MODE_INDEXED_UNORDERED_WT
MEMBLOCK_VEC_MODE_INDEXED_ORDERED_WT

MEMBLOCK_VEC_FORM_NORMAL_WT
MEMBLOCK_VEC_FORM_WHOLE_REGISTER_WT
MEMBLOCK_VEC_FORM_MASK_LOAD_WT
MEMBLOCK_VEC_FORM_FOF_WT          // plus 输入，范围为 [0:100]

MEMBLOCK_VEC_FORM_FOF_VL_TAIL_WT  // seq_csr_common 派生有效值，不是 plus 输入
```

建议默认值为：两个 vector op-class 权重均为 `0`，`NORMAL` 和 `UNIT_STRIDE` 的子权重为 `1`，
其余 mode/form 子权重为 `0`。因此默认 testcase 保持 scalar-only；用户只需打开
`V_LOAD/V_STORE` 权重即可先获得普通 unit-stride 向量激励。

FOF 的 form 权重使用下列约束：

```text
0 <= MEMBLOCK_VEC_FORM_FOF_WT <= 100
MEMBLOCK_VEC_FORM_FOF_VL_TAIL_WT
  = 100 - MEMBLOCK_VEC_FORM_FOF_WT
```

`MEMBLOCK_VEC_FORM_FOF_VL_TAIL_WT` 由 `seq_csr_common` 在读取 `FOF_WT` 后计算，不允许在
`plus.sv`、testcase cfg 或命令行中作为第二个可配置输入。这样两个 FOF form 的有效权重始终和为
100，不会出现权重冲突或两者同时为 0。

`fof_vl_tail` 仍不是普通主表随机的独立候选。选中 `V_LOAD + fof + unit_stride` 后，构造器建立
同一 FOF 组的 data-uop 与唯一 tail；FOF 组内可按上述互补权重选择下一个待构造/待处理成员，但在
组关闭前必须保证两类成员均已建立。若选择结果指向 tail 而尚未有前置 data-uop，构造器必须先建立
或保留该 data-uop，再连接 tail；不得只创建 tail。

其余权重必须为非负整数。向量 op-class 权重为 0 时，对应 mode/form 全零是合法的；向量 op-class
权重非零时，至少应存在一个可选合法组合。`whole_register`、`mask_load`、`fof` 与非
`unit_stride` mode 的组合属于配置错误，而非运行时随机重试对象。`fof_vl_tail` 即使派生权重非零，
也不能因为该数值被加入普通独立表项的候选集合。

### 10.6 同一 ROB 多 uop 的前置改造

当前框架的 active map 假定一个 `robIdx` 只对应一个 `uid`。该假定对普通单 data-uop 的
unit-stride 测试足够，但对 whole-register 和 FOF 不成立：它们会产生同一 `robIdx` 下不同
`vuopIdx` 的多个主表表项。

在开启 `whole_register` 或 `fof` 权重前，必须将向量相关的动态身份升级为：

```text
vector_uop_key = {dynamic_epoch, robIdx, vuopIdx}
```

`robIdx -> uid` 的标量 map 可以继续服务普通标量路径；向量 writeback、feedback、range owner 和
issue/replay 反查必须使用 `vector_uop_key` 或等价的 `{robIdx, vuopIdx}` 索引。否则第二个 data-uop
激活时会覆盖或冲突于第一个 data-uop。

在该索引改造完成前，自动随机只能开启：

```text
V_LOAD/V_STORE + normal + unit_stride
vuopIdx = 0
lastUop = 1
```

`whole_register` 和 FOF 组必须从普通候选集中排除；其中
`MEMBLOCK_VEC_FORM_FOF_WT` 保持为 0，`FOF_VL_TAIL_WT` 虽按公式派生为 100，也不得触发任何
tail 构造。该限制不是 ISA 限制，而是当前 scalar-only 主表/状态表索引的实现边界。

## 11. 现有框架的改造落点

后续实现至少会涉及以下位置：

| 模块 | 当前限制 | 向量支持后职责 |
| --- | --- | --- |
| `memblock_op_behavior_util` | 拒绝 vector `fuType`。 | 为普通 `vldu/vstu` 返回正确的 `need_alloc`、LQ/SQ 使用方向和 `numLsElem`。 |
| `lsq_ctrl_model` | 单 UID 单 entry 的 map。 | 分配和维护 vector range，更新 pointer/free count，保留每个物理 entry 的 owner。 |
| `memblock_lsqenq_dispatch_base_sequence` | 强制 `numLsElem==1`。 | 从 vector uop context 取得 `numLsElem/uopIdx/lastUop` 和 range 起始指针，构造一拍 `enqLsq`。 |
| `lsqenq_agent` driver | 只接受 scalar `fuType/fuOpType`。 | 对 vector slot 允许合法 vector opcode 和 `numLsElem=1..16`，仍严格检查 idle slot 一拍协议。 |
| vector issue scheduler/sequence | 当前没有 vector issue queue。 | 从已对 DUT 可见的 vector context 构造 `issueVldu`，在 `ready=0` 时保持 payload。 |
| `vecissue_agent` driver | `valid=1` 时直接 fatal。 | 发送 vector payload，并保证 `flowNum` 与入队 range 一致。 |
| deq/commit、writeback、feedback monitor | 只认识 scalar owner。 | 用 vector range owner map 做 entry 级 deq，用 `{robIdx,vuopIdx}` 做 uop 级完成和 replay 匹配。 |

上述改动需要在正式 coding 前单独形成可执行 plan，并补齐 vector writeback、vector IQ feedback
和 redirect/cancel 的验证策略；不能仅通过删除现有 `uvm_fatal` 获得表面上的向量支持。

## 13. 当前状态

- 本文是草案，未修改 UVM/SystemVerilog 源码。
- 当前 V2 测试框架仍为 scalar-only；任何 vector `valid`、vector writeback 或 VSTU feedback
  都会触发现有保护性 fatal。
- 已完成的设计结论是：向量入队的资源真源是 `numLsElem`，而不是 `activeNum`；测试框架
  必须以连续 range 维护指针、free count、deq 和 cancel。
