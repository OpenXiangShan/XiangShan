# 向量测试框架需求文档

## 0. Flow 文档分层与使用边界

本需求文档下的向量生命周期产物分为两类不同文档，不能把它们视为同一份文档的长短版本。

| 文档类别 | 当前文件 | 主要读者和用途 | 内容边界 |
| --- | --- | --- | --- |
| `flow 逻辑文档` | `vector_admission_lsq_enqueue_flow.md`、`vector_issue_flow.md`、`vector_monitor_recovery_flow.md`、`vector_commit_dequeue_recycle_flow.md` | 后续 coding 的设计输入和实现 review | 保留真实入口、接口字段、状态所有权、队列、helper、时序边界、详细文字伪代码、异常分支和源码位置。 |
| `flow 描述文档` | `vector_lifecycle_flow_description.md` | 人工 review 的自然语言摘要 | 只按生命周期串联关键阶段、边界和决策，不重新展开 helper 内部控制流、逐字段赋值或 coding 细节。 |

`flow 描述文档` 的输入是四份 `flow 逻辑文档`，而不是另一个独立实现方案；它不能替代逻辑文档作为 coding
依据。后续发现描述文档与逻辑文档不一致时，应先按本需求文档和生命周期决策记录修正对应 `flow 逻辑文档`，再同步
更新描述文档。优先级为：本需求文档和决策记录的明确约束 > `flow 逻辑文档` > `flow 描述文档`。

### 0.1 本组文档的规划期例外

本组向量生命周期文档在 coding 开始前承担测试框架的详细设计/plan 角色，而不是 coding 完成后的“现状总结
flow”。因此本组文档不适用面向已实现 flow 的“所有函数调用必须能在当前源码中逐一定位”的要求。

- 逻辑文档中的 `vector_*()`、`*_handler()`、`*_helper()` 等名称可以是**规划新增或扩展后的设计接口**；在流程图、
  文字伪代码和调用关系中可以按普通函数调用表示。
- 名称前的“拟新增”只说明当前实现状态，不削弱其作为后续 coding 约束、调用边界和状态所有权定义的作用；不需要为了
  当前源码尚未实现而把它改写成某个已有函数内部的模糊文字分支。
- 已有源码函数和位置仍可列出，用于标明接入点、复用范围和“不改变标量既有逻辑”的边界；这不要求所有规划 helper 都
  已在当前源码存在。
- `flow 描述文档` 同样是规划期的人工 review 摘要，不是 coding 完成后的行为证明；它只抽象阶段关系，不替代逻辑
  文档中对接口、状态、时序和异常路径的约束。

该例外只适用于本需求文档所列的五份向量生命周期文档及其关联决策记录，不修改项目中其他已实现 flow 文档的编写
规则。

## 1. 主表中的向量项

主表随机出 `op_class = V_LOAD` 或 `op_class = V_STORE` 后，才进入向量初始化流程。

- 主表新增 `v_mode`：向量项的合法取值为 `unit_stride`、`strided`、`indexed_unordered`、`indexed_ordered`；标量项使用中性值 `NONE`。
- 主表新增 `v_form`：向量项的合法取值为 `normal`、`whole_register`、`mask_load`、`fof`；标量项使用中性值 `NONE`。其中 `mask_load` 专指 `vlm.v`，`fof` 表示完整的 fault-only-first 指令组，包括其 data-uop 和可能的 fix-VL tail。
- `op_class`、`v_form` 和 `v_mode` 必须从下表的**合法三元组**联合随机。每个候选的权重为
  `op_class_weight * form_weight * mode_weight`；选中后再回填对应的 `fuType` 和 `fuOpType`。不允许分别随机三个字段
  后再丢弃非法组合。
- 主表原有的 `src` 在向量项中语义更正为向量 `src_rs1`，即访存基地址 `baseAddr`。初版可直接随机一个合法基地址值。
- 主表保存一个向量表。一个向量主表项代表一条向量宏指令，而不是其中单独的一个 data-uop。

当前初版唯一允许的 `{op_class, v_form, v_mode}` 组合如下。`segment` 不在候选表中，不能通过权重启用。

| `op_class` | `v_form` | 合法 `v_mode` | 说明 |
| --- | --- | --- | --- |
| `V_LOAD` | `normal` | `unit_stride`、`strided`、`indexed_unordered`、`indexed_ordered` | 普通向量 load。 |
| `V_STORE` | `normal` | `unit_stride`、`strided`、`indexed_unordered`、`indexed_ordered` | 普通向量 store。 |
| `V_LOAD` | `whole_register` | `unit_stride` | 整寄存器 load。 |
| `V_STORE` | `whole_register` | `unit_stride` | 整寄存器 store。 |
| `V_LOAD` | `mask_load` | `unit_stride` | 仅 `vlm.v`。 |
| `V_LOAD` | `fof` | `unit_stride` | 仅 unit-stride fault-only-first load。 |

不在表中的组合一律不是随机候选，例如 `V_STORE + fof`、`V_STORE + mask_load`、`whole_register + indexed_*`
和 `mask_load + strided`。若所有合法三元组的乘积权重均为 `0`，必须在测试开始时报告 plus 配置错误，不能退化为
任意默认向量操作。

本项新增的 plus 参数与草案保持一致：

```text
MEMBLOCK_OP_CLASS_V_LOAD_WT
MEMBLOCK_OP_CLASS_V_STORE_WT

MEMBLOCK_VEC_MODE_UNIT_STRIDE_WT
MEMBLOCK_VEC_MODE_STRIDED_WT
MEMBLOCK_VEC_MODE_INDEXED_UNORDERED_WT
MEMBLOCK_VEC_MODE_INDEXED_ORDERED_WT

MEMBLOCK_VEC_FORM_NORMAL_WT
MEMBLOCK_VEC_FORM_WHOLE_REGISTER_WT
MEMBLOCK_VEC_FORM_MASK_LOAD_WT
MEMBLOCK_VEC_FORM_FOF_WT                 // plus 输入，范围 [0:100]
```

不再提供 `MEMBLOCK_VEC_FORM_FOF_VL_TAIL_WT`，也不允许将 fix-VL tail 作为主表 `v_form` 或独立
权重类型。fix-VL tail 是选中 `v_form=fof` 后，由向量表构造逻辑按 DUT 时序需要派生的内部 uop。

## 2. 向量 VTYPE 与 VL 随机要求

`vec_static` 初始化时，`vsew`、`veew`、`vlmul` 必须作为一个合法三元组随机，不能在三个字段
分别随机完成后再丢弃非法结果。三个字段的编码和实际含义如下：

```text
vsew / veew:
  00 / 01 / 10 / 11 对应 e8 / e16 / e32 / e64

vlmul:
  101 / 110 / 111 / 000 / 001 / 010 / 011
  对应 mf8 / mf4 / mf2 / m1 / m2 / m4 / m8
  100 保留，禁止使用
```

为三个字段的每个可选值提供以下 plus 权重：

```text
MEMBLOCK_VEC_VSEW_E8_WT
MEMBLOCK_VEC_VSEW_E16_WT
MEMBLOCK_VEC_VSEW_E32_WT
MEMBLOCK_VEC_VSEW_E64_WT

MEMBLOCK_VEC_VEEW_E8_WT
MEMBLOCK_VEC_VEEW_E16_WT
MEMBLOCK_VEC_VEEW_E32_WT
MEMBLOCK_VEC_VEEW_E64_WT

MEMBLOCK_VEC_VLMUL_MF8_WT
MEMBLOCK_VEC_VLMUL_MF4_WT
MEMBLOCK_VEC_VLMUL_MF2_WT
MEMBLOCK_VEC_VLMUL_M1_WT
MEMBLOCK_VEC_VLMUL_M2_WT
MEMBLOCK_VEC_VLMUL_M4_WT
MEMBLOCK_VEC_VLMUL_M8_WT

MEMBLOCK_VEC_VTYPE_ILLEGAL_0_WT         // vtypeIllegal=0 的权重，范围 [0:100]
```

`vec_static.vtypeIllegal` 是整条向量宏指令共享的 VTYPE 非法标志，不属于每个 data-uop 的独立
随机字段：

```text
vtypeIllegal = 0：VTYPE 的 illegal/vill 位为 0，表示使用合法 VTYPE 配置。
vtypeIllegal = 1：VTYPE 的 illegal/vill 位为 1，表示非法 VTYPE 负向激励。
```

`MEMBLOCK_VEC_VTYPE_ILLEGAL_0_WT` 只控制 `vtypeIllegal=0` 的命中权重，隐含的
`vtypeIllegal=1` 权重为 `100 - MEMBLOCK_VEC_VTYPE_ILLEGAL_0_WT`。参数必须位于 `[0,100]`；当
该参数为 `0` 时，不执行普通随机抽样，直接将 `vtypeIllegal` 赋值为 `1`。因此参数为 `100` 时
始终生成合法 VTYPE，参数为 `0` 时始终生成非法 VTYPE，介于两者之间时按权重随机。

当前建议默认值为 `100`，以保持普通向量访存默认走合法 VTYPE；只有显式调整 plus 参数时才增加非法
VTYPE 激励比例。该字段不改变 `vsew/veew/vlmul` 合法三元组的候选筛选，非法场景仍使用已选中的字段
快照。注意：当前 V2 MemBlock 的 `issueVldu` 顶层没有可驱动的 `uop.vpu.vill` 端口，且 `src_4` 高位
不是 VTYPE 通道，因此 `vtypeIllegal` 在本测试框架中仅作为配置/覆盖元数据；普通 MemBlock 输入必须将
实际可见的 VTYPE 字段保持为合法 canonical 值。若要验证 vill/非法 VTYPE，必须另建支持该字段的接口或
异常专用测试，不得把它编码到 `src_4` 高位。

推荐的抽样行为如下，避免将“0 权重”误解为固定生成 `0`：

```text
weight0 = MEMBLOCK_VEC_VTYPE_ILLEGAL_0_WT
if weight0 == 0:
  static_cfg.vtypeIllegal = 1
else:
  draw = uniform(0 .. 99)
  static_cfg.vtypeIllegal = (draw < weight0) ? 0 : 1
```

因此 `vtypeIllegal=0` 的概率为 `weight0/100`，`vtypeIllegal=1` 的概率为
`(100-weight0)/100`。权重超出 `[0,100]` 时必须在配置阶段报错，不能静默截断。

随机算法采用先建立合法三元组的方式：

```text
candidate = {}
for each {vsew, veew, vlmul}:
  EMUL = LMUL(vlmul) * EEW(veew) / SEW(vsew)
  if 1/8 <= EMUL <= 8:
    weight = vsew_weight(vsew) * veew_weight(veew) * vlmul_weight(vlmul)
    if weight > 0:
      candidate.add({vsew, veew, vlmul, EMUL, weight})

若 candidate 为空：报错
否则：按 weight 从 candidate 中选择一个三元组
```

选中三元组后，按以下规则派生字段：

```text
VLMAX = VLEN * LMUL(vlmul) / SEW(vsew)
```

`layout.data_uop_num` 不能在这里统一等同于 `max(1, EMUL)`。它表示会进入普通 VLSU 的 data-uop
数量，必须同时依赖 `v_form` 和 `v_mode`，完整公式见第 5.2 节。它也不等同于完整后端
`uop.numUops`：后者还可能包含基地址/stride 准备 uop，以及 FOF 的 fix-VL tail；测试框架的
向量表只记录需要直接驱动 `issueVldu` 的 data-uop。

### 2.1 VL 的按形式随机约束

`VL` 不是所有向量形式都具有相同的随机语义。只有 VL 实际控制元素范围的形式，才在
`[0, VLMAX]` 内随机；不能对 whole-register 等忽略 VL 的形式进行无意义随机。

| `v_form` / `v_mode` | VL 是否控制访存范围 | VL 生成规则 |
| --- | --- | --- |
| `normal` + 任意 `v_mode` | 是 | 在 `[0, VLMAX]` 内随机。`VL=0` 合法，表示没有活跃元素。 |
| `fof` + `unit_stride` 的 data-uop | 是 | 在 `[0, VLMAX]` 内随机，表示 FOF 的初始 VL；发生异常后，DUT 可以将最终写回 VL 缩短。 |
| `mask_load` + `unit_stride` | 是 | 在 `[0, VLMAX]` 内随机。VL 的单位是逻辑 mask bit/元素；内部实际访存字节数为 `ceil(VL/8)`。 |
| `fof` 的 fix-VL tail | 否，tail 不独立访存 | 不单独随机 VL；继承同一 FOF 宏指令的初始 VL。tail 由 `v_form=fof` 的向量表内部派生。 |
| `whole_register` + `unit_stride` | 否，整寄存器传输忽略输入 VL | 固定 `VL=0` 作为合法占位值，不提供 VL 随机覆盖；实际传输长度由 whole-register 的寄存器数和 EEW 决定。 |
| segment | 当前不支持 | 不生成该形式，因此不定义 VL 随机行为。 |

对所有需要随机 VL 的形式，先由已选的 `{vsew, veew, vlmul}` 计算 `VLMAX`，再在闭区间
`[0, VLMAX]` 内取得一个整数。对不随机 VL 的形式，必须按上表提供规定的合法值，不能沿用上一条
向量指令的 VL，也不能将其作为独立覆盖点。

同一宏指令的共享 VL 必须同时写入 `vec_static`、每个 data-uop 的 `uop.vpu.vl` 和
`src_4[7:0]`。由 `v_form=fof` 派生的 tail 也必须携带同一初始 VL；最终写回 VL 由 DUT
根据 FOF 的实际完成或异常情况产生，测试框架不得预先随机该最终值。

`EMUL`、`VLMAX`、`VL` 和 `layout.data_uop_num` 均为三元组及指令形式的派生结果，不作为无约束独立随机字段。

## 3. NF 随机约束

`uop.vpu.nf` 的编码含义为实际字段数减一，即 `NFIELDS = nf + 1`。当前不支持 segment，
因此 `nf` 不能作为所有向量形式的通用随机字段，必须由 `v_form` 约束：

| `v_form` | `nf` 合法值 | 生成规则 |
| --- | --- | --- |
| `normal` | `0` | 固定为 `0`。适用于 unit-stride、strided 和 indexed 的非 segment load/store。 |
| `fof` | `0` | 固定为 `0`。当前 FOF 仅支持单字段 load。 |
| `mask_load` | `0` | 固定为 `0`。 |
| `whole_register` | `0`、`1`、`3`、`7` | 在四个合法值中按 whole-register 的 NF 权重随机，分别表示传输 `1/2/4/8` 个完整向量寄存器。 |
| segment | 不生成 | 当前不支持。任何 `normal` 指令出现 `nf!=0` 都会被视为 segment，必须禁止。 |

whole-register 的四种候选值使用以下 plus 参数控制：

```text
MEMBLOCK_VEC_WHOLE_NF_1REG_WT    // nf=0
MEMBLOCK_VEC_WHOLE_NF_2REG_WT    // nf=1
MEMBLOCK_VEC_WHOLE_NF_4REG_WT    // nf=3
MEMBLOCK_VEC_WHOLE_NF_8REG_WT    // nf=7
```

仅将权重大于 `0` 的合法 whole-register 值放入候选集并按权重选择；如果
`MEMBLOCK_VEC_FORM_WHOLE_REGISTER_WT` 大于 `0`，但四个 whole-register NF 权重均为 `0`，
配置必须报错。plus 权重不能使 `nf=2、4、5、6` 成为 whole-register 的候选值。

## 4. VM 与 src_mask/src_3 随机约束

`uop.vpu.vm` 表示该向量指令是否使用 `v0` mask：

```text
vm = 1：不使用 v0；[vstart, VL) 内的元素均可参与。
vm = 0：使用 src_mask/src_3；对应 bit 为 1 的元素才可参与。
```

`vm` 由以下 plus 参数控制：

```text
MEMBLOCK_VEC_VM_UNMASKED_WT    // vm=1
MEMBLOCK_VEC_VM_MASKED_WT      // vm=0
```

按 `v_form` 的取值约束 `vm`：

| `v_form` | `vm` 生成规则 |
| --- | --- |
| `normal` | 在 `0/1` 中按 VM 权重随机。 |
| `fof` | 在 `0/1` 中按 VM 权重随机。 |
| `whole_register` | 固定 `1`。 |
| `mask_load` | 固定 `1`。 |
| segment | 当前不支持，不生成。 |

`src_mask/src_3` 是实际输入的 `v0` mask 数据。其值必须依赖 `vm`，不能独立随机：

```text
vm = 1：src_3 = 全 1。
        RTL 不读取 src_3，而是直接采用全 1 作为有效 mask；固定全 1 是测试框架约束，
        用于消除不会影响功能的随机差异。

vm = 0：先按 mask pattern 权重选择模式，再由该模式生成 src_3。
```

`vm=0` 时使用以下 plus 参数选择 `src_3` 的整体生成模式：

```text
MEMBLOCK_VEC_MASK_ALL_ON_WT
MEMBLOCK_VEC_MASK_ALL_OFF_WT
MEMBLOCK_VEC_MASK_DENSE_WT
MEMBLOCK_VEC_MASK_SPARSE_WT
MEMBLOCK_VEC_MASK_RANDOM_WT
```

| mask 模式 | `src_3` 的生成规则 |
| --- | --- |
| `all_on` | 所有 bit 置 `1`。 |
| `all_off` | 所有 bit 置 `0`。 |
| `dense` | 对 `[vstart, VL)` 内每个 bit 以较高概率置 `1`，初版采用 `75%`。 |
| `sparse` | 对 `[vstart, VL)` 内每个 bit 以较低概率置 `1`，初版采用 `25%`。 |
| `random` | 对 `[vstart, VL)` 内每个 bit 以 `50%` 概率置 `1`。 |

对 `dense`、`sparse`、`random` 模式，`[vstart, VL)` 外的 bit 统一置 `1`。这些 bit 不参与本条
指令的元素选择，固定取值可避免无效随机差异。`all_on/all_off` 按其名称覆盖整个 `src_3`。

当 `vm=0` 且 `src_3` 为全 0 时，实际可以没有活跃元素；但普通 data-uop 的 `numLsElem` 和
`flowNum` 仍按已有规则分配，不能因 mask 全关改为 `0` 或回收 LSQ 预留。

### 4.1 VMA 与 VTA 随机约束

`uop.vpu.vma` 和 `uop.vpu.vta` 是向量目的寄存器的合并策略，不改变地址生成、实际内存访问、
`flowNum` 或 LSQ 资源预留：

```text
vma = 0：mask-off 的目的元素 undisturbed，保留旧 vd。
vma = 1：mask-off 的目的元素 agnostic，允许 DUT 写任意值。

vta = 0：tail（元素下标 >= VL）的目的元素 undisturbed，保留旧 vd。
vta = 1：tail 的目的元素 agnostic，允许 DUT 写任意值。
```

提供以下 plus 参数：

```text
MEMBLOCK_VEC_VMA_UNDISTURBED_WT    // vma=0
MEMBLOCK_VEC_VMA_AGNOSTIC_WT       // vma=1

MEMBLOCK_VEC_VTA_UNDISTURBED_WT    // vta=0
MEMBLOCK_VEC_VTA_AGNOSTIC_WT       // vta=1
```

按指令形式生成 `vma/vta`：

| `v_form` | `vma` 规则 | `vta` 规则 |
| --- | --- | --- |
| `normal` load | 按 VMA 权重随机；仅 `vm=0` 时影响 mask-off 写回元素。 | 按 VTA 权重随机；仅 `VL<VLMAX` 时影响 tail 写回元素。 |
| `fof` load | 按 VMA 权重随机；仅 `vm=0` 时影响 mask-off 写回元素。 | 按 VTA 权重随机；仅初始或最终 `VL<VLMAX` 时影响 tail 写回元素。 |
| `normal` store | 固定 `0`。store 没有向量目的寄存器，vma 不影响访存。 | 固定 `0`。store 没有向量目的寄存器，vta 不影响访存。 |
| `whole_register` load/store | 固定 `0`。不使用普通 mask-off 合并语义。 | 固定 `0`。不使用普通 VL tail 合并语义。 |
| `mask_load` | 固定 `0`。当前不使用 v0 mask 选择。 | 固定 `0`。初版不将其作为普通 tail 合并覆盖点。 |
| segment | 当前不支持，不生成。 | 当前不支持，不生成。 |

`vma/vta` 是同一宏指令的共享 VTYPE 字段，所有 data-uop 必须相同，并同时写入 `vec_static` 和
`uop.vpu.vma/vta`。当前 V2 `src_4` 不携带 VTYPE；FOF 内部派生的 fix-VL tail 继承该 FOF
宏指令的 `vma/vta`，不单独随机。

对于 `vm=1` 的 load，`vma` 不会影响当前指令的元素结果，但仍可按权重生成，以保持 VTYPE 配置
覆盖；对于 `VL=VLMAX` 的 load，`vta` 同样不影响当前指令的元素结果。参考模型在检查 agnostic
元素时不得要求确定值；只检查实际 active 元素，以及 undisturbed 策略要求保留的元素。

### 4.2 VSTART 固定约束

当前阶段所有支持的向量形式固定 `uop.vpu.vstart=0`，不随机生成中间元素恢复执行：

```text
static_cfg.vstart = 0
每个 data-uop.uop.vpu.vstart = static_cfg.vstart
由 FOF 派生的 fix-VL tail.uop.vpu.vstart = 0
```

适用范围为 `normal` 的 unit-stride、strided、indexed，`fof`、`whole_register` 和 `mask_load`；
segment 当前不支持。固定值表示从第 `0` 个逻辑元素开始执行，当前有效元素范围为 `[0, VL)`，不覆盖
异常后从 `vstart>0` 恢复、`vstart>=VL` 的无活跃元素，以及其与 data-uop/flow 窗口交叉的场景。

后续如支持 `vstart` 随机，必须先扩展参考模型、活跃元素 mask、flow 地址期望和 FOF 异常恢复检查；
届时合法域为 `0 <= vstart <= VL`，不能单独放开该字段。

### 4.3 ISVLEFF 派生约束

`uop.vpu.isVleff` 表示当前 uop 属于 fault-only-first load。该字段不独立随机，由 `v_form` 和 uop
角色派生：

| 向量形式或 uop 角色 | `isVleff` |
| --- | --- |
| `v_form=fof` 的每个 data-uop | `1` |
| `v_form=fof` 内部派生的 fix-VL tail | `1` |
| `normal`、`whole_register`、`mask_load` | `0` |

FOF data-uop 的 `isVleff=1` 表示该 uop 经过普通 VLSU data 路径执行并可更新 FOF 的最终 VL；
其 `lastUop=0`。fix-VL tail 同样 `isVleff=1`，但 `lastUop=1`、不建立普通 LSQ range，供 DUT
识别为 FOF 的最终 VL 写回事件。测试框架不得仅依靠 `vuopIdx` 区分 FOF data-uop 与 tail。

### 4.4 基地址对齐随机约束

主表向量项中的 `src` 是 `src_rs1`，即 `baseAddr` 的唯一真源。当前所有支持的向量形式统一使用
`16B` 作为测试框架的基地址对齐粒度：

```text
BASE_ALIGN_BYTES = 16

MEMBLOCK_VEC_BASE_ALIGNED_WT   = 1    // 默认值
MEMBLOCK_VEC_BASE_UNALIGNED_WT = 0    // 默认值
MEMBLOCK_VEC_ADDR_GUARD_BYTES  = 1024 // 默认值，单位为 byte
```

向量不新增独立的虚拟地址窗口，仍使用标量普通自动主表的：

```text
MEMBLOCK_MAIN_VADDR_BASE  = 0x8000_0000
MEMBLOCK_MAIN_VADDR_RANGE = 0x1000_0000
```

默认主窗口为 `[0x8000_0000, 0x8fff_ffff]`。`MEMBLOCK_VEC_ADDR_GUARD_BYTES` 仅约束新随机
生成的向量 `baseAddr`，不修改已有 load/store 参考项的地址。设：

```text
MAIN_LO = MEMBLOCK_MAIN_VADDR_BASE
MAIN_HI = MAIN_LO + MEMBLOCK_MAIN_VADDR_RANGE - 1
G       = MEMBLOCK_VEC_ADDR_GUARD_BYTES

SAFE_LO = MAIN_LO + G
SAFE_HI = MAIN_HI - G
```

先按两个 plus 权重选择 `base_align_mode`，再仅在 `[SAFE_LO, SAFE_HI]` 内生成新的随机
`baseAddr`：

```text
BASE_ALIGNED:
  baseAddr[3:0] = 0

BASE_UNALIGNED:
  offset 在 [1, 15] 内均匀随机
  baseAddr[3:0] = offset
```

生成器必须直接在安全区间内寻找满足低位约束的候选，不能先随机整个地址再清低位或强制写低位。
初始化时必须检查：

```text
MEMBLOCK_MAIN_VADDR_RANGE >= 2 * G + BASE_ALIGN_BYTES
```

否则安全区间可能无法容纳合法的 `BASE_ALIGNED` 或 `BASE_UNALIGNED` 候选。当前 V2 的
`VLEN=128bit=16B`；默认 `G=1024B`。strided 的候选不再固化为 `±1x/±2x/±4xEEW_B`，而是由
第 4.5 节的最小/最大倍数、正负号和对齐模式参数生成；每个候选仍必须通过该节的 guard 检查。

`G` 同时约束新随机 indexed index 的范围，但不引入独立的 index 最大偏移 plus 参数。indexed 中
`veew` 是 index 元素宽度，实际 memory data 元素宽度为 `SEW_B=SEW/8`。index 按无符号 byte
offset 生成：

```text
indexFieldMax  = 2^(8 * indexEEW_B) - 1
indexOffsetMax = min(indexFieldMax, G - SEW_B + 1)

0 <= indexOffset <= indexOffsetMax
```

`veew` 决定单个 index 字段的位宽和一个 `indexedSrc1[127:0]` 分片能容纳的 index 个数；它不改变
被访问数据的元素宽度。每个有效 index 字段均表示相对 `baseAddr` 的无符号 byte offset，实际地址为：

```text
vaddr[element] = baseAddr + index[element]
```

| `veew` / indexed 指令后缀 | 单个 index 字段 | 每个 `indexedSrc1` 分片的字段数 | ISA 字段范围 | 当前新随机地址路径的实际范围 |
| --- | ---: | ---: | ---: | --- |
| `ei8` | 8 bit | 16 | `0 .. 255` | `0 .. min(255, indexOffsetMax)` |
| `ei16` | 16 bit | 8 | `0 .. 65535` | `0 .. min(65535, indexOffsetMax)` |
| `ei32` | 32 bit | 4 | `0 .. 2^32-1` | `0 .. min(2^32-1, indexOffsetMax)` |
| `ei64` | 64 bit | 2 | `0 .. 2^64-1` | `0 .. min(2^64-1, indexOffsetMax)` |

字段采用低位优先 packing。例如 `ei16` 的 `indexedSrc1` 为：

```text
indexedSrc1[15:0]    = index[0]
indexedSrc1[31:16]   = index[1]
...
indexedSrc1[127:112] = index[7]
```

提供如下 0/1 型 plus 参数控制 indexed 的元素自然对齐：

```text
MEMBLOCK_VEC_INDEX_ALIGNED_WT = 1    // 默认值；仅允许 0 或 1
```

```text
MEMBLOCK_VEC_INDEX_ALIGNED_WT == 1：
  每个生成的 index[i] 必须额外满足：
    index[i] % SEW_B == 0

MEMBLOCK_VEC_INDEX_ALIGNED_WT == 0：
  不施加上述模约束；index[i] 只需满足无符号字段范围和 indexOffsetMax。
  因此可以产生使 baseAddr + index[i] 对数据元素自然非对齐的访问。
```

该参数直接表示“是否强制对齐”，不是百分比权重。取值既非 `0` 也非 `1` 时必须在配置初始化阶段报错。
当 `SEW_B=1` 时，`index[i] % SEW_B == 0` 恒成立，两个参数取值的实际结果相同。生成时必须先计算
`indexOffsetMax`，再从满足上述全部约束的候选中选择；若对齐约束后没有候选，应重新选择上游配置或报错。

因此修改 `MEMBLOCK_VEC_ADDR_GUARD_BYTES` 后，index offset 合法范围自动联动改变。若
`G < SEW_B`，对应 indexed 配置没有合法 offset，必须报错或从合法三元组/指令候选中排除。strided
的 stride 随机与 guard 约束见第 4.5 节。

该规则适用于当前支持的 `normal`、`fof`、`whole_register` 和 `mask_load`，不区分 load/store；
segment 当前不支持。`BASE_ALIGNED` 表示按当前 VLSU 的 `16B` flow 粒度对齐，因此也天然满足
e8/e16/e32/e64 的基地址自然对齐。它是测试框架的统一约束，不是 ISA 对所有向量指令的最小对齐要求。

`BASE_UNALIGNED` 表示基地址不是 `16B` flow 对齐，不等同于必然按元素宽度未对齐。例如 e32 的
`baseAddr=0x1004` 是 `BASE_UNALIGNED`，但仍按 `4B` 自然对齐。若后续需要专门覆盖元素地址未对齐
异常，应新增独立的元素自然对齐维度，不能改变本节 `base_align_mode` 的定义。

`baseAddr` 生成后写入主表 `src`，并作为同一向量宏指令所有 data-uop 的 `src_rs1`；FOF 内部派生的
fix-VL tail 继承该值，不独立随机。生成过程不得在地址对齐后再随意裁剪地址低位，否则会破坏已选的
`base_align_mode`。本节的 `[SAFE_LO, SAFE_HI]` 只适用于这个“新随机 baseAddr”路径；地址复用路径
的规则见第 7 节。

`issueVldu` 的物理 `src_0` 宽度为 128 bit，但当前 V2 向量地址只使用低 64 bit。payload builder 必须
固定按下列方式组装，不能让高 64 bit 保留随机值：

```text
src_0[63:0]   = baseAddr
src_0[127:64] = 0
```

标量与向量的非对齐生成逻辑必须隔离：现有标量 boundary-profile 非对齐激励只适用于标量
`op_class`，不得用于 `V_LOAD` 或 `V_STORE`。主表生成识别到向量 `op_class` 后，必须跳过标量
非对齐参数和标量地址模板，改用本节定义的：

```text
MEMBLOCK_VEC_BASE_ALIGNED_WT
MEMBLOCK_VEC_BASE_UNALIGNED_WT
MEMBLOCK_VEC_ADDR_GUARD_BYTES
BASE_ALIGN_BYTES = 16
在标量 MAIN_VADDR 窗口内扣除 guard 后的向量随机基地址安全区间
由 G 派生的 strided/indexed 访问偏移约束
```

向量非对齐的地址、flow、异常和写回预期由向量测试框架逻辑独立处理；不得将标量
`MISALIGN_WITHIN_8B`、跨 8B/16B/cacheline/4KB boundary profile，或标量 misalign 结果模型直接
套用于向量项。

### 4.5 Strided 的 stride 随机约束

本节只适用于 `v_mode=strided` 的普通 load/store data-uop。`EEW_B` 是 strided 访存元素的
字节宽度，不是一个“是否对齐”的随机字段：

```text
EEW_B = 2^veew

veew = 00 / 01 / 10 / 11
EEW_B = 1 / 2 / 4 / 8 byte
```

新增以下 plus 参数：

```text
MEMBLOCK_VEC_STRIDE_ZERO_WT       = 0  // 可选覆盖；0 表示默认不生成 stride=0
MEMBLOCK_VEC_STRIDE_POS_WT        = 1
MEMBLOCK_VEC_STRIDE_NEG_WT        = 1

MEMBLOCK_VEC_STRIDE_MIN_EEW_MULT  = 1
MEMBLOCK_VEC_STRIDE_MAX_EEW_MULT  = 4

MEMBLOCK_VEC_STRIDE_ALIGNED_WT    = 1
MEMBLOCK_VEC_STRIDE_UNALIGNED_WT  = 0
```

其中 `*_WT` 为权重，`MIN_EEW_MULT` 和 `MAX_EEW_MULT` 是正整数范围边界，不是权重。初始化时
必须检查：

```text
MIN_EEW_MULT >= 1
MAX_EEW_MULT >= MIN_EEW_MULT
POS_WT + NEG_WT > 0
ALIGNED_WT + UNALIGNED_WT > 0
```

`ZERO_WT` 是独立的可选覆盖点。第一层从 `{ZERO, POSITIVE, NEGATIVE}` 中按
`{ZERO_WT, POS_WT, NEG_WT}` 选择 stride 类别；选择 `ZERO` 后直接令 `stride=0`，不再选择符号、
倍数或对齐模式。默认 `ZERO_WT=0`，因此初版默认只覆盖非零 stride；此时第一层等价于仅按
`POS_WT / NEG_WT` 选择符号。

对非零 stride，按以下顺序产生绝对值和符号：

```text
1. 按 POS_WT / NEG_WT 选择 sign = +1 或 -1。

2. 计算总绝对字节范围：
   L = MIN_EEW_MULT * EEW_B
   H = MAX_EEW_MULT * EEW_B

3. 按 ALIGNED_WT / UNALIGNED_WT 选择 stride_align_mode。

   ALIGNED：
     k = uniform(MIN_EEW_MULT .. MAX_EEW_MULT)
     magnitude = k * EEW_B

   UNALIGNED：
     在 [L, H] 内均匀选择一个不是 EEW_B 整数倍的 magnitude。
     等价实现为：
       q       = uniform(MIN_EEW_MULT .. MAX_EEW_MULT - 1)
       residue = uniform(1 .. EEW_B - 1)
       magnitude = q * EEW_B + residue

4. stride = sign * magnitude。
```

非对齐的定义为：

```text
abs(stride) % EEW_B != 0
```

上面的 `UNALIGNED` 公式不会超过配置的 `H`。不得使用
`k * EEW_B + residue` 且 `k` 仍取到 `MAX_EEW_MULT` 的写法，否则实际绝对值会超过
`MAX_EEW_MULT * EEW_B`。例如默认 `MIN=1`、`MAX=4`、`EEW_B=4` 时：

```text
ALIGNED   : 4, 8, 12, 16
UNALIGNED : 5, 6, 7, 9, 10, 11, 13, 14, 15
```

若 `EEW_B=1`，任意整数 byte stride 都天然满足 `stride % EEW_B == 0`，没有非对齐候选；若
`MAX_EEW_MULT == MIN_EEW_MULT`，区间中也没有非对齐候选。这两种情况即使随机命中
`UNALIGNED`，也必须退化为 `ALIGNED`，而不是报错或生成越界值。若 guard 过滤后当前模式不再有合法
候选，但另一个模式仍有候选，也按另一个模式重新选择；两个模式均无候选时，当前 `{VL, EEW_B, stride
参数}` 组合非法，必须重新选择上游配置或报错。

向量新随机基地址使用第 4.4 节的安全区间时，还必须对最终 stride 施加：

```text
VL == 0：不计算 (VL - 1)，视为无实际元素访问。

VL > 0：
  (VL - 1) * abs(stride) + EEW_B - 1 <= G
```

此约束同时覆盖正负 stride；负 stride 不因符号而放宽。它只过滤新生成的 strided 配置和基地址，地址
复用路径仍按第 7.5 节检查当前向量的完整实际访问范围。

`src_1` 是复用物理源字段，不应在所有向量模式中一律称为 stride。生成规则如下：

| 向量形式 | `src_1` 合法生成值 | 与本节参数的关系 |
| --- | --- | --- |
| `strided` data-uop | `src_1[63:0]` 为 `stride` 的 64-bit 二补码，`src_1[127:64]=0` | 同一宏指令的所有 data-uop 共享该 stride；写入 `vec_static`。 |
| `unit_stride`、`fof`、`whole_register`、`mask_load` | 固定 `src_1=0` | 不使用 stride 参数。FOF fix-VL tail 同样使用 canonical `0`。 |
| `indexed_unordered`、`indexed_ordered` | 当前 uop 的合法 index-vector 分片 | `src_1` 此时不是 stride；按第 4.4 节的 index 字段范围、guard 和 `MEMBLOCK_VEC_INDEX_ALIGNED_WT` 生成，不受本节任何 stride plus 参数影响。 |

即使 `baseAddr` 按 `EEW_B` 自然对齐，非对齐 stride 也会使后续元素自然未对齐。例如
`EEW_B=4`、`baseAddr=0x1000`、`stride=5` 时，元素地址依次为 `0x1000`、`0x1005`、`0x100a`。因此
`MEMBLOCK_VEC_STRIDE_UNALIGNED_WT` 默认应保持 `0`；开启前必须保证向量非对齐异常和写回预期已由
向量专有 checker 处理，不能复用标量 misalign 模型。

## 5. 向量表结构

一个向量主表项描述一条 RVV 宏指令，不描述单独一次 `issueVldu` 握手。主表保存完整的静态向量激励，
运行时状态另存于独立的 `vec_runtime_table`，不嵌套进主表：

```text
vec_table {
  vec_static_t static_cfg;     // 所有 data-uop 共用的配置和共享 source
  vec_layout_t layout;         // D 与 F：同一宏指令的固定拆分形状
  vec_uop_t uop[];             // 仅保存 data-uop；uop[i] 对应 vuopIdx=i
}

vec_runtime_table[uid] {        // 独立运行状态表，不属于主表随机字段
  vec_runtime_entry_t runtime;
}
```

- `vec_static` 保存同一宏指令的共享字段，例如包含 `vtypeIllegal` 的 VTYPE、初始 `VL`、`vstart`、mask 和 strided 形式的
  stride。`src_0` 的 `baseAddr` 必须在主表已有的 `src` 中保存，不能在 `vec_static` 中再建立第二个
  可独立修改的副本。
- `layout.data_uop_num` 是 `D`，表示普通 VLSU data-uop 数量；它不包含 Decode 的准备 uop，也不包含
  FOF 的 fix-VL tail。
- `layout.data_uop_numLsElem` 是 `F`，表示每个 data-uop 固定预留的最大 flow/LSQ entry 数。当前支持的
  非 segment 形式中，所有 data-uop 共享同一个 `F`。
- `uop[]` 为动态数组，只保存会建立普通 LQ/SQ range、会进入 VLSU 的 data-uop。数组下标与 `vuopIdx`
  一一对应，因此发射时可直接通过 `uop[vuopIdx]` 取得该 uop 的专有字段。
- FOF fix-VL tail 不是 data-uop，不占 `uop[]` 槽位，也不保存为一份预先可发射的完整 payload。它必须在
  FOF data-uop 达到允许收尾的运行状态后动态构造；tail 使用现有通用 `pdest` 字段，不新增
  专用 tail 目的寄存器字段。

主表内五个 source 的静态归属固定如下：

| 物理字段 | 主表存储位置 | 说明 |
| --- | --- | --- |
| `src_0` | 主表 `src` | 向量时 `src[63:0]` 为 `baseAddr`，高 64 bit 由 builder 置 `0`。 |
| `src_1` | `static_cfg.stride` 或 `vec_uop[i].indexedSrc1` | strided 共享；indexed 随 uop 变化；其它形式发射时置 `0`。 |
| `src_2` | `vec_uop[i].src2` | 每个 data-uop 独有；FOF tail 动态发射时置 `0`。 |
| `src_3` | `static_cfg.src_mask` | 整条宏指令共享的原始 `v0` mask。 |
| `src_4` | `static_cfg.src_vl_payload` | 统一 128-bit source 中的 VL 通道：`[7:0]=VL`、`[127:8]=0`；VTYPE 不在此字段编码。 |

### 5.1 共享拆分形状与 `vec_uop_t`

`D` 和 `F` 是同一宏指令全部 data-uop 共同使用的值，不能在每个 `uop[i]` 中复制并分别随机：

```text
typedef struct {
  // 共享 VTYPE/VL
  logic [7:0]   vl;
  logic [1:0]   vsew;
  logic [1:0]   veew;
  logic [2:0]   vlmul;
  bit           vtypeIllegal;  // VTYPE illegal/vill 元数据；当前 standalone issue 接口不可发送
  logic [2:0]   nf;
  bit           vm;
  bit           vma;
  bit           vta;
  logic [7:0]   vstart;

  // 共享 source
  logic [127:0] src_mask;       // src_3
  logic [127:0] src_vl_payload; // src_4：低 8 bit 为 VL，高位 canonical 0
  logic signed [63:0] stride;   // strided 的 src_1；其它模式置 0
} vec_static_t;
```

`src_vl_payload` 只由同一份共享 `VL` 派生，不能再随机一份独立的 VL。当前 V2 的 128-bit source 物理宽度
只是为了统一 vector source 端口；VLSU 实际只消费低 8 bit：

```text
src_vl_payload[7:0]   = vl
src_vl_payload[127:8] = 0              // 未使用高位必须清零
```

所有 data-uop（以及 FOF 动态 tail）共享同一个 `src_vl_payload` 快照。`vsew`、`vlmul`、`vma`、`vta`、
`veew`、`vm`、`vstart` 以及 `vill`（若接口支持）均由对应的 `uop.vpu` 字段发送；当前生成的 V2
MemBlock 顶层没有 `uop.vpu.vill` 输入，故 `vtypeIllegal` 不可通过本接口注入。

`vtypeIllegal=0` 时，向量项按本文其余章节的合法 VTYPE 规则计算 `EMUL`、`VLMAX`、`VL`、`D` 和
`F`。`vtypeIllegal=1` 时仅保留为配置/覆盖元数据；当前 MemBlock standalone issue 接口不能把它
发送给 DUT，因此普通向量 flow 必须筛选为 `vtypeIllegal=0`，非法 VTYPE 另建接口专用测试。

当前生命周期 flow 的普通随机 profile 明确属于“尚未实现 illegal-VTYPE 专用异常模板”的情形：普通
`V_LOAD/V_STORE` 只接受 `vtypeIllegal=0`，默认 `MEMBLOCK_VEC_VTYPE_ILLEGAL_0_WT=100`。若用户把该权重
调低而未同时选择后续新增的专用模板，主表构造期必须报出配置错误或筛除该候选，不能把 `vtypeIllegal=1`
误送入正常 success/terminal 路径。这一限制只约束当前生命周期实现范围，不改变 `uop.vpu` VTYPE 字段的真源规则。

```text
typedef struct {
  int unsigned data_uop_num;         // D，data-uop 数量，范围 1..8
  int unsigned data_uop_numLsElem;   // F，每个 data-uop 的 LSQ/flow 容量，范围 1..16
} vec_layout_t;
```

对普通 data-uop，接口字段必须从这一份共享真源派生：

```text
enqLsq.req.numLsElem = layout.data_uop_numLsElem = F
issueVldu.flowNum    = layout.data_uop_numLsElem = F
```

`F` 是保守资源容量，不是本次实际访问的 flow 数。`VL`、`vstart`、`vm/src_3`、`vuopIdx`、地址对齐和
replay mask 会在 VSplit 中形成实际 `flowMask`；实际活跃 flow 数可以小于 `F`，也可以为 `0`。即使
mask 全关或最后一个 uop 没有活跃元素，`F` 仍不能改小，也不能回收原先预留的 LSQ range。

`VL=0` 或当前 data-uop 的活动 mask 全关时，测试框架仍须完成普通 `issueVldu` 发射并等待一次宏观
`writebackVldu`。VSplit 可把该 uop 的内部 `activeNum` 派生为 `0`，并仍形成对应的 merge-buffer bookkeeping
和 uop writeback；这不改变外部 `issueVldu.flowNum=F`。`flowNum=0` 仅属于 FOF fix-VL tail，绝不能把普通
data-uop 的零活动状态编码成接口 `flowNum=0`。这不是“无需观察即可自行 terminal”的许可。因而本框架不创建额外的
零活动完成分支：仍以正常 writeback 将 `issue_accepted` 清零并置 `terminal`，LSQ range 也仍只由真实 deq 释放。

`vec_uop_t` 是已经拆出的 data-uop 的静态描述，不是完整 `issueVldu` payload，也不保存运行期
`flowMask`、实际地址或完成状态：

```text
typedef struct {
  // data-uop 身份与顺序
  int unsigned vuopIdx;
  bit          lastUop;
  bit          isVleff;
  int unsigned uop_send_pri;  // 仅测试框架调度使用，不送 DUT

  // 静态预留范围；实际起始指针在 admission 时产生
  bit          hasLqRange;
  bit          hasSqRange;
  int unsigned lqRange;       // load 预留 entry 数，等于 F
  int unsigned sqRange;       // store 预留 entry 数，等于 F

  // 随 data-uop 切换的向量源分片
  logic [127:0] src2;         // load 的 old-vd 或 store 的 vs3 data 分片
  logic [127:0] indexedSrc1;  // 仅 indexed 的 index-vector 分片

  // MemBlock 内部验证使用的回写标签和写使能
  // 不保存 ldest：该字段不属于 issueVldu 顶层输入，且本方案不模拟 Decode/Rename。
  pdest_t      pdest;
  bit          vecWen;
  bit          v0Wen;
  bit          vlWen;
} vec_uop_t;
```

字段不是独立随机量，必须从主表、`vec_static`、`layout`、uop 位置和 LSQ 分配结果派生：

| 字段 | 生成规则 |
| --- | --- |
| `vuopIdx` | 对 `i=0..D-1`，固定 `uop[i].vuopIdx=i`。不得对每个 data-uop 独立随机 7-bit 值。 |
| `lastUop` | 普通指令仅 `i=D-1` 为 `1`；FOF 的所有 data-uop 都为 `0`，详见 5.3 节。 |
| `isVleff` | `v_form=fof` 的 data-uop 固定为 `1`；其它 data-uop 固定为 `0`。 |
| `uop_send_pri` | 按 5.4 节的开关生成。它只改变测试框架的发射选择顺序。 |
| `hasLqRange/hasSqRange` 和范围 | load data-uop 保存 `hasLqRange=1,lqRange=F`，store data-uop 保存 `hasSqRange=1,sqRange=F`；另一侧置 canonical `0`。实际 `lqStart/sqStart` 依赖运行时环形指针，只在 admission launch 对应 sample/promotion 后写入 `vec_runtime_table`，指针必须保留 `flag+value`。 |
| `src2` | 初始化时对每个 data-uop 执行一次 `random_128bit()`，作为该 `vuopIdx` 的 old-vd 或 store-data 分片。该值写入表后必须稳定，replay 同一 uop 时复用，不能重新随机。 |
| `indexedSrc1` | 仅 indexed 有效，固化当前 `vuopIdx` 的 index-vector 分片；非 indexed 固定为 canonical `0`。 |
| `pdest/vecWen/v0Wen/vlWen` | 按本节的 MemBlock 内部验证简化规则派生；不模拟 Decode/Rename 的逻辑目的寄存器映射或三类 physical free-list。 |

`uopIdx` 不在 `vec_uop_t` 中重复存储。对 data-uop，它是 `vuopIdx` 的接口别名，必须按下列关系
由 builder 派生，不能单独随机：

```text
issueVldu.uop.vpu.vuopIdx = uop[i].vuopIdx
issueVldu.uop.vpu.lastUop = uop[i].lastUop
issueVldu.flowNum         = layout.data_uop_numLsElem

enqLsq.req.uopIdx         = uop[i].vuopIdx
enqLsq.req.lastUop        = uop[i].lastUop
enqLsq.req.numLsElem      = isLoad ? uop[i].lqRange : uop[i].sqRange
                           = layout.data_uop_numLsElem
```

因此一个 `uop[i]` 同时是一次普通 LSQ 预留和一次 `issueVldu` data-uop 发射的专有字段真源；`D/F`
仍由 `layout` 统一提供。当前 `issueVldu` agent 接口没有独立的通用 `uopIdx`、`firstUop` 或 `numUops`
输入，测试框架不得额外随机一个与 `vuopIdx` 不一致的后端 uop 编号。

发射 builder 必须从主表内的 `vec_table` 组装全部 source，不能在 agent transaction 中重新随机：

```text
payload.src_0[63:0]   = main_tr.src[63:0]
payload.src_0[127:64] = 0

payload.src_1 = strided ? vec_table.static_cfg.stride
              : indexed ? uop[i].indexedSrc1
              : 0
payload.src_2 = uop[i].src2
payload.src_3 = vec_table.static_cfg.src_mask
payload.src_4 = vec_table.static_cfg.src_vl_payload // [7:0]=VL，[127:8]=0
```

同一宏指令的 data-uop 共享 `src_0/src_3/src_4`；`src_1` 是否随 uop 变化由地址模式决定；只有
`src_2` 和 indexed 的 `src_1` 使用 `vec_uop[i]` 的专有值。`src_4` 不允许只赋低 8 bit 后让高位保持
随机或上一次 transaction 的残留值。

#### 5.1.1 `ldest`、`pdest` 与写使能的简化规则

当前阶段只验证 MemBlock 内部的 LSQ、VLSplit/VSSplit、地址、flow、merge、replay 和写回握手；不验证
Decode/Rename 的逻辑目的寄存器、RAT 或 physical free-list 行为。因此 `ldest` 不保存到主表、`vec_static`
或 `vec_uop_t`，也不作为 `issueVldu` payload 构造输入。尤其不覆盖 Decode 中 `ldest==0` 将普通向量写
转换为 `v0Wen` 的行为。

当前支持形式的写回字段固定按下表派生：

| data-uop 类型 | `pdest` | `vecWen` | `v0Wen` | `vlWen` |
| --- | --- | ---: | ---: | ---: |
| 普通/whole-register/mask load 的 data-uop | 稳定的普通向量回写标签 | 1 | 0 | 0 |
| FOF data-uop | 稳定的普通向量回写标签 | 1 | 0 | 0 |
| 任意 vector store data-uop | canonical `0` | 0 | 0 | 0 |

`mask_load` 在本简化模型中也使用 `vecWen=1`，不是 `v0Wen=1`。`v0Wen` 对本需求文档当前支持的
全部向量访存形式固定为 `0`。这刻意排除了“目的寄存器恰好为 v0”的 Decode/Rename 覆盖，不影响
MemBlock 对 mask-register 访存的地址、flow 和数据路径验证。

`pdest` 仅作为 MemBlock 回写侧稳定透传和测试框架匹配标签，不代表真实 physical register。定义：

```text
PDEST_BASE  = 1
PDEST_RANGE = 128

普通 vector load data-uop 或 FOF data-uop：
  pdest = PDEST_BASE + ((UID * 8 + vuopIdx) % PDEST_RANGE)

vector store data-uop：
  pdest = 0

FOF fix-VL tail：
  pdest = PDEST_BASE + ((UID * 8 + data_uop_num) % PDEST_RANGE)
```

同一个 data-uop 的首次发送、ready 停顿、replay 和最终 writeback 必须复用同一个 `pdest`；同一条宏指令的
不同 data-uop 使用不同标签。FOF tail 使用与 data-uop 不同的稳定标签，只与 `vlWen=1` 配对。该规则不需要
建立 vector、v0、VL 三套 free-list，也不要求 `pdest` 与未建模的 `ldest` 存在对应关系。

下列共享字段必须只保存一次，issue builder 从 `vec_static` 或主表复制到每个 data-uop payload，不能重复随机：

```text
robIdx、fuType、fuOpType、src_0/baseAddr、src_3/mask、src_4/src_vl_payload、
vsew、veew、vlmul、vtypeIllegal、nf、vm、vma、vta、vstart，以及 strided 的 stride/src_1。
```

其中 `src_1` 的最终组装规则为：strided 从 `static_cfg.stride` 取得；unit-stride、FOF、whole-register
和 mask-load 使用 canonical `0`；indexed 从 `uop[i].indexedSrc1` 取得。`src_2` 始终从
`uop[i].src2` 取得，`src_3` 从 `static_cfg.src_mask` 取得，`src_4` 从已经打包好的
`static_cfg.src_vl_payload` 取得（仅低 8 bit 有效，高位清零）。`uop.vpu.vmask` 在初版固定为 canonical `0`，FTQ/ROB 等公共元数据继续由
主表提供；它们都不是 `vec_uop_t` 的独立随机字段。

`isVecPartReplay`、`vecReplayMask`、`vecReplayMbIdx`、已发射状态、实际 flow 地址和完成状态都属于独立的
`vec_runtime_table`，不写入静态主表或 `vec_uop_t`。首次 issue 时 replay 字段为 `0`；发生 DUT feedback
后，以 `{主表 UID, vuopIdx}` 查找原 data-uop，更新运行时记录并重发原有静态 payload。

### 5.2 `D` 与 `F` 的派生规则

先由已选的指令形式计算 `D = layout.data_uop_num`。当前仅支持非 segment 形式，合法取值为 `1..8`；
推导结果超过 `8` 的组合必须在随机阶段排除，不能截断数组或复用 `vuopIdx`。

| `v_form` / `v_mode` | `D = data_uop_num` |
| --- | --- |
| `normal` + `unit_stride` 或 `strided` | `max(1, EMUL)` |
| `normal` + `indexed_unordered` 或 `indexed_ordered` | `max(1, LMUL, EMUL)` |
| `whole_register` | `nf + 1`，即 `1/2/4/8`。 |
| `mask_load` | `1` |
| `fof` + `unit_stride` | `max(1, EMUL)` 个 data-uop；fix-VL tail 不计入 `D`。 |

这里的 `LMUL`、`EMUL` 是实际倍率，不是三位编码按无符号数解释后的数值。`D` 计算完成后必须连续建立
数组下标和 `vuopIdx`：

```text
vuopIdx_q = new[D]  // 构建期/调试期索引表
uop       = new[D]
for i = 0 .. D-1:
  vuopIdx_q[i]     = i
  uop[i].vuopIdx   = vuopIdx_q[i]
```

`vuopIdx` 参与 VSplit 的寄存器分片、元素窗口和地址偏移计算，因此它不能独立随机，也不能出现
`0, 2, 3` 这类空洞编号。`vuopIdx_q=[0,1,...,D-1]` 可以作为构建期或调试期索引表，但唯一真源仍是
`uop[i].vuopIdx`。

再计算 `F = layout.data_uop_numLsElem`。`MulDataSize(x)` 表示当前单个 data-uop 对应寄存器分片的
字节容量：`mf8/mf4/mf2` 分别为 `2/4/8B`，`m1/m2/m4/m8` 均为 `16B`；它不是整条寄存器组的总字节数。

```text
unit-stride / whole-register / mask-load / FOF data:
  F = 2

strided:
  F = MulDataSize(EMUL) / EEW_B

indexed_unordered / indexed_ordered:
  F = (EMUL > LMUL)
      ? MulDataSize(EMUL) / EEW_B
      : MulDataSize(LMUL) / SEW_B
```

其中 `EEW_B=EEW/8`、`SEW_B=SEW/8`。对于当前支持的 data-uop，`F` 必须为 `1..16`；若候选三元组和
指令形式的计算结果落在这个范围之外，必须排除该候选。`F=0` 只属于 FOF fix-VL tail，不能用于普通
data-uop。

例如 strided `SEW=e32, EEW=e32, LMUL=m4` 时，`EMUL=m4`、`D=4`，而每个 data-uop 的
`MulDataSize(EMUL)=16B`，所以 `F=16/4=4`。四个 uop 的 `vuopIdx` 分别为 `0/1/2/3`，但每个均
预留 `numLsElem=flowNum=4`；即使 `VL` 使最后一个 uop 实际没有活跃 flow，也不能把最后一个 uop 的
`F` 缩为 `0`。

### 5.3 `lastUop` 与 FOF 动态 tail

普通指令的 `lastUop` 必须由 `D` 和数组下标唯一派生：

```text
v_form = normal / whole_register / mask_load：
  for i = 0 .. D-1:
    uop[i].lastUop = (i == D - 1)
    uop[i].isVleff = 0
```

因此单 data-uop 指令必定为 `vuopIdx=0, lastUop=1`；whole-register 只有最后一个寄存器 data-uop
的 `lastUop=1`。该值必须同时驱动 `issueVldu.uop.vpu.lastUop` 与 `enqLsq.req.lastUop`，不得作为
独立随机字段，也不得只在一个接口修改它。

FOF 的 data-uop 与收尾事件必须分开：

```text
v_form = fof：
  for i = 0 .. D-1:
    uop[i].lastUop = 0
    uop[i].isVleff = 1

  不建立静态 tail payload
  // tail 状态在 activation/re-admission 时初始化；这里仅说明该宏需要 tail
```

FOF tail 不新增专用目的寄存器字段。它在动态构造时按 5.1.1 节的顺序公式生成独立的稳定 `pdest`，并通过
`vlWen=1` 表示该标签属于 FOF 的最终 VL 写回；data-uop 的 `pdest` 仍由 `vec_uop[i].pdest` 提供。tail 的
`pdest` 不能在重试时重新随机，也不能与同一宏指令的 data-uop 标签重复。

`vec_runtime_table` 至少需要记录每个 data-uop 的 admission、当前 issue 尝试、正常终态和 replay 状态，以及
`fof_tail_pending/issued/written_back/canceled`。其中 `issue_accepted` 只表示“当前一次已 fire、尚未被 writeback 或 replay
feedback 收尾的 live 尝试”，不是历史上曾经 issue 过的永久标志；文档中出现的 `outstanding` 与此字段是同义词，
不能再维护第二个独立 bit。`suppressed` 仅为未来具备唯一可观测 FOF 抑制事件时预留，当前初版不写入。这些是随
DUT 反馈变化的运行状态，既不随机，也不作为主表的静态访存字段：

```text
vec_runtime_entry_t {
  memblock_uid_t uid;
  bit data_uop_issue_pending[];
  bit data_uop_issue_accepted[];  // 当前 live attempt，等同 outstanding
  bit data_uop_terminal[];
  bit data_uop_replay_pending[];
  bit suppressed[];            // 当前初版恒为 0，保留给后续可观测抑制事件
  bit fof_tail_pending;       // tail 尚未完成最终 VL 写回
  bit fof_tail_issued;        // tail 已 fire；在 WB 前禁止再次选择
  bit fof_tail_written_back;  // tail writeback 已采样
  bit fof_tail_canceled;      // redirect/fault 取消，禁止再次选择
}
```

`vec_runtime_table` 在主表静态项创建后建立，以主表 UID 为键；对应 uop 完成、flush 或整个宏指令生命周期
结束后回收。它只服务于测试框架的发射调度和反馈处理，不参与主表随机化，也不作为 DUT 输入字段。

初版测试框架对同一条 FOF 使用保守顺序：同一 FOF 内的 data-uop 必须按递增 `vuopIdx` 发送，不能让
`uop_send_pri` 将它们重排。只有前一个 data-uop 已达到终态，下一 data-uop 才可发送。当前顶层没有唯一的
“后续 data-uop 已被 FOF 内部抑制”事件，因此不得仅凭普通 writeback 的 `vl` 变化或推测的内部抑制，把后续
uop 标为 `suppressed` 或停止发送。顶层明确观察到的 FOF `exceptionVec` 是本需求规定的特殊 fault 路径：它先
keyed kill 并取消 tail，然后 fatal 停止 testcase；redirect/cancel 同样会停止未发射 uop。

上述逐 uop writeback 串行是测试框架为避免依赖不可见内部状态而采用的保守驱动策略，不是对 RTL 唯一合法
发射时序的断言。

该顺序由 `vec_macro_runtime_t.fof_next_vuopIdx` 唯一控制，而不是依赖 queue 当前排列：

```text
activation/re-admission：fof_next_vuopIdx = 0
FOF data-uop 可选条件：uop.vuopIdx == fof_next_vuopIdx
该 uop 正常 writeback 且无 replay/fault：fof_next_vuopIdx++
fof_next_vuopIdx == D：所有 data-uop 已完成，才允许选择 tail
redirect/fault/kill：旧 epoch 的 cursor 一并失效；新 epoch 重新从 0 开始
```

tail 的发送条件是：所有 data-uop 均已进入 `terminal`，没有 replay 在途，且当前宏指令
未被 redirect/flush；同时必须满足 `fof_tail_pending && !fof_tail_issued && !fof_tail_written_back && !fof_tail_canceled`。
`valid && ready` 只表示 data-uop 被 VLSU 接收，不代表其 flow 已经完成，因此不能
仅在最后一个 data-uop 握手后立即发 tail。

```text
若 v_form=fof 且
   fof_tail_pending && !fof_tail_issued && !fof_tail_written_back && !fof_tail_canceled：
  若未 flush
     且所有 data-uop 为 terminal
     且 fof_next_vuopIdx == D
     且不存在 replay_pending：
    动态构造并发送唯一 tail：
      isVleff = 1
      lastUop = 1
      flowNum = 0
      lqIdx   = 0                 // direct MemBlock tail 不查询普通 LQ/SQ range
      sqIdx   = 0
      src_0   = {64'b0, main_tr.src[63:0]}
      src_1   = 0
      src_2   = 0
      src_3   = 0                 // tail 不进入普通 VSplit mask 路径
      src_4   = static_cfg.src_vl_payload
      vecWen = 0
      v0Wen  = 0
      vlWen  = 1
      pdest  = PDEST_BASE + ((UID * 8 + data_uop_num) % PDEST_RANGE)
      payloadVuopIdx = 0  // 仅接口占位，不是身份
    tail fire 后：调用独立的 mark_fof_tail_fire()，置 vec_runtime_table[uid].fof_tail_issued = 1；
      在 tail writeback 前不得再次选择或发送该 tail

  若发生 flush：
    先调用 `kill_vector_driver_pending(uid,dynamic_epoch)` 清理旧 issue 所有权；
    取消未发送的 data-uop 与 tail；无论 tail 是否已经 fire，只要尚未完成 writeback 就置
    `vec_runtime_table[uid].fof_tail_canceled = 1`，并为已 fire 的 tail 写入旧 epoch 的 tail/ROB tombstone
```

tail 只发送到 `issueVldu`，绝不生成 `enqLsq.req`，也不分配普通 LQ/SQ range；其概念上的
`numLsElem=0` 仅表示“不入队”，不写入 `layout`。tail 的识别条件固定为
`isVleff=1 && lastUop=1`，不能仅靠 `{rob_key, vuopIdx}` 识别。普通 data-uop 的身份仍为
`{主表 UID, vuopIdx}`。

### 5.4 `uop_send_pri` 的测试框架调度规则

提供下列 plus 参数：

```text
MEMBLOCK_VEC_UOP_SEND_PRI_EN
```

```text
MEMBLOCK_VEC_UOP_SEND_PRI_EN = 0：
  所有 uop[i].uop_send_pri = 0

MEMBLOCK_VEC_UOP_SEND_PRI_EN = 1：
  `indexed_ordered`：所有 data-uop 的 `uop_send_pri = 0`，由 scheduler 的 vuopIdx 顺序保证有序；
  其它支持形式：每个 data-uop 独立均匀随机 uop_send_pri ∈ [0, 100]
```

`uop_send_pri` 只被测试框架 scheduler 使用，不送到 DUT，也不能改变 `vuopIdx`、`lastUop`、LSQ range、
`F`、source 或 replay identity。调度器必须采用如下确定性选择顺序：

```text
1. 在当前允许发射的候选 uop 中，优先选择 uop_send_pri 较大的 uop；
2. 若 MEMBLOCK_VEC_UOP_SEND_PRI_EN=0，所有 priority 均为 0，直接按同一宏指令的 vuopIdx 升序发送；
3. 若多个候选 uop 的 uop_send_pri 相等，则在同一宏指令内按 vuopIdx 较小者优先；
4. 若 priority 和 vuopIdx 都相同，再按 UID/ROB 年龄选择较老的宏指令，不能依赖 queue 当前排列顺序。
```

因此，“priority 关闭”或“priority 相等”都必须回退到 `vuopIdx` 顺序，不能因为候选项进入队列的
先后不同而产生不确定发射顺序。启用 priority 时，较大的 priority 可以让不同 `vuopIdx` 的 data-uop
竞争发射机会；但 priority 只是测试框架的 data-uop 调度字段，不能改变一个 uop 内部 flow 的拆分或
元素完成顺序。对于 `indexed_ordered`，若测试框架选择主动施加指令内顺序约束，仍必须使用上述
`vuopIdx` 升序规则；对于 `indexed_unordered`，测试框架可以允许 priority 造成 uop 级乱序，但不要求
每次都产生乱序，最终元素/flow 顺序由 DUT 内部逻辑决定。同一条 FOF 内部仍必须遵守 5.3 节的顺序约束。

### 5.5 标量隔离与向量运行状态

#### 5.5.1 现有标量状态模型

当前标量框架以“一条主表项对应一个 UID、一个动态状态对象”为基本单位。静态激励保存在
`main_table_by_uid[uid]`，运行时状态保存在 `status_by_uid[uid]`。标量状态对象统一记录：

```text
宏指令生命周期：active、enq、rob_commit、lsq_deq、success、terminal_done
三条标量发射目标：load / sta / std 的 queued、dispatched、writeback、pass、fault
恢复控制：replay_pending、replay_seq、redirect_pending、flushed、issue_killed
资源快照：robIdx、lqIdx、sqIdx、各 target 的 issue_epoch
```

标量 monitor 事件通过以下 active map 反查 UID：

```text
uid_by_active_rob[rob_order_util::rob_to_map_key(rob_key)] -> UID
uid_by_lq[lqIdx]          -> UID
uid_by_sq[sqIdx]          -> UID
```

其中 `uid_by_active_rob` 是一对一映射。标量 writeback handler 按上述索引找到 UID 后，直接更新该 UID 的
`status_transaction`。该模型假设一个 UID 只需维护单一标量 load/sta/std 生命周期；不得把一个向量宏指令的
多个 data-uop 写入标量 `load_issue_q/sta_issue_q/std_issue_q`，也不得让向量 writeback 进入标量
`writeback_status_handler`。

#### 5.5.2 向量独立运行状态表

向量主表项仍只拥有一个 UID 和一个 ROB 项，但该宏指令包含 `D` 个 data-uop。向量使用自己的
`vec_runtime_table` 保存 uop 级运行状态；ROB 所有权则和标量共用同一张公共 active map：

```text
uid_by_active_rob[rob_order_util::rob_to_map_key(rob_key)] -> UID     // 标量、向量唯一真源
vec_runtime_table[uid]    -> 该 UID 的 vector macro runtime
vec_runtime_table[uid].uop[vuopIdx]
                              -> 当前 data-uop 的 runtime
```

不再建立 `vec_uid_by_active_rob`。激活时统一检查并写入
`uid_by_active_rob`，再由 `main_table_by_uid[uid].op_class` 决定进入标量还是向量运行路径。这样同一个
ROB 编码空间只有一个 owner，能避免标量/向量双 map 不一致；向量仍然不会进入标量三条 issue queue。

向量 writeback/feedback 到来时，必须按下列固定路径定位状态：

```text
事件携带 robIdx、vuopIdx
  -> uid_by_active_rob[rob_order_util::rob_to_map_key(rob_key)] 得到 UID
  -> 检查 main_table_by_uid[UID].op_class 为 V_LOAD/V_STORE
  -> main_table_by_uid[UID].vec_table 取得静态 uop payload
  -> vec_runtime_table[UID].uop[vuopIdx] 取得并更新动态状态
```

不需要额外建立 `{rob_key, vuopIdx} -> uop` 的关联数组。完整 `rob_key` 已唯一定位 UID，而 `uop[]` 的数组下标
与 `vuopIdx` 一一对应；一次公共 map 查询加一次有界数组索引即可完成反查。向量只使用
`status_by_uid` 中的公共生命周期字段（例如 `active/enq/rob_commit/lsq_deq/terminal_done` 和 ROB 快照），
不得读写其中 scalar-specific 的 LOAD/STA/STD target、标量 issue 或标量 writeback 字段。

**ROB key 与动态实例真源约束：** 文中为简洁写成 `robIdx` 的 map 下标，统一指完整
`rob_key={flag,value}`，不能只使用裸 `value`。实现访问 `uid_by_active_rob`、ROB tombstone 或 commit owner
前，必须先通过 `rob_order_util::rob_to_map_key(rob_key)` 生成 map key；否则 ROB wrap 后可能把旧实例事件匹配到
新实例。`status_by_uid[uid].dynamic_epoch` 是同一 UID 动态实例的唯一可变真源，因为公共 commit/recovery 逻辑
已经读取该字段。向量 runtime 中若保留 `dynamic_epoch`，它只能是同步镜像，不能独立递增或回退；实现也可以省略
该镜像并统一调用 `current_dynamic_epoch(uid)`。queue item、launch token、cancel record、tombstone 中的 epoch
是创建时复制的不可变快照，镜像与公共字段不一致时必须报告模型错误。

#### 5.5.3 宏指令与 data-uop 的最小状态

向量运行表只追踪测试框架可观测的 data-uop 生命周期，不追踪每个 flow 是否命中 TLB、是否进入 DCache、
是否完成单个元素，或是否发生某次内部 cache retry。这些属于 DUT 内部微观行为；测试框架只以 uop 的接收、
反馈、写回和终态作为边界。

```text
vec_macro_runtime_t {
  uid;
  rob_key;

  active;
  flushed;
  redirect_pending;
  dynamic_epoch;               // 只读镜像；唯一可变真源是 status_by_uid[uid].dynamic_epoch
  redirect_old_epoch_valid;    // redirect 后 re-admission 的旧 owner 检查门控
  redirect_old_dynamic_epoch;  // 上一次被取消实例的 epoch 快照
  redirect_cancel_record_ref;  // 无正式未释放 range 时为 invalid；否则必须等 record.software_applied
  success;
  rob_committed;
  lsq_dequeued;
  terminal_done;

  data_uop_num;       // 固定等于 vec_table.layout.data_uop_num
  enq_done;           // 所有 data-uop 的普通 LSQ 预留均已完成 sample/promotion
  initial_issue_route_pending; // enq_done 后等待一次性建立 D 个初始 issue item
  initial_issue_routed;        // 防止 service loop 重复插入同一批 D 个 item
  next_enq_vuopIdx;   // admission 唯一游标，范围 0..data_uop_num；不跳过未完成 uop
  fof_next_vuopIdx;   // FOF issue 唯一游标，范围 0..data_uop_num；tail 仅在等于 D 时可选

  fault_pending;      // 顶层 exceptionVec 的异常提交状态，不等于 redirect
  fault_vuopIdx;      // 初版 direct-fault profile 中唯一的 D=1 uop

  fof_tail_pending;           // activation 时按 v_form==fof 重新 arm
  fof_tail_issued;
  fof_tail_written_back;
  fof_tail_canceled;
  issue_killed;              // runtime 镜像；公共 status.issue_killed 是唯一可变真源

  uop[0 .. data_uop_num-1];
}

`redirect_cancel_record_ref` 保存当前 redirect 的**公共 aggregate** cancel record 引用；它不是“向量专属 record”，
同一 redirect 的多个 vector UID 可以合法指向同一个 record。没有该 UID 的正式 range 尚未释放时为 `invalid`。record
至少包含 `{redirect_epoch, cancel_record_id, lq_count, sq_count, software_count_finalized, software_applied}`；其中 count
可同时包含 scalar 和 vector 贡献。向量 activation 只有在引用为 `invalid` 或该 aggregate record
`software_applied=1` 时，才允许重新分配共享 LQ/SQ pointer/free count；不能只因为 tombstone 到期就跳过软件回退。

`redirect_old_epoch_valid=1` 时，re-admission gate 还必须按
`{uid,redirect_old_dynamic_epoch}` 检查旧实例的 `fof_send_reservation`、`active_fof_owner` 和
`fault_head_kind=VECTOR` 的 shared fault-head token 均已清除；不能要求全局没有 FOF owner 或 scalar fault-head，
因为其它宏可以合法占用这些资源。gate 通过后，在同一原子 reset 中清除
`redirect_old_epoch_valid`、旧 epoch 快照和 `redirect_cancel_record_ref`（设为 `invalid`）；历史信息如需保留只能
写 debug-only history，不能继续作为下一实例的运行门控。

vec_uop_runtime_t {
  enq_pending;
  enq_accepted;

  // admission launch 与下一次 sample 之间的暂存 reservation。
  launch_token {
    valid;
    visible;                 // 0=provisional，1=已 promotion
    dynamic_epoch;
    predicted_lqStart/sqStart;
    predicted_lq_keys[]/sq_keys[];
    enq_pointer_before/after;
    reserved_entries;        // 固定等于 F；token 唯一拥有的 provisional free-count delta
  }

  // admission launch 对应 sample/promotion 后得到的当前动态实例资源快照。
  // replay 复用；redirect/cancel 后清空，重新 admission 时可重新分配。
  lqStart/sqStart;          // 有效侧保留 flag + value，另一侧为 canonical 0
  range_remaining_entries; // 初值为 F，按真实 deq/cancel 递减
  range_dequeued;

  issue_pending;
  issue_accepted;       // 当前已 fire 但尚未被 WB/replay 收尾；即 outstanding

  writeback_seen;
  terminal;             // 正常 writeback 的 data-uop 终态；fault 不伪造为正常 terminal
  replay_pending;
  replay_count;

  suppressed;         // 预留给未来可唯一观察到的 FOF 抑制事件；当前初版恒为 0
  canceled;           // redirect/flush 取消

  stable_pdest;       // 从静态 vec_uop 复制，仅用于回写匹配
}
```

`launch_token` 是 admission 的短暂运行时字段，不属于静态 `vec_uop_t`。它可以和同一 macro 先前已经
promotion 的正式 range 同时存在：redirect 时必须由持有 redirect writer gate 的 coordinator 先取消所有
`visible=0` token，再扫描正式 owner 并按实际剩余 entry 记 cancel。token 只保存自己的 enqueue pointer 前/后边界和 `reserved_entries=F`，不保存可被并发 deq/cancel
改变的 `free_count` 历史快照。取消 token 时，必须先确认当前对应 enqueue pointer 仍等于 token 的 `after`。pointer 不匹配
时必须报告 fatal/返回失败，token、pointer 和当前 free count 均保持不变，并停止该 UID 的后续 redirect/re-admission
状态转换；校验成功后才把 pointer 回退到 `before`，同时对**当前** free count 增加 `reserved_entries`，不改 dequeue pointer。
pointer 不匹配说明出现了未建模的后续 allocation，不能覆盖当前 pointer/free count。`visible=0` token 永远不写正式 owner map、
tombstone 或 cancel record；promotion 成功后才写入 `lqStart/sqStart` 和 per-entry owner。
初版不仅要求“同一 macro 一次只 launch 一个 data-uop”，还必须复用既有 LSQ dispatcher 的**全局**单深度
`pending_sample_valid` 边界：任何 vector `visible=0` token 在完成 sample/promotion 或 redirect cancel 前，整个
LSQ admission 不再 launch 任意 scalar/vector allocation。这样该 token 必定是对应 LQ/SQ enqueue pointer 的尾部，
不会被后续 scalar allocation 覆盖；初版正常情况下全系统至多存在一个未 promotion 的 vector token。

redirect service 先只读计算：

```text
vector_involved =
  存在被当前 redirect 覆盖的 active V_LOAD/V_STORE macro
  || 存在属于被覆盖旧实例的 valid visible=0 vector launch token
```

`vector_involved=0` 时必须走现有 **scalar-only fast path**：保留
`apply_redirect_flush_range()`、scalar `prepare_uid_for_redirect_reissue()`、现有 cancel-record 和
`apply_pending_lsq_cancels()` 的全部调用顺序及行为；不创建 vector transition plan、不取得 writer gate、不执行 vector
预检或 vector aggregate apply。

仅 `vector_involved=1` 时，资源回退才由每个 redirect 一次的
`run_redirect_lsq_transition(redirect_epoch)` 统一拥有，而不是由某个 vector UID 单独拥有。它先收集本 redirect 覆盖的
token，以及所有会由 scalar/vector 正式 owner 计入 aggregate record 的 domain；domain_mask 不能只由 token 推导。

开始资源事务前必须先满足 **资源排空栅栏**：以当前 cancel record 的
`redirect_lsq_sample_seq` 为 cut line，所有 `sample_seq <= cut line` 的 raw LQ/SQ dequeue batch 都必须先经既有的
联合预检/提交路径结算，且不存在未消费的更早 batch。若尚未排空，coordinator 不取得 writer gate、不取消 token、也不清
vector lifecycle；它只保持 redirect freeze 与原始 redirect plan，先让最早的完整 deq batch 以 resource-drain-only 方式
完成，再重新收集 owner/domain 并重试。`redirect_transition_plan.covered_uid_set` 必须在 drain 前由当前 redirect 的
ROB 覆盖范围建立，并随 batch 传入；此时 `status.flushed/redirect_pending` 还没有写入，不能用这些后续状态位判断是否
抑制 terminal。该方式不违反 redirect-first：deq 是已经被 DUT 采样的资源事实，必须先反映到
`range_remaining_entries`，但被 redirect 覆盖的 scalar/vector UID 不得由这次 drain 调用 normal/fault terminal、
`try_retire_committed_uid()`、terminal prefix 或 recycle；全局 fault-head sync 也延后到 coordinator 完成 redirect 状态提交后再重检。

这里的 raw deq batch 必须保存 monitor capture 时的不可变 `sample_seq`，并随 `deferred_raw_ctrl_q` 的重试保持不变。
当前 `dispatch_raw_ctrl_t` 的 `cycle=$time` 只能用于日志，不能与 `redirect_lsq_sample_seq` 比较；后续实现必须在
`dispatch_raw_ctrl_t` 中新增 `sample_seq`，或由不丢失 raw 身份的外层 envelope 保存该值。禁止在消费 deferred batch 时用
当前 sample 重新推导，因为那会把一个早到 deq 错误地分类为 gate 之后的 deq。

除了 sample 序号，deferred raw deq 还必须在**第一次**进入持久 FIFO 时冻结物理 key，形成：

```text
deferred_deq_envelope_t {
  capture_order;             // FIFO 原始顺序，重放不得重排
  sample_seq;                // monitor capture 时固定，非零
  lq_keys[];                 // 按 lq_deq_start_key(raw_lq_ptr,count,ptr_is_next=1) 还原起点后一次展开
  sq_keys[];                 // V2 count-only SQ 由 capture 时 shadow head 一次展开
  sq_deq_ptr_at_capture;     // 仅 V2 SQ key provenance；不等于重放时当前 head
}

redirect_deq_tombstone_t {
  redirect_epoch;
  redirect_lsq_sample_seq;   // 本 tombstone 的 cut line
  domain;                    // LQ / SQ
  physical_key;
  uid;
  old_dynamic_epoch;
  expire_sample_seq;
}
```

V2 的 `sqDeq` 只有 count：`sq_keys[]` 必须从 deferred FIFO 的 shadow SQ cursor 依 FIFO 顺序展开；shadow cursor 仅用于
冻结后续 envelope 的 key，绝不推进真实 `lsq_ctrl.sq_deq_ptr/free_count`。某 SQ envelope 被 `LIVE_COMMIT` 时，其第一
个冻结 key 必须仍等于真实 `sq_deq_ptr`，随后才可推进真实 pointer；`STALE_DROP` 不推进真实 pointer，因此 FIFO 排空后
shadow cursor 必须丢弃并从真实 pointer rebase，而不是假设两者天然相等。若 stale 之后仍有一个后续 SQ envelope 需要
live commit、但其冻结起点已不等于真实 pointer，初版没有可靠 resync 信息，必须 fatal，不能用 shadow 覆盖真实状态。
redirect coordinator 在删除任一未释放 scalar/vector owner 前都要写 `redirect_deq_tombstone_t`；它用于
gate 后缓存 deq 的分类，不能只给 vector owner 写 tombstone。

`redirect_deq_tombstone_t` 同时是**共享 allocation quarantine**：公共 scalar admission 和 vector admission 在
`preview_allocate/commit_allocate` 或等价 key 预检前，都必须查询对应 LQ/SQ physical key。命中未过期 redirect-deq
tombstone 时返回“暂不可分配”，保持 admission cursor、真实 pointer 与 free count 不变，等待该 redirect 的
gate-owned deferred envelope 已分类/消费且达到 output-drain 过期条件；不得覆盖 tombstone 建立新 owner。该状态只由
`vector_involved=1` 的 mixed/vector redirect 创建，因此 `vector_involved=0` 的 scalar-only fast path 保持现有 allocation
和 cancel 行为。

资源排空后才在相应 LQ/SQ writer gate 内执行 `precheck_vector_launch_token_batch()`；预检通过后才取消 provisional token、
扫描 scalar/vector 正式 owner、完成当前 redirect 的 aggregate cancel record 并回退 pointer/free count。gate 覆盖期间，
admission/reservation、DUT dequeue commit 和 foreign cancel-record apply 只能保留完整 `deferred_deq_envelope_t`、延期到
下一 service sample；同时触及 LQ/SQ 的联合 batch 必须整体延期，不能只提交其中一侧。

gate 释放后，缓存 envelope 必须按 `capture_order` 先做 provenance 分类，不能直接重新执行普通 owner 预检：

```text
要求：envelope.sample_seq > redirect_lsq_sample_seq。
      否则资源排空栅栏漏掉了该 batch，fatal。

对每个非空 domain：
  所有冻结 key 都命中唯一 live scalar/vector owner
    -> LIVE_COMMIT。
  所有冻结 key 都无 live owner，且逐 key 都命中当前
     {redirect_epoch, cut_line, domain} tombstone；每项 tombstone 的 uid 属于 covered_uid_set，
     old_dynamic_epoch 与该 key 的旧 owner 快照一致
    -> STALE_DROP（同一 domain 可以跨多个被覆盖 UID，不要求 uid/epoch 相同）。
  同一 domain 混合 live/tombstone，或出现空 owner、success tombstone、其它 epoch/cut line、owner 不匹配
    -> fatal。

STALE_DROP：
  只消费这一侧 raw sideband；不推进该侧 dequeue pointer/free count，不删 owner，不递减 range，
  不触发 terminal、fault-head、terminal prefix 或 recycle。
  同一 raw 的 MMIO tag、sbIsEmpty 等非-deq sideband 仍按既有顺序精确处理一次，不能因两侧 stale 而丢弃完整 raw。

effective batch：
  从原 raw 中去掉完整 STALE_DROP domain。
  两侧都 live -> 继续既有联合预检/提交；
  一侧 stale、一侧 live -> 仅提交 live 侧；
  两侧 stale -> 仅 pop envelope。
```

因此“联合 LQ/SQ raw 不得拆开”仍适用于 gate 前延期和所有 live domain 的普通资源提交；上面的一侧 stale/一侧 live
是取消已完成后基于已冻结 provenance 的专门分类结果，不会二次释放 stale domain。matching redirect deq tombstone 必须
保留到 gate-owned deferred FIFO 段已经全部分类/消费，并达到既有 output-drain 过期边界；在此前不能复用对应物理 key。
effective batch 必须使用冻结 key/token 的专用提交 helper，不能把 stale 侧的 raw count 简单清零后调用旧的 count-only SQ
helper，否则它会从重放时的当前 head 重新推导错误 key。

资源排空未完成、gate 暂时不可取得，或存在更早且未 `software_applied` 的同 domain cancel record 时，coordinator 返回
DEFER：保持 active redirect/freeze 和全部 vector redirect 状态原样；资源排空分支仅让已有 deq 流程结算最早 raw batch，
其余分支先让既有 FIFO cancel 服务完成更早 record 后再重试。只有 token 的 after/before 链、当前 pointer
或 allocation owner 预检不一致才是模型错误，必须 fatal；此时 token、pointer、free count 均保持不变，不能先清 issue/
fault-head/range 再发现错误。当前 redirect 的 aggregate record 必须在所有被覆盖 UID 都完成计数并置
`software_count_finalized=1` 后，才由持 gate 的 `apply_guarded_lsq_cancel_record()` 一次应用并置 `software_applied=1`；
不得由单个 vector UID 提前调用通用 `apply_pending_lsq_cancels()`。

若 `vector_involved=1`，但**全部被覆盖的 scalar/vector UID** 都尚未形成 LQ/SQ provisional token 或正式 owner，
则 `domain_mask=0`。此时仍由 coordinator 清理 vector issue/fault/runtime，但不取得物理 writer gate、不暂停标量
dequeue/cancel，也不创建/应用 aggregate LQ/SQ count；这与 `vector_involved=0` 的 scalar-only fast path 不同，因为前者仍有
向量生命周期状态需要收尾。只要任一被覆盖 scalar 或 vector UID 仍有正式 owner，相关 domain 必须进入 nonzero mask，
不能走这个零资源分支。

未来若扩展 multi-slot，不得仅按“每个 macro 至多一个 token”分别反向取消。必须先建立覆盖 scalar/vector 的统一
allocation ledger，再按每个 domain 的全局逆 allocation 顺序预检和取消；在该 ledger 设计完成前，不允许同时存在多个
`visible=0` vector token。

`vec_uop_runtime_t` 不复制 `src1/src2/src3/src4`、`flowNum`、静态 range 长度、`vuopIdx`、`lastUop` 或
`uop_send_pri`。这些均以主表中的 `vec_table.uop[vuopIdx]` 与 `layout.F` 为唯一真源；运行表只保存会随
事件变化的状态，以及由本次 admission 产生的实际起始指针和剩余 entry 数。

为避免高频 service loop 重复扫描完整主表或重复向 `vector_issue_q` 插入 item，向量运行期额外维护一个轻量
`vector_route_ready_q`。它的元素只包含 `{uid,dynamic_epoch}`：`enq_done` 从 `0` 变为 `1` 时插入一次；
`route_all_vector_issue_queues()` 只消费此队列，成功后置 `initial_issue_routed=1`。redirect/cancel 删除旧 epoch
的 ready item；全局 redirect freeze 期间则保留未被覆盖 macro 的 ready item，解除 freeze 后再 route。store replay
不经过该队列，而是只为同一个 `{uid,dynamic_epoch,vuopIdx}` 直接重新插入一个 issue item。

FOF fix-VL tail 不属于普通 data-uop，不占用 `uop[]`。它仅使用 macro runtime 中的
`fof_tail_pending/issued/written_back/canceled` 四个状态；这与第 5.3 节的动态构造规则保持一致。

FOF 还使用一个 scheduler 瞬态 `fof_send_reservation={uid,dynamic_epoch,kind,lane,vuopIdx}`，它不保存到主表或长期 runtime：每个
调度拍先全局仲裁至多一个可发送 FOF data-uop/tail，再让绑定 lane 产生单拍 valid。这样在尚未建立
`active_fof_owner={uid,dynamic_epoch}` 的首拍也不会有两个 lane 同时发出 `isVleff=1`。reservation 只能在绑定
lane 已观察到 `ready=1` 时创建；ready=0 时 reservation 与 valid 均为 0，原 data-uop/tail 保持 pending。fire 后
reservation 转为 active FOF owner；只有已经创建 reservation 的拍出现 valid=1 && ready=0 才是协议错误，不能退化为
普通 valid-hold 或下一拍静默重试。

`fof_send_reservation` 的完整身份为 `{uid,dynamic_epoch,kind,lane,vuopIdx}`。`kind=DATA` 时 `vuopIdx` 必须是
`0..D-1` 的真实数组索引；`kind=TAIL` 时它固定为 canonical 占位值 `0`，只用于结构打包，**不参与** tail 身份
比较、owner 查找或 `uop[]` 索引。tail 的唯一身份仍是 `{uid,dynamic_epoch,kind=TAIL,lane}`，不能以这个占位值冒充
`uop[0]`。

Issue scheduler 的 lane pending 和 FOF 所有权属于独立运行时状态，不写入主表：

```text
vector_issue_driver_state {
  pending_payload[2] { valid, uid, dynamic_epoch, kind, payload }; // 仅普通 data-uop
  fof_send_reservation { valid, uid, dynamic_epoch, kind, lane, vuopIdx }; // TAIL 的 vuopIdx 固定 0 且不参与身份
  active_fof_owner { valid, uid, dynamic_epoch };
}
```

公共 commit handler 的 fault-head 也必须从现有无类别 token 扩展为：

```text
fault_head_waiting;
fault_head_kind = NONE / SCALAR / VECTOR; // waiting=0 时固定 NONE
fault_head_uid;
fault_head_dynamic_epoch;
latched_is_store_exception;
```

普通 scalar fault 只写 `kind=SCALAR`；D=1 vector direct-fault 只由 vector fault commit 写 `kind=VECTOR`。
后续 terminal sync 和 redirect cancel 必须同时检查 `{kind,uid,dynamic_epoch}`，不能用 `issue_killed` 或 UID 单独
清除 shared token。特别是 VECTOR token 的 `issue_killed=1` 只表示 issue 已停，直至真实 range deq 形成
`success=0、terminal_done=1` 前仍必须保留该 token；详细收敛规则见 commit/dequeue flow。

任何 fault/redirect 清理必须按 `{uid,dynamic_epoch}` 匹配这些字段，不能清除新 epoch 的 pending 或 FOF owner。
`kill_vector_driver_pending(uid,dynamic_epoch)` 是该清理的唯一入口：它清除匹配的两个 lane pending payload、
`fof_send_reservation`，并调用 `release_active_fof_owner(uid,dynamic_epoch)` 清理匹配的
`active_fof_owner`，置 `issue_killed=1`，但不回退 LSQ range；range 回退仍由
admission/redirect 专用 helper 负责。

`active_fof_owner` 的正常释放也必须使用 keyed helper：

```text
release_active_fof_owner(uid,dynamic_epoch)：
  仅当当前 owner 的 uid 和 dynamic_epoch 均匹配时清除 owner.valid；
  不匹配时报告 owner mismatch，不能清除其它宏的 FOF barrier。
```

tail writeback、FOF fault/redirect kill 和最终回收均通过该 helper 释放 owner，禁止直接写全局 owner bit。

向量 issue queue 的 item 也必须携带动态实例版本，避免同一 UID 在 redirect 后重新 admission 时误用旧 item：

```text
vec_issue_item_t {
  uid;
  dynamic_epoch;
  vuopIdx;
  queue_id;
  uop_send_pri;
  replay_seq;
  kind;                 // DATA；FOF tail 不进入该队列
}
```

初始 route、replay 入队、queue membership 去重、scheduler 选择和 redirect 清理均使用
`{uid,dynamic_epoch,vuopIdx,replay_seq}` 作为身份。item 的 epoch 与 runtime 不一致时只能丢弃并记录旧事件，不能按
当前 runtime 重新组装 payload；同 UID re-admission 产生新 epoch 和新 item。

FOF tail 没有 `vuopIdx` 数组身份。若 tail 已经 fire 但尚未 writeback，redirect 仍必须将其标记
`fof_tail_canceled=1`，并写入独立的 tail tombstone：

```text
vec_tombstone_by_fof_tail[rob_key] = {uid, dynamic_epoch, expected_pdest, expire_sample_seq}
```

键只使用完整 `rob_key`，因为迟到的 tail writeback 不携带可用于查询的 `dynamic_epoch` 或可靠的数组
`vuopIdx`；其 value 保存旧 epoch 用于诊断和一致性检查。重新 activation 在该 tombstone 过期前被禁止，
因此同一完整 ROB key 同时至多存在一条未过期 tail tombstone，不会与新实例混淆。tail tombstone 在 output
drain 前有效，不能用 `payloadVuopIdx=0` 代替，也不能让旧 tail writeback 解除新 epoch 的 FOF owner。

#### 5.5.4 抽象生命周期

向量运行状态按如下行为推进：

```text
创建向量主表项：
  创建 vec_table 的 D 个静态 data-uop；创建空 vec_runtime_table[uid]。

激活向量宏指令：
  在公共 uid_by_active_rob 建立完整 rob_key -> UID；
  若这是 redirect 后 re-admission，必须先确认旧 `{uid,redirect_old_dynamic_epoch}` 的 vector issue item、pending payload、
  `vector_route_ready_q` ready item、range owner 与 active ROB owner 均已删除；相关 tombstone 已到期；若旧实例产生
  非零 cancel record，则该 record 已 `software_applied=1`；同时按旧 UID+epoch 确认 `fof_send_reservation`、
  `active_fof_owner` 和 `fault_head_kind=VECTOR` 的 shared fault-head token 均不存在。不能用“全局没有 FOF owner 或
  scalar fault-head”替代该 keyed 检查。redirect transition 只把公共
  `status_by_uid[uid].dynamic_epoch` 增加一次，本次 activation 使用该新 epoch，不再次递增。
  在建立新 active ROB owner 时原子重置公共状态：`active=1`、`flushed=0`、`redirect_pending=0`、`enq=0`、
  `issue_ready=0`、`success=0`、`rob_commit=0`、`lsq_deq=0`、`terminal_done=0`、`fault=0`、
  `exception_pending=0`、公共 `issue_killed=0`；同时清 `fault_pending`、旧 replay/pending 和 route-once 状态，避免新 epoch 读取旧实例结果；
  初始化或重置 D 个 uop runtime 为 enq_pending=1、其余状态为 0；设置 next_enq_vuopIdx=0、
  fof_next_vuopIdx=0；同步 runtime epoch 镜像并清除 runtime `issue_killed`、replay/pending payload；清除
  `redirect_old_epoch_valid`、旧 epoch 快照和 `redirect_cancel_record_ref`（置为 `invalid`）。
  仅通过带 UID+epoch 的 release/kill helper 清理旧 FOF scheduler ownership；不得无条件清除其它宏的 owner。
  按当前 v_form 重新 arm FOF tail：`fof_tail_pending=(v_form==fof)`，`fof_tail_issued=0`、
  `fof_tail_written_back=0`、`fof_tail_canceled=0`。只有旧 redirect/cancel/tombstone 生命周期完成后，才能执行该重置。

普通 LSQ 入队：
  scheduler 从 enq_pending 的 data-uop 中选择入队候选；
  每个 data-uop 的 enqLsq launch 只建立 visible=0 的 provisional token，保留 enq_pending；
  下一 sample 边界确认 DUT 已采样后执行 promotion：把 token 提升为正式 range owner，写入运行期
  lqStart/sqStart 和完整 key，再置 enq_accepted；
  全部 data-uop 已入队并完成 sample 后置 macro.enq_done 和 initial_issue_route_pending，
  向 vector_route_ready_q 写入当前 UID/epoch；route helper 只消费这一次状态变化，
  再一次性为所有 data-uop 置 issue_pending 并创建 D 个初始 issue item。

issueVldu 发射：
  scheduler 从 issue_pending 的 data-uop 中选择候选；
  普通 uop 在 valid && ready 后置 issue_accepted，并清 issue_pending；此时该 uop 是唯一 outstanding 尝试。
  FOF data-uop 还必须满足 `vuopIdx==fof_next_vuopIdx`；正常 writeback 后才将该游标加一。

replay：
  顶层 feedback 不携带 issue/replay 序号；只有原 uop 满足 `issue_accepted=1 && !replay_pending && !terminal` 时，
    才将 hit=0 视为当前唯一 live attempt 的 replay 请求。无 live outstanding 的 hit=0 除 redirect tombstone 命中外
    都是协议错误，不能凭本地 `replay_seq` 猜测它属于旧尝试；
  若公共 `status_by_uid[uid].issue_killed=1` 或 macro.fault_pending=1，feedback 只允许在 redirect tombstone 命中时丢弃；
    否则报告协议错误，不进入 replay 或 success 状态更新。
  满足前置条件后，预检原 uop 的队列与 driver pending 不存在重复下一次尝试；
  成功向原 vector issue queue 写回一个同 UID/uop 的 item 后，再一次性置 replay_pending、清 issue_accepted、
  重新置 issue_pending，并增加 replay_count；
  重发同一份静态 vec_table.uop[vuopIdx]，不得重新随机 source、pdest、vuopIdx 或 LSQ range；
  新一轮 issue 成功接收后清 replay_pending，并再次置 issue_accepted。

写回：
  完整 rob_key -> UID，vuopIdx -> uop runtime；
  正常 data-uop 写回前必须确认 `fault_pending=0` 且公共 `status_by_uid[uid].issue_killed=0`（runtime 同名字段只作镜像）；
    若任一为 1，迟到正常 WB 只能在 redirect tombstone 命中时丢弃，否则报告协议错误，不置 terminal、不清 outstanding、
    不推进 FOF cursor；
  正常 data-uop 写回后置 writeback_seen、清 issue_accepted；该 uop 进入正常 terminal；FOF data-uop 同时要求
  `vuopIdx==fof_next_vuopIdx`，然后递增 `fof_next_vuopIdx`；
  FOF tail 的 shape 与 data-uop writeback 互斥：一旦呈现 `vlWen=1 && vecWen=0 && v0Wen=0` 的 tail shape，
  只能走 tail match/tombstone 分支，绝不能因占位 `payloadVuopIdx=0` 回落为 `uop[0]`。tail 写回前必须已满足
  fof_tail_issued=1、fof_tail_canceled=0 和 exceptionVec=0；先执行带 `{uid,dynamic_epoch}` 校验的 owner release，
  只有 release 成功后才置 fof_tail_written_back=1、fof_tail_pending=0 并调用 terminal helper。若 owner 不匹配、
  tail 已取消或 exceptionVec 非零，属于协议错误；owner release 返回失败时保持 tail 未完成，并将 testcase 标记为
  fatal/不可继续，不能让 service loop 无限重试；其中 tail exception 必须先 keyed kill、置 fof_tail_canceled=1
  后 fatal，不能将任意全局 FOF owner 直接置无效，也不进入普通 `vector_fault_handler()`。

fault：
  顶层 exceptionVec 非零时先按 v_form 分支；它不是自动 redirect。
  非 FOF 且 D=1 的专用模板置 macro.fault_pending、记录 fault_vuopIdx，并写公共 status.fault/exception_pending；
    该 UID 在 ROB head 走带 `fault_head_kind=VECTOR` 的 vector fault-head commit，等待实际 range deq 后以
    `exception_pending=0、success=0、terminal_done=1` 回收；`fault=1` 和异常信息保留作最终诊断。该 tagged fault
    head 阻塞公共 commit cursor，直到异常 UID 已回收。
    fault handler 可先调用 `kill_vector_driver_pending()`，因此公共 `issue_killed=1` 在这个 direct-fault 路径表示
    “停止旧 issue”，不是 redirect。vector fault-head selector 和 tagged fault-head sync 必须允许该位为 1；只有
    epoch 不匹配、flushed/redirect_pending、显式 keyed fault-head cancel，或真实 `success=0` fault terminal 才能
    解除 VECTOR token。标量 fault-head 的 `issue_killed` 规则保持原有语义，不由向量路径改写。
  非 FOF 且 D>1 的不支持组合先清理该旧 dynamic_epoch 的 issue pending，再报告不受支持并等待真实 redirect；
    不将未完成 uop 伪造为 terminal，也不自行回收 range。
  FOF 若观察到 exceptionVec，先调用 `kill_vector_driver_pending(uid,dynamic_epoch)`、置 `fof_tail_canceled=1`，
    再报告 fatal 并停止 testcase；不等待 tail/redirect，也不伪造 terminal。

FOF 抑制边界：
  当前顶层没有唯一的“后续 data-uop 已被 FOF 内部抑制”事件；
  因此初版不因普通 writeback 或 VL 变化自行把后续 uop 标为 suppressed。
  正常路径继续遵守 data-uop 0 -> ... -> data-uop D-1 -> tail 的可观测顺序；FOF exceptionVec 路径则先
  keyed kill、置 `fof_tail_canceled=1` 并 fatal，立即停止该 testcase，不等待 redirect。未来新增可唯一归属的
  抑制输出后，才允许使用 suppressed 状态。

提交、出队和回收：
  ROB commit 与 LSQ dequeue 只记录宏指令级状态，不拆成 flow 级状态；
  所有 data-uop 均正常终态，且必要的 ROB commit、LSQ dequeue、FOF tail 条件均满足后，
  由 vector 专用 terminal helper 显式置 status.success=1、status.terminal_done=1，
  再删除公共 uid_by_active_rob 项并回收 vec_runtime_table[uid]。

redirect/reissue：
  redirect 命中旧向量动态实例时，先保留旧 dynamic_epoch，按旧 epoch 取消 driver pending、FOF reservation 和
  active FOF owner；同时按 `{kind=VECTOR,uid,old_dynamic_epoch}` 清除匹配的 shared fault-head 等待 token/队列项，
  不能清除 scalar 或其它 epoch 的 fault-head；为每个可见 data-uop 写 ROB/range tombstone，已 fire 未写回的 tail 另写 tail tombstone。
  删除 vector queue/range owner 并回退未释放 range 后，通过公共 active-map API 删除完整 rob_key 对应的 uid_by_active_rob 项，
  再调用 clear_uid_dispatch_result(uid) 清除 active_instance_flush_epoch_valid 等旧 activation provenance；
  最后保留同一 UID 和静态 vec_table，置 flushed=1、redirect_pending=1、success=0、terminal_done=0、
  只递增公共 `status_by_uid[uid].dynamic_epoch` 一次，并同步 runtime epoch 镜像。tombstone drain 后才允许重新
  activate/admission，不能把旧实例标为 terminal 或生成新 UID。
```

向量 issue scheduler、vector writeback handler、vector commit/dequeue handler 必须只访问本节定义的
向量运行表。标量 scheduler、标量 writeback handler 和标量 `status_transaction` 不因向量支持而改变其
字段含义、状态推进规则或正常回归行为。

### 5.6 标量与向量统一 UID、Admission 和 LSQ 流程

标量和向量主表统一生成 UID。一个 UID 只能属于标量或向量中的一种，类别由主表的 `op_class` 唯一决定：

```text
op_class = SCALAR_*       -> 标量 UID
op_class = V_LOAD/V_STORE -> 向量 UID
```

因此不再为标量和向量维护两套 ROB owner 映射。统一的 active map 只保存一份：

```text
uid_by_active_rob[rob_order_util::rob_to_map_key(rob_key)] -> UID
```

处理事件时先由完整 `rob_key` 得到 UID，再查询主表 `op_class` 判断后续进入标量或向量专用逻辑。若保留
`owner_type` 仅用于 debug，它必须由 UID 的主表类别派生，不能作为第二份可独立修改的真源。激活时必须
检查完整 `rob_key` 尚未被任何 UID 占用，避免标量和向量同时使用同一个 active ROB 项。

#### 5.6.1 统一主流程与专用状态

公共流程统一为：

```text
主表建立 -> UID/ROB 分配 -> Admission/激活 -> 统一 LSQ 入队
  -> 按 op_class 分派 issue queue -> 标量或向量发射
  -> 标量或向量 monitor/writeback -> 正常完成或异常/replay/redirect
  -> 统一 ROB 提交 -> 统一 LSQ 出队 -> UID 回收
```

公共流程只负责 UID、ROB、LSQ 资源和全局 ROB 顺序；状态细节仍按类别隔离：

```text
标量：status_by_uid、load_issue_q/sta_issue_q/std_issue_q、标量 writeback/replay handler
向量：vec_runtime_table、vector_issue_q[0/1]、向量 writeback/replay handler
```

向量不得写入标量 `status_transaction` 的标量 target 字段，也不得进入标量三条 issue queue。标量逻辑
保持原有字段含义和状态推进规则。

#### 5.6.2 统一 Admission 与 LSQ 入队

统一 `activate_uid(uid)` 完成以下公共动作：

```text
1. 从 main_table_by_uid[uid] 读取完整 rob_key；
2. 通过 `rob_order_util::rob_to_map_key(rob_key)` 检查 UID 尚未 active，且完整 ROB map key 不存在；
3. 建立 `uid_by_active_rob[rob_order_util::rob_to_map_key(rob_key)] = uid`；
4. 置公共 active 状态；
5. 标量 UID 初始化 status_by_uid，向量 UID 初始化 vec_runtime_table。
```

统一 LSQ 入队控制器随后按 `op_class` 选择入队行为：

```text
标量 load/store：
  复用原有标量 LQ/SQ 入队逻辑，通常一次请求预留一个标量 entry。

普通向量 data-uop：
  按 vuopIdx=0..D-1 处理；每个 data-uop 预留 F=numLsElem 个 LQ 或 SQ entry；
  入队成功后更新 vec_runtime_table[uid].uop[vuopIdx]；全部 data-uop 成功后置 macro.enq_done。

segment（启用时）：
  由统一控制器识别后跳过普通向量 LQ/SQ 预留，交给专用 segment 路径；当前未支持时直接排除。
```

向量的 LQ/SQ 关联表按每个物理 entry 独立保存：

```text
vec_range_owner_by_lq[lqIdx] -> { UID, vuopIdx }
vec_range_owner_by_sq[sqIdx] -> { UID, vuopIdx }
```

一个 data-uop 预留 `F` 个 entry 时，必须建立 `F` 条 owner map；不能只映射起始 key。公共控制器只负责
entry 分配、范围连续性和 map 建立，不解析 flow 的实际地址、TLB 命中或 DCache 访问。

#### 5.6.3 向量双 issue queue

向量 data-uop 入队完成后，根据主表指令类型进入两个专用发射队列：

```text
vector_issue_q[0] -> issueVldu_0
vector_issue_q[1] -> issueVldu_1
```

segment（启用时）只能进入 `vector_issue_q[0]`。其它向量形式可以在主表建立时按权重或均匀随机选择
`queue_id`；建议同一宏指令的全部 data-uop 使用同一个 `queue_id`，避免同一条指令在两个队列之间
产生额外的顺序协调。queue item 只保存以下轻量索引，完整 payload 始终从主表
`vec_table.uop[vuopIdx]` 和当前 runtime 快照读取：

```text
vec_issue_item_t {
  uid;
  dynamic_epoch;
  vuopIdx;
  queue_id;
  uop_send_pri;
  replay_seq;
  kind;                  // DATA；FOF tail 不进入 issue queue
}
```

初始 route、replay 入队和去重均以 `{uid,dynamic_epoch,vuopIdx,replay_seq}` 为身份。

初始 item 的建立不是每拍扫描所有 `enq_done` macro：`complete_vector_admission_sample()` 在 `enq_done` 的唯一
上升沿把 `{uid,dynamic_epoch}` 写入 `vector_route_ready_q`，`route_all_vector_issue_queues()` 只消费该小队列并
为 D 个 data-uop 各建立一个 item。一个宏置 `initial_issue_routed=1` 后不得再次建立初始 item；replay 只由
feedback handler 为对应 uop 建立一个 replay item。

#### 5.6.4 统一事件入口与类别分派

monitor 事件统一先解析 UID，再按 `op_class` 分派：

```text
event.rob_key
  -> uid_by_active_rob[rob_order_util::rob_to_map_key(event.rob_key)] 得到 UID
  -> op_class=SCALAR_*：调用标量 writeback/replay handler
  -> op_class=V_LOAD/V_STORE：调用向量 handler，并用 event.vuopIdx 索引向量 uop runtime
```

向量事件不进入标量 `writeback_status_handler`。向量 writeback 只需更新 data-uop 的接收、写回、replay
和终态；不需要记录每个 flow 的 TLB、DCache 或内部 retry 状态。FOF tail 使用宏指令 runtime 的
`fof_tail_pending/issued/written_back/canceled` 状态，不占普通 `uop[]`。

#### 5.6.5 统一 ROB 提交、LSQ 出队与回收

ROB 提交使用一个公共 ROB cursor。公共提交器根据完整 `rob_key` 查询
`uid_by_active_rob[rob_order_util::rob_to_map_key(rob_head)]` 得到 UID，再按类别调用：

```text
标量 UID -> 原有标量 commit handler
向量 UID -> 向量 commit handler
```

正常向量只有在所有 data-uop 为 `terminal`、无 replay 在途，且 FOF tail（如有）完成后，才进入向量 ROB commit
candidate。ROB commit 与 LSQ 出队均完成后，向量专用 terminal helper 才置 `success=1` 和 `macro.terminal_done`；
LSQ 出队以每个物理 entry 的 vector owner map 为依据，不建立 flow 内部 TLB/DCache 状态。

fault 候选与正常候选分开：`fault_pending=1` 的 D=1 专用模板在 ROB head 只发送 fault-head commit，
`isStoreException` 由 `op_class==V_STORE` 派生；它等待真实 range deq 后由 vector fault terminal helper
置 `success=0、terminal_done=1`。该路径不调用标量 `required_targets_done()` 或标量 `try_retire_committed_uid()`。
redirect 则继续使用下一段的 cancel/re-admission 语义，不能与 fault 合并。若 redirect 覆盖了已经记录的
vector fault（无论尚未到 ROB head，还是已经登记 fault-head），必须在递增 epoch 前调用
`cancel_vector_fault_head(uid,old_dynamic_epoch)`：它总会删除同 UID/epoch 的 pending-fault record；只有 shared
fault-head 同时匹配 `{kind=VECTOR,uid,old_dynamic_epoch}` 才清 token。其它 UID/epoch 或 scalar fault-head
必须保留，避免误解除公共 ROB cursor。

当提交、出队和终态条件全部满足时，统一回收：

```text
删除 uid_by_active_rob[rob_order_util::rob_to_map_key(rob_key)]
删除向量 vec_range_owner_by_lq/vec_range_owner_by_sq 中属于该 UID 的映射
删除 vec_runtime_table[uid]（标量则回收 status_by_uid 的 active 生命周期）
```

redirect/flush 也遵循同一类别分派。若本 redirect 不覆盖 vector macro/token，则保持既有 scalar-only fast path，不进入
向量 coordinator。若覆盖 vector macro/token，先排空不晚于当前 `redirect_lsq_sample_seq` 的完整 raw LQ/SQ deq batch；
这一步只反映已观察到的 entry 释放，不允许覆盖 UID 因此进入 terminal/recycle。资源排空后才进入一次按 `redirect_epoch`
拥有的 `run_redirect_lsq_transition()`，再执行各 UID 的回调。coordinator 取得非空 LQ/SQ writer gate 后，先取消全局尾部的
`visible=0` provisional token；再按 ROB 年龄扫描被覆盖 UID，标量沿用原有 reissue 计数，向量写 tombstone、清理旧
`vector_issue_q` 和 range owner，并把实际未释放 entry 数累加到同一个 aggregate cancel record。每个向量 UID 只保存
该公共 record 的引用，不能提前把它标记 `software_applied`。所有计数 finalized 后，coordinator 在仍持 gate 时一次回退
该完整 record；回退成功后才通过统一 active-map API 删除旧完整 `rob_key` 对应的 `uid_by_active_rob` 项、调用
`clear_uid_dispatch_result(uid)` 清旧 activation epoch，并由 `mark_vector_redirect_reissue_pending()` 写
flushed/redirect_pending 状态。`apply_redirect_flush()` 只能在 gate 释放后清全局 redirect/freeze；失败路径保持现场，
不让其它 LSQ writer 越过不一致的 pointer/free count。

gate 后缓存的 raw deq 不得直接按当前 owner/pointer 重放。monitor capture 时已冻结的 `{sample_seq,lq_keys[],sq_keys[]}`
必须先按 LQ/SQ domain 与当前 redirect 的 deq tombstone 比较：整侧全部 live owner 才走普通提交；逐 key 全部匹配当前
redirect 且各自属于 covered UID 的 tombstone 才 `STALE_DROP`（可跨多个 UID，仅消费 raw，不改 pointer/free count）；
同侧混合或身份不符 fatal。该 tombstone 同时覆盖
被 redirect 的 scalar 和 vector 正式 owner，并保留到相关 deferred FIFO 段已分类/消费；否则 mixed redirect 的迟到 scalar
deq 会被错误地当作空 owner。

向量 per-UID 回调仍在旧（即 `status_by_uid[uid].dynamic_epoch` 当前值）下为每个已 promotion data-uop 写
`vec_tombstone_by_rob[{rob_key,vuopIdx}]`；若 FOF tail 已 fire 但尚未写回，再写入
`vec_tombstone_by_fof_tail[rob_key]`，并把旧 epoch 和期望 pdest 存在 value 中。

redirect handler 必须在删除 active ROB owner 前调用 `cancel_vector_fault_head(uid, old_dynamic_epoch)`，无论旧实例的
fault 还停留在 `vector_fault_pending_q`（或等价的 per-macro pending record），还是已经登记公共 vector fault-head token。
该 helper 先删除同一旧实例的 pending record；随后仅在 `fault_head_kind=VECTOR`、UID 和旧 epoch 同时匹配时清除
`fault_head_waiting/fault_head_uid/fault_head_dynamic_epoch`，并把 `fault_head_kind` 回填为 NONE；必要时让下一次
commit service 基于当前 commit cursor 重新建立 modeled head。若没有匹配的 shared token，或 token 属于其它 UID/epoch
或 scalar fault-head，则该 token 保持不变，不能清除全局 fault-head bit。取消 fault-head
只解除公共 cursor 的旧阻塞，不把旧实例标记为 terminal；随后仍按上述 tombstone、cancel 和同 UID re-admission
流程处理，`clear_uid_dispatch_result()` 负责清除旧公共 `exception_pending`。
monitor 在 active map 查不到 owner 时，必须先查询有效 ROB/tail tombstone 并丢弃旧 writeback；只有 tombstone
到期后才允许重新建立该 ROB owner。
只有正常 terminal 回收才删除统一 active ROB map 和 `vec_runtime_table`；迟到事件在 tombstone 有效期内丢弃。

#### 5.6.6 发射期派生字段与 replay 字段

主表只保存跨 Admission、LSQ、Issue、Monitor、Commit 多个阶段都必须保持稳定的信息，例如 `uid`、
`robIdx`、`op_class`、`v_mode`、`v_form`、向量静态配置、`vec_uop[]` 中的源数据和 uop 身份字段。
仅用于一次 `issueVldu` transaction，或可以由主表稳定字段直接派生的信息，不放入主表。以下字段采用
发射时赋值：

| 接口字段 | 主表是否保存 | 首次发射赋值 | replay 发射赋值 |
|---|---|---|---|
| `uop.ftqPtr_flag` | 否 | 固定为合法默认值 `0` | 仍为 `0` |
| `uop.ftqPtr_value` | 否 | `ftqPtr_flag=0` 时固定为 `0` | 仍为 `0` |
| `uop.ftqOffset` | 否 | 固定为合法默认值 `0` | 仍为 `0` |
| `uop.fuOpType` | 否（由静态配置派生） | 由主表 `v_mode + v_form + load/store` 查表生成 | 使用相同派生结果 |
| `isVecPartReplay` | 否 | 固定为 `0` | 仅 partial replay 置为 `1`；full replay 保持 `0` |
| `vecReplayMask` | 否 | 固定为 `0` | 仅 partial replay 使用 feedback 的待重放 flow mask；full replay 为 `0` |
| `vecReplayMbIdx` | 否 | 固定为 `0` | 仅 partial replay 使用 feedback 的 merge-buffer entry 编号；full replay 为 `0` |

`fuOpType` 虽然不单独存储，但不能随机生成；它必须与主表已经确定的 `op_class`、`v_mode` 和 `v_form`
一致。发射 helper 每次根据同一组静态字段查表，保证首次发射和 replay 发射的操作类型一致。若 DUT
接口对 FTQ 字段有更严格的实现要求，再在该 helper 中增加对应约束；在当前 MemBlock 只验证向量访存行为的
范围内，`ftqPtr_flag=0` 且其伴随字段为零是最小且确定的合法表示。

replay 字段属于单次发射状态，不应污染 `vec_table.uop[]` 的静态身份和源数据：

```text
首次 issue：
  isVecPartReplay = 0
  vecReplayMask   = 0
  vecReplayMbIdx  = 0

收到 DUT replay feedback：
  顶层 feedback 没有 replay 序号；仅当原 uop `issue_accepted=1 && !replay_pending && !terminal` 时接收 hit=0。
  若没有 live outstanding，只有 redirect tombstone 命中时允许作为旧事件丢弃；其余情况报告协议错误，不能用
  `replay_seq` 猜测或过滤迟到 feedback；
  在该前置条件下检查 queue/driver pending 不存在重复下一次尝试；
  成功把同一 uid/vuopIdx 的 replay item 追加回原 issue queue 后，再一次性更新
  runtime[uid].uop[vuopIdx].replay_pending = 1、issue_accepted = 0、issue_pending = 1；
  若 isVecPartReplay=1：同时保存 feedback 的 replay mask 和 merge-buffer index；
  若 isVecPartReplay=0 且 hit=0：记录 full replay，但不保存部分 replay 字段；
  若预检或入队失败，则保持原 live 状态并报告错误，不留下孤立 pending 标志。

重新入队并 issue：
  partial replay：isVecPartReplay = 1，使用 runtime 中保存的 feedback mask/index
  full replay：isVecPartReplay = 0，vecReplayMask = 0，vecReplayMbIdx = 0

issueVldu 握手成功后：
  清除该 uop 的 replay_pending；静态 source、vuopIdx、LSQ 起始位置和 flowNum 保持不变
  置 issue_accepted=1、清 issue_pending，直到下一次 writeback 或 replay feedback 收尾
```

因此 replay 不创建新的 UID、ROB 项或普通 LSQ entry，也不能重新随机 `src_0~src_4`、`pdest`、`vuopIdx`
等主表字段。若没有 replay feedback，所有 replay 字段必须保持默认零值。上述字段的赋值集中在
`issueVldu` transaction builder 中，主表和 `vec_runtime_table` 只保存生成这些字段所需的稳定信息及
replay feedback，不保存每次 transaction 的临时副本。

## 6. 初始化要求

向量表初始化按以下顺序执行：

```text
随机主表 op_class
若 op_class 为 V_LOAD 或 V_STORE：
  随机 v_mode、v_form
  回填 fuType、fuOpType
  建立合法 {vsew, veew, vlmul} 三元组并加权选择
  按本节的 MEMBLOCK_VEC_VTYPE_ILLEGAL_0_WT 随机 static_cfg.vtypeIllegal
  计算 EMUL、VLMAX，并按 2.1 节的指令形式生成 VL
  按第 3 节的 v_form 约束生成 nf
  按第 4 节的 v_form 约束生成 vm，并依赖 vm 生成 src_3
  按第 4.2 节固定生成 vstart=0
  按第 4.4 节的 base_align_mode 生成主表 src/baseAddr
  若 v_mode=strided：按第 4.5 节生成 static_cfg.stride
  随机初始化 static_cfg 的其余共享字段
  按第 5.1 节由 static_cfg 的 VL 生成 `static_cfg.src_vl_payload`（低 8 bit 为 VL，高位清零）；VTYPE 字段
  单独写入每个 issueVldu 的 `uop.vpu`，不从 src_4 高位派生

  由 5.2 节计算 layout.data_uop_num = D
  由 5.2 节计算 layout.data_uop_numLsElem = F
  若 D 不在 [1, 8] 或 F 不在 [1, 16]：丢弃候选并重新选择合法组合

  分配主表中的 uop[D]
  在 vec_runtime_table[uid] 中建立长度为 D 的运行状态数组
  对 i = 0 .. D-1：
    填写 uop[i].vuopIdx、lastUop、isVleff
    按 5.4 节填写 uop[i].uop_send_pri
    按共享 F 填写静态 LSQ range 容量，但不分配起始指针：
      load  -> hasLqRange=1，lqRange=F，hasSqRange=0，sqRange=0
      store -> hasSqRange=1，sqRange=F，hasLqRange=0，lqRange=0
    lqStart/sqStart 和完整连续 key 只能在 admission 的 enqLsq launch 对应 sample/promotion 后，
      从 provisional token 提升时的共享环形 pointer 写入 vec_runtime_table[uid].uop[i]；
      replay 复用该快照，redirect/cancel 后清空并等待重新 admission。
    填写 uop[i].src2；若为 indexed，按第 4.4 节填充 uop[i].indexedSrc1 的全部 index 字段
    填写 uop[i] 的 pdest 和写使能

  若 v_form=fof：
    只记录该 macro 需要动态 tail；静态建表阶段不 arm tail runtime
    不创建静态 tail payload，也不为 tail 分配 LQ/SQ range
  否则：
    不建立 FOF tail runtime 状态

  按第 7 节从统一地址参考队列尝试地址复用，并重新检查最终 baseAddr 合法性
```

FOF tail 的 `pending/issued/written_back/canceled` 是 activation/re-admission 所属的运行期状态：每次成功
activation 才按 `pending=(v_form==fof)`、其余三项为 `0` 初始化。静态建表不得依赖预先置位的 pending，避免
redirect 后的 runtime 重置被旧静态状态覆盖。

`vec_static` 中每个可随机共享字段都必须定义合法取值范围，并提供对应的 plus 权重控制随机分布。plus
权重只改变合法值的命中概率，不允许生成非法取值。`D`、`F`、`vuopIdx`、`lastUop`、`isVleff`、静态
range 容量与 `vec_runtime_table` 状态均为派生结果，不提供独立随机入口；实际 LSQ 起始指针是 admission
时的运行期 allocation fact，也绝不能独立随机。

## 7. 标量与向量统一地址复用

### 7.1 目标与队列语义

地址复用的目标是提高标量和向量访存之间的同址或相同基地址场景出现频率。复用对象可以是较早的
标量访存，也可以是较早的向量访存；当前项同样可以是标量或向量。

不新增向量专属的 reference queue。现有主表生成期的两条队列改为统一的地址参考队列：

```systemverilog
memblock_uid_t recent_load_uid_q[$];
memblock_uid_t recent_store_uid_q[$];
```

它们只保存已经完成地址生成的较早主表项 UID，主表仍是唯一的 transaction 真源。入队方向由访存
类型决定，不由标量或向量类别决定：

```text
scalar load  -> recent_load_uid_q
vector load  -> recent_load_uid_q
scalar store -> recent_store_uid_q
vector store -> recent_store_uid_q
```

为避免改变其它依赖标量 load/store 语义的路径，地址复用入队使用独立分类函数
`is_addr_reuse_load_ref()` 和 `is_addr_reuse_store_ref()`；不得直接扩大既有
`is_load_main_tr()` 或 `is_store_main_tr()` 的语义。

每次从队列选中 UID 后，测试框架回读参考主表项并按其类别取得最终地址锚点：

```text
参考项为 scalar：
  anchorAddr = ref_tr.vaddr

参考项为 vector：
  anchorAddr = ref_tr.src[63:0]
```

标量参考项必须使用最终 `vaddr`，不能只复制 `src_0`，因为 `vaddr = src_0 + sign_extend(imm)`。
向量参考项使用同一宏指令共享的 `src_rs1/baseAddr`。FOF 的 fix-VL tail 不是独立主表项，不入队；
segment 当前不支持，也不参与本节逻辑。

### 7.2 可覆盖的地址关系

统一队列支持以下方向关系；每一行的参考项都可以是标量或向量：

| 当前项 | 参考队列 | 地址关系 |
| --- | --- | --- |
| scalar/vector load | `recent_load_uid_q` | load-after-load |
| scalar/vector load | `recent_store_uid_q` | load-after-store |
| scalar/vector store | `recent_load_uid_q` | store-after-load |
| scalar/vector store | `recent_store_uid_q` | store-after-store |

因此可产生如下跨类型组合：

```text
scalar load  <- vector store
scalar store <- vector load
vector load  <- scalar store
vector store <- scalar load
vector load  <- vector load
vector store <- vector store
```

现有的地址复用 plus 参数统一作用于这四类关系：

```text
MEMBLOCK_ADDR_REUSE_EN_1_WT
MEMBLOCK_ADDR_REUSE_EN_0_WT
MEMBLOCK_ADDR_REUSE_LOAD_AFTER_STORE_WT
MEMBLOCK_ADDR_REUSE_LOAD_AFTER_LOAD_WT
MEMBLOCK_ADDR_REUSE_STORE_AFTER_LOAD_WT
MEMBLOCK_ADDR_REUSE_STORE_AFTER_STORE_WT
MEMBLOCK_ADDR_REF_WINDOW_*
```

若需要四类关系都具备命中机会，四个 `MEMBLOCK_ADDR_REUSE_*_WT` 关系权重均须大于 `0`。提高
`MEMBLOCK_ADDR_REUSE_EN_1_WT` 相对 `MEMBLOCK_ADDR_REUSE_EN_0_WT` 的比例即可提高全局标量、
向量和跨类型复用频率，不新增 vector 专属地址复用权重。

### 7.3 生成和地址回填规则

主表按 UID/ROB 顺序生成。当前项只允许引用已完成生成并已加入统一队列的较早项；当前项完成最终地址
处理后，才按自身 load/store 方向加入队列，不能引用自身或较晚项。

```text
生成当前主表项
  若当前项是向量：先完成 static_cfg 和 vec_uop[] 初始化
  从与选中关系对应的 recent load/store 队列中选择较早 UID
  回读参考项并取得 anchorAddr
  若当前项是 vector：检查 anchorAddr 与当前 base_align_mode 兼容，且当前整条向量访问范围合法
  合法：按当前项类别回填地址
  不合法或无参考项：执行当前项类别定义的 fallback
  将当前项的最终地址作为新的参考项加入对应队列
```

地址回填按“当前项类别”和“参考项类别”组合处理：

| 当前项 | 参考项 | 回填方式 |
| --- | --- | --- |
| scalar | scalar | 保持既有逻辑，复制 `ref.src_0/ref.imm`。 |
| scalar | vector | `src_0 = anchorAddr`，`imm = 0`，再计算 `vaddr`。 |
| vector | scalar | `main_tr.src = ref.vaddr`。 |
| vector | vector | `main_tr.src = ref.src[63:0]`。 |

主表 `src` 是向量 `src_0/baseAddr` 的唯一真源，地址复用后只更新主表 `src`；`vec_static` 不保存第二个
可独立修改的 `baseAddr`。

`[SAFE_LO, SAFE_HI]` 只限制第 4.4 节中新随机生成的向量 base，不是 load/store reference 的
硬过滤条件。复用时必须原样采用 `anchorAddr`，不得为了落入安全区间而对参考地址向上/向下对齐、裁剪
或改写。例如标量 reference 的 `vaddr` 位于安全区间外、但当前向量从该地址出发的完整访问范围仍落在
`[MAIN_LO, MAIN_HI]` 内，且满足当前 `base_align_mode` 时，该复用仍然合法。

### 7.4 标量和向量的关系选择与 fallback

标量当前项保持既有地址复用语义：先按四个关系权重选择关系，再决定当前 scalar load/store 类型；若
对应参考队列为空或所选参考地址无法满足当前标量访问范围，则继续执行既有的 scalar fallback，即按
选中关系的目标 scalar load/store 生成新的合法标量地址。

向量当前项不能直接调用标量专属的 `apply_addr_reuse_window()`，也不能把已初始化的 `V_LOAD` 或
`V_STORE` 改成标量 load/store。向量的关系选择必须保持已随机完成的宏指令方向：

```text
当前为 V_LOAD：
  仅在 load-after-load 与 load-after-store 中选择。

当前为 V_STORE：
  仅在 store-after-load 与 store-after-store 中选择。
```

向量 fallback 为：参考队列为空、参考候选非法或没有满足条件的候选时，保持当前 `V_LOAD/V_STORE`、
`v_mode`、`v_form`、`fuType`、`fuOpType`、`vec_static` 和 `vec_uop[]` 不变，继续使用向量基础
初始化阶段已经随机出的合法 `baseAddr`。不得为了 fallback 改变向量方向；例如 `fof` 和
`mask_load` 只对 load 合法，强行把其改为 store 会破坏向量表约束和权重分布。

### 7.5 合法性检查与初版边界

地址锚点相同不自动表示当前项整个访问范围合法。每个候选 `anchorAddr` 都必须按当前项自身的访问
规则重新检查：

```text
scalar：使用当前 scalar fuOpType 的访问字节数检查 [vaddr, vaddr + size - 1]。
unit-stride：检查当前向量从 baseAddr 开始的有效访问范围。
strided：检查 baseAddr 与 baseAddr + (VL - 1) * stride 所确定的两端范围。
whole-register：检查完整寄存器传输范围；它忽略输入 VL。
mask-load：检查与 VL 对应的 mask 字节传输范围。
```

对于当前项为 vector 的复用，除完整访问范围外还必须保持当前主表项已选的
`base_align_mode`：

```text
BASE_ALIGNED:   anchorAddr[3:0] == 0
BASE_UNALIGNED: anchorAddr[3:0] != 0
```

当前向量在某个候选锚点下超出 `[MAIN_LO, MAIN_HI]`，或不满足已选对齐模式时，丢弃该候选，不得修改
当前向量配置来迁就参考地址；向量 fallback 继续使用其新随机路径产生的安全 base。indexed 的随机
index 均受第 4.4 节的 `indexOffsetMax` 约束；复用候选仍需使用本次已生成 index 的最大实际 offset
检查：

```text
anchorAddr + max(indexOffset) + SEW_B - 1 <= MAIN_HI
```

初版 indexed 形式只保证 `src_rs1/baseAddr` 相同，不保证实际元素地址必然重叠；要稳定制造真实 indexed
元素同址场景，后续需额外约束至少一个 active 元素的 index 为 `0`。

本节的统一地址复用不复用标量 boundary-profile 的未对齐语义。标量当前项仍按其既有 boundary
profile 规则检查，向量当前项仍按第 4.4、4.5 节的向量专有基地址、VL、stride/index 和传输长度规则
检查。
