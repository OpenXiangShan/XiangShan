# 向量测试框架入队并行决策反馈

## 1. 背景与结论

原始生命周期决策中的 D3 采用“每拍至多一个 vector data-uop，且不与标量交错”的保守
admission 方案。该方案适合第一阶段快速打通向量路径，但未覆盖 V2 DUT 已有的多 slot
`enqLsq` 行为，也无法覆盖标量和 unit-stride 向量同拍混合入队。

本反馈决定以 V2 DUT 的真实 dispatch/LSQ 边界替代该限制：测试框架使用一套统一的
mixed LSQ admission batch，同时容纳标量和受支持的向量 data-uop。标量原有入队行为、
参数和状态语义保持不变；向量仅作为新的 candidate 类型接入同一批量分配与回退机制。

本文件的 D45 取代
[向量测试框架生命周期决策记录](向量测试框架生命周期决策记录_20260826.md)中的 D3。
后续实现与 flow 文档应以本文件为准；旧 D3 的“单 data-uop enqueue”不再作为约束。

本文后续的 D46 同时修订生命周期决策记录中的 D4。D4 原先要求整条 vector macro 的所有
data-uop 都完成 `enqLsq` 后才开放 issue；本反馈改为按 data-uop 的 LSQ range 独立开放。

## 2. 问题澄清

`enqLsq` 的一个 slot 表示一条 dispatch request：它可以是一个标量访存，也可以是一个
vector data-uop。它不是一条完整向量 macro，也不是一个 vector flow。

一个 vector data-uop 的 `numLsElem=F`，表示它在对应 LQ 或 SQ 中预留 `F` 个连续 entry；
标量请求固定为 `numLsElem=1`。同拍 batch 内的 LQ/SQ 起始指针按 slot 顺序分别做前缀和：

```text
lqStart(slot j) = lqBase + sum(i < j 且 slot i 为 load 的 numLsElem[i])
sqStart(slot j) = sqBase + sum(i < j 且 slot i 为 store 的 numLsElem[i])
```

因此，标量与向量可以混合进入同一个 batch。例如：

```text
slot 0: scalar load          numLsElem = 1
slot 1: unit-stride vload uop0  numLsElem = 2
slot 2: scalar store         numLsElem = 1
slot 3: unit-stride vload uop1  numLsElem = 2

该 batch 消耗：LQ = 1 + 2 + 2 = 5，SQ = 1
```

公共 slot 上限为 6；实际 batch 长度还受现有 `MEMBLOCK_ENQ_PER_CYCLE` 的运行期预算限制。
LQ 和 SQ 容量分别计算，且 DUT 只有一个共同 `canAccept`，所以一个 batch 必须整体发送或整体不发送，
不能只发送其中部分 slot。

## 3. D45：统一 mixed LSQ admission batch

**决策：** 泛化现有标量 `collect_lsq_candidates()` 与 pending-sample reservation 模型。每拍先按
主表 admission 顺序构造一个连续 candidate 前缀，再一次性驱动一个多 slot `enqLsq` batch。
候选可包含 scalar 或 vector data-uop；每一个 candidate 均以独立 slot 进入 DUT。

统一 candidate 至少携带：

```text
kind          = SCALAR / VECTOR_DATA
uid           = 主表全局唯一 UID
dynamic_epoch = 当前动态实例
vuopIdx       = 仅 VECTOR_DATA 有效
direction     = LOAD / STORE
numLsElem     = scalar 为 1；vector 为该 data-uop 的 F
lqStart/sqStart = batch 预检得到的实际连续 range 起点
```

构造 batch 时按 slot 0 到 slot N-1 顺序执行下列动作：

1. 受 `MEMBLOCK_ENQ_PER_CYCLE`、硬件 6-slot 上限和向量类型 profile 限制，选择下一个连续 candidate。
2. 累加该 candidate 对 LQ 或 SQ 的 `numLsElem` 消耗，并根据同方向前缀和计算 `lqStart/sqStart`。
3. 检查统一 active owner、vector range owner、tombstone、pending token 和 LQ/SQ 前瞻容量。
4. 任一 candidate 预检失败时停止扩展 batch；已经选中的连续前缀仍可整体发送。若第一个 candidate
   无法预检，当前拍不发送。
5. 整批预检成功后，将所有 slot 一次性写入 `enqLsq` transaction；剩余 slot 的 valid 置零。
6. 将 scalar/vector token 一起加入现有 `pending_sample_tokens[]`。下一 DUT sample 未被 redirect
   覆盖时统一 promotion；若 launch sample 失效，则按全局逆 allocation 顺序整体取消。

vector runtime 只保存每个 `{uid, dynamic_epoch, vuopIdx}` 对应的 token identity 和 promotion 后
的 LQ/SQ range。不得另建一套 vector pointer/free-count 回退逻辑，否则混合 batch 在 redirect
时会出现重复或乱序释放。

**理由：** V2 的 `LsqEnqCtrl` 以公共 slot 顺序计算 load/store 前缀和；把 vector 扩展到原有
标量 batch 是唯一能自然保持同拍 pointer、capacity、sample promotion 与 redirect 回退一致性的方案。
它提高 unit-stride 向量与标量混合覆盖，同时不改变纯标量 testcase 的候选选择和 allocation 语义。

## 4. D46：按 data-uop range 独立开放 issue

**决策：** 不再等待同一 vector macro 的全部 data-uop 完成 LSQ admission。某个 data-uop
自己的 `enqLsq` 请求完成 sample 确认、其 LQ/SQ range 写入 vector range map 后，立即将该
data-uop 标记为 `issue_ready`，允许它进入绑定的 vector issue queue。其它 data-uop 是否已经
完成 admission 不影响该 uop 的 issue 开放。

这里的“range 完成”只指 admission reservation 已经从 provisional 状态提升为正式状态：

```text
enqLsq launch
    -> DUT sample 确认
    -> 写入该 uop 的 lq/sq range owner
    -> range_confirmed = 1
    -> issue_ready = 1
```

它不表示该 range 的所有 flow 已执行完成，也不表示 LQ/SQ 已出队。每个 data-uop 独立维护
以下状态：

```text
ADMISSION_PENDING
    -> RANGE_CONFIRMED
    -> ISSUE_READY
    -> ISSUE_ACCEPTED
    -> WRITEBACK / REPLAY / FAULT
    -> TERMINAL
```

同一个 mixed batch 中的多个 vector data-uop 可以在同一轮 promotion 后同时变成
`ISSUE_READY`。标量 candidate 仍按原有标量状态机处理，不需要等待 vector macro 或其它
slot 的 issue 状态。

### D46 的 FOF 例外

FOF data-uop 也按自己的 range 完成 admission；但 issue scheduler 还必须施加同一 FOF
macro 内的顺序门控：

```text
FOF uop[0] range_confirmed && FOF owner 可用
    -> 允许 uop[0] issue

FOF uop[i] range_confirmed && uop[i-1] 已最终 writeback
    -> 允许 uop[i] issue
```

因此 FOF 可以多个 data-uop 同拍完成 LSQ 入队，但不能因为多个 uop 都已
`issue_ready` 就乱序发射。全部 data-uop 完成后，才发送 `fix-VL tail`；tail 仍然不进入
普通 `enqLsq`，且 `numLsElem=0`、`flowNum=0`。

### D46 的 redirect 处理

- `RANGE_CONFIRMED` 之前发生 redirect：取消该 uop 的 provisional token，不设置
  `issue_ready`。
- `RANGE_CONFIRMED` 之后发生 redirect：清除该 uop 的 issue candidate，并设置
  `issue_killed=1`，禁止后续 issue、replay 和旧实例 writeback 接收。
- 同一 macro 中已经确认的 uop 与尚未确认的 uop 分别处理；不因为某个 uop 尚未入队而
  回滚同 batch 中其它未被 redirect 覆盖的 range。

**理由：** 按 uop 开放 issue 可以缩短从 LSQ admission 到执行的等待时间，并与每个
`numLsElem=F` 的独立 range owner 相匹配。该方案仍保留 batch 的原子 launch/promotion/cancel，
所以不会破坏 mixed scalar/vector 的指针和 redirect 资源管理；新增的复杂性仅限于 vector
issue-ready 状态，不改变标量路径。

## 5. D47：FOF fault 观察与 fix-VL tail 收尾策略

### 决策范围

本决策只补充 standalone MemBlock 测试框架的 FOF fault 收尾方式，不改变 D45 的 mixed
admission，也不改变 D46 的“每个 data-uop 独立确认 range、FOF data-uop 按
`vuopIdx` 顺序 issue”规则。当前框架不记录预先注入的 fault 位置，也不实现完整架构异常
后的 redirect/reissue，因此不能把完整 XiangShan 后端的异常路径直接当作测试框架的前提。

采用以下最小策略：

```text
静态建立 data-uop[0..D-1] 和一个 fix-VL tail
    -> 按 vuopIdx 顺序发送 data-uop，并等待每个 data-uop 的最终 writeback
    -> 仅记录观测到的 exceptionVec，不据此提前取消 tail
    -> 所有可继续完成的 data-uop 完成后，在下一 DUT sample 发送一次 tail
    -> 等待 tail writeback，再按 fault_seen 分类正常完成或 direct-fault 终态
```

这里的“静态建立”表示 tail 在框架建立向量表时就作为该宏指令的 pending metadata 保存；
它不是 MemBlock 发现 fault 后临时生成的新 uop。tail 仍然满足：

```text
isVleff  = 1
lastUop  = 1
numLsElem = 0
flowNum   = 0
不调用普通 enqLsq，不建立新的 LQ/SQ range
```

### RTL 中首元素与非首元素的真实分工

Backend/VecMem IssueQueue 不读取每个元素的 fault 结果来决定 tail。它只依据静态 FOF
序列、`isVleff`、LQ dequeue/range 顺序和 `lastUop` 门控后继 issue。因此 Backend 在发出
tail 时并不知道 fault 是首元素还是非首元素。

MemBlock 内部才会在 `VMergeBuffer` 选择最老的异常元素并判断其位置：

```text
data-uop 且 vstart == 0
    -> 保留 exceptionVec
    -> 由 LoadQueue 的异常路径保存，最终可由 ROB 产生 VLS exception redirect

data-uop 且 vstart > 0
    -> 不把该 fault 作为架构 exceptionVec 保留
    -> 将最终 VL 缩短为不超过 fault 元素位置
    -> 仍需要 fix-VL tail 写回新的 VL
```

完整 DUT 中，向量异常会进入 `LqExceptionBuffer`，ROB 在异常提交条件满足后产生
`isVlsException` redirect；MemBlock 对该 redirect 使用 `flushAfter`，并由
`VfofBuffer` 清理被覆盖的 FOF 状态。若 redirect 在 tail 被接收前到达，tail 可以随旧
动态实例一起被杀掉；这属于完整后端的 redirect 行为，不是 Backend 根据 fault 位置做的
即时判断。

### 测试框架的观测与分类

框架不需要也不应该增加 `fault_pos` 随机字段。monitor 只使用已经返回的写回字段进行
分类，并按 `{robIdx, dynamic_epoch}` 将事件绑定到唯一 FOF 宏指令：

```text
is_fof_vload      = isVleff && FuType.isVLoad(uop.fuType)
is_data_uop       = is_fof_vload && !lastUop
is_tail           = is_fof_vload &&  lastUop
is_first_data_uop = is_data_uop && (vuopIdx == 0)
```

`isVleff` 不是 standalone 分类的充分条件：Decode 的准备 uop 可以继承该向量控制字段，
但它不是普通 FOF VLSU data-uop。分类时必须同时确认其为 vector load/VLSU 身份；必要时再
确认 `fuOpType` 是 FOF load 类型。

`vuopIdx==0` 只能用于识别 FOF 的首个 data-uop；一个 unit-stride data-uop 可能覆盖多个
元素，所以它不能单独证明 fault 一定发生在元素 0。真正的首元素判断应优先使用返回的
`vstart`（或等价的 fault element index）。若当前 monitor 只拿到 `vuopIdx` 而拿不到元素
位置，应保守地把 `exceptionVec` 当作 direct-fault，不猜测它是首元素还是非首元素。
tail 的 `vuopIdx` 不是稳定的唯一身份，不能用 `{robIdx, vuopIdx}` 单独判断 tail；tail
应始终用 `isVleff && lastUop` 识别。

每个 FOF runtime 保存一个 `fault_seen` 锁存位和可选的异常快照：

```text
fault_seen      = 0
fault_rob_idx   = 0
fault_vuop_idx  = 0
fault_vstart    = 0       // monitor 可观测时保存；否则标为未知
fault_vaddr     = 0       // monitor 可观测时保存；否则标为未知
fault_exception = 0
```

收到 data-uop writeback 时：

1. 先确认 `{robIdx, dynamic_epoch, vuopIdx}` 仍是当前活动实例，迟到旧实例事件直接按
    tombstone/epoch 规则丢弃。
2. `exceptionVec != 0` 时置 `fault_seen=1`，保存 `vuopIdx` 和异常快照；不把该事件当作
   tail 已取消的证据。
3. 没有 `exceptionVec` 但最终 VL 变小，按 FOF 的正常 fix-VL 语义继续等待 tail；不能把
    “VL 变小”误判成架构异常。
4. `is_tail` writeback 只负责提供最终 VL/`vlWen` 收尾，不重新生成或重新分配 LSQ entry。

按当前 RTL 语义，非首元素 fault 应被压缩为 VL 更新而非架构异常。若框架在
`vuopIdx>0` 的 data-uop 上，或在已确认 `vstart>0` 的 flow 上观察到非零 `exceptionVec`，
应保存完整快照并标记为“需要复核的 FOF 异常观测”；不能仅靠这一个字段静默归类为正常
FOF 成功，也不能立刻断言 DUT/激励协议错误。`vuopIdx==0` 但 `vstart>0` 的情况同样属于
“首个 data-uop 内的非首元素”，不能仅按 `vuopIdx` 判为首元素 fault。

当前顶层存在两个相关但不同的可观测路径：`writebackVldu` 返回 data/tail 的最终 uop
writeback，而 `FeedbackToLsq.feedback.FLUSH` 携带需要送入 `LqExceptionBuffer` 的向量异常
信息。首元素 fault 的 `exceptionVec` 需要以实际 monitor 可采到的那一路为准；如果当前
monitor 只采 `writebackVldu`，应先确认其 `uop.vpu.vstart`、`exceptionVec` 和最终 VL 的
语义，再把它用于 fault 分类。没有可观测 fault-element 位置时，只记录 direct-fault，
不伪造首/非首元素结论。

### 无 redirect 环境下的收尾状态机

当前 standalone 框架采用以下状态转换：

```text
FOF_DATA_READY
    -> FOF_DATA_ISSUING
    -> FOF_WAIT_DATA_WB
         exceptionVec != 0: fault_seen = 1（仍保持 drain 流程）
    -> FOF_DATA_DRAINED
    -> FOF_TAIL_PENDING
    -> FOF_TAIL_ISSUED
    -> FOF_WAIT_TAIL_WB
    -> FOF_NORMAL_DONE 或 FOF_DIRECT_FAULT
```

具体规则如下：

- data-uop 仍按 `vuopIdx=0,1,...,D-1` 发射；当前测试框架采用比 RTL 更保守的顺序：
  每个 uop 等前一个 uop 的最终 writeback（含 replay 收敛）后再发下一个。它是为了避免
  standalone 环境在未知 fault/redirect 时出现不可恢复的并发状态，不应误解为 DUT 对所有
  FOF data-uop 的唯一硬件时序要求。
- 最后一个 data-uop 的 writeback 在一个 monitor/sample 边界被确认后，下一次 service
  周期才允许驱动 tail，避免把同一拍的 data feedback 与 tail 当成一个事件。
- 每次驱动 pending tail 前先检查 matching redirect/flush；一旦已观察到，redirect/flush
  优先，取消未发送 tail 并转入对应清理流程。
- 若没有外部 redirect/flush，`fault_seen` 不能单独阻止 tail。这样可以让
  `VfofBuffer` 完成最终 VL 收尾，也避免框架等待一个永远不会出现的 tail writeback。
- tail writeback 且 `fault_seen==0`：记录 DUT 返回的最终 VL，进入正常 FOF 完成流程。
- tail writeback 且 `fault_seen==1`：记录为 direct-fault 结果，`success` 保持为 0，
  不把该实例当作普通成功提交；异常快照保留 `robIdx/vuopIdx/vstart/vaddr` 中可取得的字段。
  首元素 fault 时 `VfofBuffer` 可能保留初始 VL，因此 tail 返回的 VL 只记录为 DUT 观测值，
  不能作为“异常时 VL 必须等于某个固定值”的检查期望。
- direct-fault 之后停止创建该实例的 younger 宏指令。只有确认共享 LSQ/range owner 已由
  DUT 正常出队，或完成 testcase 级 reset/flush 后，才能释放框架中的 active owner、
  FOF owner 和 runtime 表项；不能仅凭 monitor 看到 `exceptionVec` 就伪造 LSQ dequeue。

“等待所有 data-uop”是一个有边界的 drain 操作：如果首元素异常后 DUT/外部环境不再
接受剩余 data-uop，框架不得无限等待，而应在超时或明确 kill 事件后进入 direct-fault
终态并复位当前测试阶段。该兜底只为避免 standalone 环境死锁，不宣称它等价于完整后端
redirect/reissue。

### 有 redirect 能力后的扩展分支

未来测试框架支持真实 redirect 后，redirect 具有更高优先级：

```text
观察到 matching redirect
    -> 取消尚未发送的 data-uop 和 pending tail
    -> 按旧 dynamic_epoch 清理 issue/FOF owner 与 provisional token
    -> 不等待 tail writeback
    -> 按 redirect flow 重新入队或结束该实例
```

因此“无 redirect 时继续 drain 并发送 tail”和“有 redirect 时取消 tail”是两个环境能力
分支，不能混写成一个由 `exceptionVec` 直接决定的条件。

### 决策理由与约束

1. tail 是 Decode 预先生成的静态收尾 uop，取消它需要 redirect/flush 的实例语义；
   monitor 单独看到异常不足以安全删除 DUT 内部 FOF 状态。
2. 非首元素 fault 的可观测结果是缩短 VL，保留 tail 才能验证 `vlWen` 和最终 VL 写回。
3. 首元素 fault 在完整 DUT 中最终会走 VLS exception redirect；当前框架没有该能力，
   所以采用“先完成可观测 drain，再 direct-fault 结束并复位”的最小兼容策略，避免把
   异常误报为普通成功，也避免留下旧 FOF owner 影响后续宏指令。
4. 不新增 FOF fault-position、tail-cancel 或 redirect 伪造 plus 参数；这些是运行时协议
   和环境能力，而不是随机激励分布。异常终态复用标量已有 fault/terminal 管理语义，
   向量专用部分只维护 `{uid, dynamic_epoch, vuopIdx}` 和 FOF tail 状态。

## 6. 向量形式的合法入队 profile

| 向量形式 | 同拍多个 vector slot | 可与标量混合 | 入队约束 | 后续 issue 约束 |
| --- | --- | --- | --- | --- |
| normal unit-stride | 支持 | 支持 | 与 scalar 共同占用连续 batch slot | 常规 issue 调度 |
| whole-register / mask | 支持 | 支持 | 按各 data-uop 的 `F` 分配 range | 常规 issue 调度 |
| FOF data-uop | 支持 | 支持 | 作为 unit-stride vector load 入队 | 同一 FOF 必须按 `vuopIdx` 串行 issue 且等待前一 data-uop writeback |
| strided / indexed | 支持，但每拍仅一个 | 不支持 | 必须单独 batch 且固定占 slot 0 | 常规 issue 调度 |
| FOF fix-VL tail | 不适用 | 不适用 | 不进入普通 `enqLsq`，`numLsElem=0` | 全部 FOF data-uop 完成后单独发送 |
| segment | 暂不支持 | 暂不支持 | 不生成普通向量入队请求 | 暂不支持 |
| replay | 不适用 | 不适用 | 不重新 `enqLsq`，复用原 LQ/SQ range | 由真实 feedback 触发重发 |

这里“strided / indexed 每拍仅一个”是 V2 Backend 合法 dispatch profile，不是 `LsqEnqCtrl`
不能计算多个 vector slot。`NewDispatch` 对 vector unit-stride 保守按 2 flow 计费，标量按 1 flow
计费；其它 vector 统一按 16 flow 计费，且源码明确限制其只能从第一个 dispatch port 发出。为保持
standalone 测试框架产生的输入可由完整 V2 Backend 合法生成，strided/indexed 固定为 batch 的唯一 slot 0，
不再追加 scalar 或其它 vector request。

FOF data-uop 的特殊性仅在 issue 顺序，不在 LSQ admission。它是 unit-stride vector load，可以和标量
或其它合法 unit-stride data-uop 同拍入队；但后续顶层直接驱动时，必须等待本 FOF 前一 data-uop 的
最终 writeback 后才能 issue 下一 data-uop，最后才发送不入 LSQ 的 fix-VL tail。全局同时只维护一个
活动 FOF，避免违反 `VfofBuffer` 的单活动 FOF 假设。

## 7. 控制参数

优先复用既有标量批量入队参数，不为向量复制第二套总 slot 控制：

| 参数 | 合法值/默认值 | 作用 |
| --- | --- | --- |
| `MEMBLOCK_ENQ_PER_CYCLE` | `[1, 6]`，现有默认 4 | 一拍总入队 slot 预算，标量和向量共同消耗。 |
| `MEMBLOCK_ENQ_PER_CYCLE_RAND_EN` 及现有权重 | 沿用现有定义 | 控制每拍总 slot 预算的随机分布与空拍。 |

新增的向量专用控制只描述向量是否参与、以及参与后占用多少总预算：

| 参数 | 合法值/默认值 | 约束行为 |
| --- | --- | --- |
| `MEMBLOCK_VEC_ENQ_BATCH_EN` | `0/1`，默认 `0` | `0` 时向量保持单 slot、vector-only 的 bring-up 模式；`1` 时启用本决策的多 slot vector admission。 |
| `MEMBLOCK_VEC_ENQ_MAX_PER_CYCLE` | `[1, 6]`，默认 `1` | 一个 batch 中 `VECTOR_DATA` candidate 的最大数；实际数仍不超过总 slot 预算和类型 profile。 |
| `MEMBLOCK_VEC_ENQ_MIXED_BATCH_EN` | `0/1`，默认 `0` | 仅在 `BATCH_EN=1` 时有效。`1` 允许 normal/whole/mask/FOF data-uop 与连续 scalar candidate 同拍混合；`0` 时 vector batch 只含向量 candidate。strided/indexed 始终不受此开关影响，固定单独 batch。 |
| `MEMBLOCK_VEC_ENQ_GAP_MAX` | 非负整数，默认 `0` | `0` 表示 vector candidate 就绪时参加下一可用 batch；大于 0 时，对同一 macro 相邻 data-uop 加入 `0..GAP_MAX` 个可入队周期的延迟。不得用该延迟跳过更老的 admission head。 |

参数组合约束：

```text
有效 vector slot 上限 = min(MEMBLOCK_ENQ_PER_CYCLE,
                            MEMBLOCK_VEC_ENQ_MAX_PER_CYCLE,
                            6)

若 MEMBLOCK_VEC_ENQ_BATCH_EN == 0：
  有效 vector slot 上限固定为 1；不允许 scalar/vector 混合。

若 candidate 是 strided 或 indexed：
  batch 只能包含该一个 candidate，slot=0；忽略 MAX_PER_CYCLE、MIXED_BATCH_EN 和 GAP_MAX 的扩展含义。
```

不新增“强行允许 non-unit-stride 混合”“覆盖 `numLsElem`/F”“忽略 redirect 回退”之类参数。这些并不增加
有效覆盖，反而会生成无法从完整 V2 Backend 合法得到的输入或破坏资源模型。

## 8. 对现有 flow 的影响

后续更新 detailed flow 时，admission / LSQ enqueue 需要把“单 vector data-uop enqueue”替换为
“统一 mixed batch 构造、整体 launch、整体 promotion/cancel”。promotion 后，按 D46 为每个
vector data-uop 独立设置 `range_confirmed/issue_ready`；vector issue、monitor、commit、dequeue 与
terminal flow 的宏观状态机不需要按 slot 数复制，仍以 `{uid, dynamic_epoch, vuopIdx}` 为一个
data-uop 运行实例。唯一新增的是每个 vector data-uop 可在自身 range 确认后提前进入 issue queue。

现有标量 transaction、候选扫描顺序、总 slot 参数和 pending sample 核心机制应被保留。实现时只泛化
candidate/token 的类型与 `numLsElem`，不迁移标量状态到 vector table，也不让 vector runtime 接管公共
LSQ pointer、free count 或 redirect writer gate。

## 10. 后续 review 检查点

1. mixed batch 的 slot 顺序必须与 candidate admission 顺序一致；不得为了填满 slot 选取更年轻 UID。
2. 每个 vector data-uop 的 range 长度必须等于自身 `numLsElem=F`，不能按实际 active flow 数缩小。
3. scalar/vector promotion 与 redirect cancel 必须覆盖同一个 pending batch，禁止部分 launch 或部分 cancel。
4. 每个 range promotion 后只能开放对应 data-uop 的 `issue_ready`，不能等待或误开放整条 macro。
5. strided/indexed 必须验证 batch 长度为 1 且占 slot 0。
6. FOF data-uop 可批量入队，但 issue scheduler 必须维持同 macro 的 `vuopIdx` 完成顺序。
7. FOF tail、segment、replay 不得意外调用普通 `enqLsq` allocation。
