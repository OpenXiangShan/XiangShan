# 向量测试框架生命周期决策记录

## 1. 文档目的

本文记录 V2 MemBlock 向量访存测试框架在生命周期 flow 设计中作出的决策性选择。它不是实现代码，也不替代
[向量测试框架需求文档](向量测试框架需求文档.md)；后者定义随机输入、静态表和接口合法性，本文解释当需求有多种
实现方式时，为什么选择当前方案。

决策遵守以下五条准则：方案保持简单且不改变标量既有语义；优先服从需求文档；只增加真正有用的控制参数；只模拟
MemBlock 验证所需的可观测行为；每一个会影响后续实现边界的选择都在本文留下理由。

当前实现状态：`vecissue_agent_agent`、`io_mem_to_ooo_vec_wb_agent_agent` 和 vector IQ feedback agent 已有
接口壳，但 driver/monitor 仍明确拒绝 vector valid。因此本文中的 `vector_*` helper 均为后续实现的目标接口名。
本决策记录与四份详细 flow 逻辑文档属于规划期设计/plan：允许在流程图和伪代码中把这些目标接口写成普通函数调用，
无需为了它们尚未落地而替换成当前源码函数名；“拟新增”只标记实现状态，不改变其后续 coding 约束力。

## 2. 术语与抽象功能说明

| 英文术语 | 本文中的含义 | 状态落点 | 例子 |
| --- | --- | --- | --- |
| `macro` | 主表中一条 `V_LOAD` 或 `V_STORE` 向量宏指令 | `main_table_by_uid[uid].vec_table` | 一个 `LMUL=m4` load 可以有 4 个 data-uop。 |
| `data-uop` | 真正进入普通 `enqLsq` 和 `issueVldu` 的向量访存 uop | `vec_table.uop[vuopIdx]` | `vuopIdx=2` 的第三个寄存器分片。 |
| `active map` | 记录当前 ROB/LQ/SQ key 到 UID 或向量 uop owner 的唯一索引 | `uid_by_active_rob`、vector range map | 不为标量/向量复制第二份 ROB map。 |
| `owner` | 物理 key 当前归属的 UID 或 `{uid,vuopIdx}` | active/range map | 重复 owner 直接报告。 |
| `batch` | 同一个 service sample 内共同仲裁、提交或回收的事件集合 | 各 flow 临时队列 | 联合预检保证整批原子。 |
| `cursor` | admission、FOF 或 ROB 中维持顺序的当前位置 | `next_enq_vuopIdx`、commit cursor | 不跳过未完成 head。 |
| `epoch` | 同一 UID 的动态实例版本号 | `dynamic_epoch`、tombstone | redirect re-admission 后递增。 |
| `range` | 一个 data-uop 保留的连续 LQ 或 SQ entry 集合 | `lqStart/sqStart + numLsElem` | `F=4` 的 store uop 占 4 个连续 SQ entry。 |
| `range map` | 每个实际 LQ/SQ entry 到其向量 data-uop 的反向索引 | `vec_range_owner_by_lq/sq` | IQ feedback 只带 `sqIdx` 时可反查 `{uid,vuopIdx}`。 |
| `terminal` | 当前 data-uop 已不再需要 issue：正常写回、取消或已确认的其他终态 | `vec_runtime_table[uid].uop[]` | 普通 writeback 后该 uop terminal。 |
| `FOF tail` | `isVleff=1 && lastUop=1` 的 fix-VL 收尾 uop | `vec_macro_runtime` | 不进普通 LSQ，写回 `vlWen=1`。 |
| `outstanding` | 已 fire 但尚未收到最终 writeback 或 replay feedback 的 data-uop 尝试 | `issue_accepted/replay_pending` | 同一 `{uid,dynamic_epoch,vuopIdx}` 同时最多一个。 |
| `launch token` | admission launch 到 sample/promotion 之间的临时 range reservation | vector uop runtime | `visible=0` 被 redirect 时只撤销自身 pointer/delta reservation。 |
| `promotion` | sample 确认 DUT 已采样后，将 token 提升为正式 per-entry owner | vector admission helper | promotion 后才允许写 tombstone/cancel。 |
| `cancel record` | redirect 后由现有 LSQ 流程统一回退的软件 LQ/SQ reservation 记录 | `common_data_transaction.cancel_record_q` | 向量 range 的总 entry 数合入同一 redirect epoch。 |
| `resource drain fence` | redirect 开始统计 cancel 前必须已结算的 deq 采样边界 | `redirect_lsq_sample_seq`、deq raw batch `sample_seq` | 先更新实际 remaining，避免 deq 和 cancel 各释放一次同一 entry。 |
| `deq sample_seq` | ctrl monitor 捕获 deq 时固化的不可变 DUT sample 序号 | `dispatch_raw_ctrl_t.sample_seq` 或等价 envelope | deferred raw 重试不得改写为当前 sample。 |
| `dequeue provenance` | deferred raw deq 的 capture 顺序、sample 序号和冻结物理 key 快照 | `{capture_order,sample_seq,lq_keys[],sq_keys[],sq_deq_ptr_at_capture}` | V2 SQ 重放不重新读取当前 SQ head。 |
| `STALE_DROP` | gate 后某一完整 LQ/SQ domain 的所有 key 都逐 key 命中当前 redirect 的 tombstone 时的消费结果 | provenance classifier/effective batch | 可跨多个 covered UID；不推进 pointer/free count，不删除 owner。 |
| `covered UID set` | 当前 redirect 覆盖、资源排空时不得进入终态的 UID 集合 | `redirect_transition_plan.covered_uid_set` | 不依赖尚未写入的 `flushed` 位。 |
| `fault head` | 异常 commit 已送出、但仍等待真实 deq/终态的共享 ROB head token | `fault_head_waiting/kind/uid/epoch` | D=1 vector fault 阻塞更年轻 commit。 |
| `tagged fault-head sync` | 按 fault 类别收敛 token 与 commit cursor 的公共同步 | 扩展 `sync_modeled_head_after_fault_terminal()` | VECTOR 的 `issue_killed` 不单独代表 redirect。 |

## 3. 决策总览

| 编号 | 决策点 | 采用方案 | 不采用的方案 |
| --- | --- | --- | --- |
| D1 | UID 与 ROB 所有权 | 统一 UID、统一 `uid_by_active_rob`，按 `op_class` 分派运行状态 | 标量和向量各自维护一套 active ROB map。 |
| D2 | 向量 LSQ 所有权 | 新增 vector range map，每个 entry 映射 `{uid,vuopIdx}` | 复用标量“一个 UID 对应一个 LQ/SQ key”的 map。 |
| D3 | 向量 admission 粒度 | 一个 vector data-uop 每次发一条 `enqLsq`，同一 macro admission 期间不与后续 UID 交错 | 一次为所有 uop 建虚拟 reservation，或第一版就把一个 macro 分散到多个 slot/周期。 |
| D4 | Issue 开放时机 | 所有 data-uop 的 `enqLsq` 已完成后，整体写入 vector issue queue | 每完成一个 range 就允许该 uop issue。 |
| D5 | 双 issue lane 使用 | 普通/FOF 宏在建表时固定一个 lane；segment 暂不支持 | 同一 macro 的 uop 在两个 lane 间自由迁移。 |
| D6 | FOF 顺序与收尾 | 每个 FOF data-uop 等前一个 data-uop 的 writeback，再发下一个；全部 data-uop 正常完成后才发 tail。若顶层 data-uop WB 带真实异常，按 `{uid,dynamic_epoch}` 清理旧 issue/FOF 所有权、取消 tail 后报告 fatal；不把无法从顶层观测确认的后续元素抑制当作 terminal | 仅按 issue handshake 发 tail，或凭普通 WB 的 `vl`/异常位猜测后续 uop 已被 DUT 抑制。 |
| D7 | replay 身份 | 一个 data-uop 同时只允许一个 outstanding 尝试；full/partial replay 都只由真实 store feedback 触发 | 首次 issue 随机 replay 字段，或照搬标量 `issue_epoch` 做外部 event 匹配。 |
| D8 | redirect 后行为 | 向量沿用统一 UID 的 flushed/redirect_pending 生命周期：回退旧 range 后保留 UID，等待同 UID 重新 admission；不把旧实例直接标为 terminal | 将向量直接标成 `canceled_terminal`，或重新生成一个 UID/ROB 实例。 |
| D9 | 端到端完成定义 | 宏观等待 data-uop、FOF tail、ROB commit 和实际 LSQ deq/cancel 收尾 | 逐 flow 模拟 TLB、DCache、merge buffer 的内部状态。 |
| D10 | plus 控制 | 优先复用已有全局控制和需求文档已有向量权重；仅建议新增 lane 权重 | 为每个中间 runtime 状态增加独立开关。 |
| D11 | 指针存储时机 | 静态表保存 `F` 和方向；实际 LQ/SQ 起始指针、range 与 entry owner 在 admission 时写入 runtime | 主表随机初始化时预先占用运行期 LSQ 指针。 |
| D12 | 迟到事件保护 | redirect 删除 range/ROB owner 前创建带动态实例和过期采样边界的 vector tombstone；无 ROB 的 store feedback 只能用 SQ tombstone 过滤 | 删除 owner 后把所有无法反查的 feedback 当作新实例错误，或让 SQ key 立即复用。 |
| D13 | V2 出队预检 | SQ 侧按 count-only 从软件 `sq_deq_ptr` 展开；LQ/SQ 整批先联合预检，全部通过后才修改 map、pointer 和计数 | 把 V2 SQ raw 当作带 DUT 起始指针，或边检查边释放造成部分提交。 |
| D14 | 向量终态写入 | 使用 vector 专用 terminal helper，显式写 `status.success`/`terminal_done`，不调用 scalar `required_targets_done()` | 复用 scalar retire helper 并让其读取不存在的 LOAD/STA/STD 状态。 |
| D15 | fault 与 redirect 的关系 | 顶层 `exceptionVec` 是 fault-head 路径，不自动伪造 redirect 或 re-admission；只有真实/外部 redirect 才取消动态实例并重入队 | 将所有异常都当作 redirect，或异常后直接重新发射相同宏指令。 |
| D16 | 初版直接 fault 的覆盖边界 | 仅由专用 `D=1`、非 FOF fault 模板覆盖；普通生命周期默认 `vtypeIllegal=0`，多 data-uop 直接 fault 暂不在初版随机空间内 | 用未定义的多 uop cancel 规则强行完成异常，或把非法 VTYPE 当正常成功。 |
| D17 | LSQ admission 资源门槛 | 向量 admission 镜像 V2 `LsqEnqCtrl` 的两侧 width 保留量、延迟 `canAccept` 和 redirect 更新门控；`free_count >= F` 不是充分条件 | 只比较当前方向 free count，导致接近满载时发送 DUT 不可接受的请求。 |
| D18 | monitor 域分流 | raw event 在 scalar normalization 前分为 scalar/vector/redirect；vector 不经过 `normalize_feedback_event()` 或 scalar handler | 先按 scalar target/issue_epoch 归一化，再在末端检查 `vector_ls`。 |
| D19 | issue route 幂等性 | 初始 D 个 item 采用完整预检后一次性写入；`issue_pending` 与 queue membership 同步，重复 `(uid,vuopIdx,replay_seq)` 拒绝 | service loop 每拍重复扫描 `enq_done` 并追加同一 uop。 |
| D20 | dequeue 身份粒度 | 每个物理 key 形成 `{domain,key,uid,vuopIdx}` token，LQ/SQ 联合预检后按域更新；vector 不压成 UID 数组 | 复用 scalar UID-only deq 列表，无法递减同 UID 多个 range。 |
| D21 | 同拍 fault/replay 仲裁 | redirect > vector fault > 正常 writeback > replay miss > success feedback；同 uop fault+replay 取 fault，正常 WB+replay miss 报协议错误 | 按 port 收集顺序先处理 replay，可能重新发射已异常 uop。 |
| D22 | tombstone 对新分配的约束 | 新 vector 实例在对应 ROB/LQ/SQ tombstone 到期前不得复用 key；命中 tombstone 时等待/丢弃，不覆盖旧事件保护窗口 | 删除 owner 后立即复用 key，迟到 feedback/writeback 命中新实例。 |
| D23 | writeback 采样与零活动 uop | 当前 standalone 顶层只暴露 `writebackVldu.valid/bits`，monitor 按 `valid=1` 采样；`VL=0`/全 mask-off 仍保留 F、正常 issue 并等待宏观 writeback。若未来暴露 ready，再改按 `valid && ready` | 把不存在的 ready 当作当前输入，或因 flowMask=0 提前 terminal/释放 range。 |
| D24 | admission launch token 可见性 | launch 先建立 `visible=0` 的 provisional token；sample 前被 redirect 时仅由持 writer gate 的 coordinator 撤销 token 自身的 enqueue-pointer 边界和 reservation delta，不覆盖当前 free count、不计 cancel；sample 后 promotion 为 `visible=1`，后续按实际 remaining 计 cancel | 把所有 launch 都当成已可见 range，重复写 cancel 或错误回退。 |
| D25 | terminal 判定重检时机 | commit、dequeue、FOF tail writeback 和 fault commit 都调用对应幂等 terminal helper，覆盖 commit/deq 先后任意顺序 | 只在 dequeue 事件检查 terminal，导致 deq 先发生时后续永久卡住。 |
| D26 | replay 与 fault 状态更新原子性 | replay 先预检并成功追加 queue item，再一次性更新 runtime；fault handler 独占 `issue_accepted` 清理 | 先改 pending 再入队造成孤儿状态，或 writeback/fault 两个 handler 重复清 outstanding。 |
| D27 | FOF/redirect 的 issue 所有权清理 | 按 `{uid,dynamic_epoch}` 清除 driver pending payload、FOF send reservation 和 active FOF owner；FOF fault 初版清理后 fatal | 只删 queue item，留下旧 valid 或 active FOF lock。 |
| D28 | 规划期 flow 的调用表示 | 四份详细逻辑文档允许将规划 helper 直接写成函数调用；现有源码函数只标示接入点 | 因 helper 尚未实现而把设计调用关系退化成模糊文字分支，或错误宣称当前源码已经实现。 |
| D29 | provisional token 取消的计数边界 | 只撤销 token 自身的 enqueue-pointer delta 和 `reserved_entries`；对当前 free count 做加法，不回写历史快照 | 直接恢复 `free_count_before/after`，覆盖并发 dequeue/cancel 的变化。 |
| D30 | 主表随机组合空间 | 以显式 `op_class × v_form × v_mode` 合法表联合抽样；非法交叉组合不进入候选 | 先独立抽样三个字段再丢弃，导致 D/F、fuOpType 和 payload 互相矛盾。 |
| D31 | 无序号 replay feedback | 顶层 `hit=0` 只有在当前 uop `issue_accepted=1 && !replay_pending && !terminal` 时才接受；其余非 tombstone 事件报协议错误 | 用本地 `replay_seq` 猜测 DUT 未携带的反馈序号，承诺无法验证的迟到事件过滤。 |
| D32 | fault terminal 的公共状态 | D=1 direct-fault 完成真实 deq 和 fault-head commit 后，清 `exception_pending`，保留 `fault=1`/异常快照，再写 `success=0、terminal_done=1` | terminal 后继续保留 exception_pending，或把 fault 当正常 success。 |
| D33 | redirect re-admission 门控 | 非零 vector 贡献所引用的 shared aggregate cancel record 必须 `software_applied=1`，并与 tombstone drain、active owner 清理共同满足后才能 re-admission | 只等待 tombstone 到期就重用共享 pointer/free count。 |
| D34 | FOF tail writeback 身份 | `vlWen=1 && vecWen=0 && v0Wen=0` 的 tail shape 只能走 tail match/tombstone；release owner 成功前不得提交 tail 完成状态 | 把 tail 占位 `vuopIdx=0` 当作普通 `uop[0]`，或 release 失败后仍 terminal。 |
| D35 | re-admission 公共状态重置 | redirect 产生的新 epoch activation 原子清零旧 `flushed/redirect/enq/issue/commit/deq/fault/issue_killed` 结果、清 invalid 引用，再建立新 active 实例 | 只重建 vec runtime，保留旧公共状态导致 admission/commit 永久阻塞。 |
| D36 | issue-kill 的发射、反馈与写回门控 | DATA candidate、fire 前、正常 data-uop writeback 和 store feedback 都检查公共 `status_by_uid[uid].issue_killed`；runtime 同名字段只作镜像，旧实例被 kill 后不得继续发射、重放或标 terminal | 只删除 queue item，遗漏 pending payload/竞态 fire，或在 fault/redirect 后把迟到 WB/feedback 当正常完成。 |
| D37 | ROB key 与 epoch 真源 | active map 一律使用 `rob_order_util::rob_to_map_key(rob_key)`；`dynamic_epoch` 只由公共 `status_by_uid[uid]` 在 redirect transition 递增一次，runtime 只同步镜像 | 用裸 `robIdx` 作为 map 下标，或由多个 runtime/helper 各自递增 epoch。 |
| D38 | 多 provisional token 取消原子性 | 初版复用全局单深度 pending-sample；未来多 slot 先建立全局 allocation ledger，再按方向/全局逆序整体预检和取消；任一 mismatch 时 token、pointer、free count 均不变 | 逐 token 边取消边修改，后续 token 失败后留下部分回退。 |
| D39 | redirect 与公共 vector fault-head | redirect 在更新 epoch 前按 `{uid,old_dynamic_epoch}` 取消匹配的 vector fault-head token/待处理记录，解除旧 UID 对公共 commit cursor 的阻塞；不触碰 scalar 或其它 epoch 的 fault-head | 只清 vector runtime，留下 `fault_head_waiting` 阻塞 cursor，或无条件清除其它 fault-head。 |
| D40 | vector fault 的 issue-kill 语义 | D=1 direct-fault 可保留 `issue_killed=1` 来停止旧 issue；tagged fault-head sync 对 VECTOR 不以该位单独取消 token，只有 redirect/epoch stale 或真实异常终态才收敛 | 直接复用 scalar `issue_killed` cancel 逻辑，导致 vector fault-head 在真实 deq 前被提前解除。 |
| D41 | redirect 聚合 cancel 回退 | 一个 redirect 只建立一个 aggregate cancel record；由 `redirect_epoch` writer gate 在全部 scalar/vector 计数 finalized 后一次应用 | 每个 UID 分别 apply，或在聚合计数完成前扫描 foreign record。 |
| D42 | redirect 与已采样 deq 的资源顺序 | 以 `redirect_lsq_sample_seq` 为资源排空栅栏；先联合结算边界以前 deq，再冻结/取消剩余 range | gate 内缓存旧 deq 后直接按当前 pointer 重放，导致已取消 key 被双重释放或误报。 |
| D43 | raw deq 的 capture provenance | raw ctrl/deferred queue 保存 capture 时的不可变 `sample_seq` 和 LQ/SQ 物理 key 快照，用它与 redirect cut line 比较 | 使用 `$time` 的 `cycle`，或在重试时用当前 pointer/current sample 重新推导。 |
| D44 | gate 后 deferred deq 的 tombstone 分类 | 按完整 domain 只允许 `LIVE_COMMIT` 或 matching-tombstone `STALE_DROP`；mixed/identity mismatch fatal | tombstone 一律 fatal，或逐 key 静默 drop。 |

## 4. 决策详情

### D1. 统一 UID 和 active ROB map

**决策：** 主表中的 UID 对标量和向量全局唯一；只保留一份
`uid_by_active_rob[rob_order_util::rob_to_map_key(rob_key)] -> uid`。收到事件后先由
完整 ROB key 查询 UID，再由 `main_table_by_uid[uid].op_class` 路由到标量或向量 handler。

**理由：** 这符合需求文档第 5.6 节，且避免两个 map 对同一 ROB key 的重复所有权。当前公共框架的 active map、
terminal prefix、commit cursor 以及若干通用 helper 已依赖 `status_by_uid`；因此 vector UID 保留一份
`status_transaction`，但只使用其中的公共生命周期字段：`active/enq/issue_ready/rob_commit/lsq_deq/terminal_done`
以及 ROB snapshot。向量绝不写入或读取 scalar LOAD/STA/STD target、scalar replay target、scalar source 等字段；
所有 data-uop 生命周期仍只在 `vec_runtime_table`。这比完全绕开 `status_by_uid` 更少改动，也不改变标量字段语义。

### D2. 向量 range map 而非单一 LQ/SQ key

**决策：** 对每一个 vector range 的每个物理 entry 建立：

```text
vec_range_owner_by_lq[lqKey] = { uid, vuopIdx }
vec_range_owner_by_sq[sqKey] = { uid, vuopIdx }
```

宏 runtime 同时保留每个 uop 的 `range_remaining_entries`。LQ/SQ deq 每消费一个 entry 递减一次；只有整个
range 清零时，该 data-uop 的 `range_dequeued` 才成立。

**理由：** `numLsElem=F` 表示真实连续 entry 数，而不是一个 UID 的属性。一个 UID 下可能有多个 uop，且同一
uop 有 F 个 entry。标量 `uid_by_lq/sq` 和 `status.active_lq/sq_mapped` 只表达一个起始 key，直接复用会在
第二个 flow deq 时丢 owner，或在第一个 deq 时错误释放整个 uop。该新增 map 只服务 vector，不改变标量 map。

### D3. macro 串行 admission，单 data-uop enqueue

**决策：** 初版为一个 vector data-uop 生成一次普通 `enqLsq` 请求；同一 macro 的 `vuopIdx` 按升序 admission，
在全部 D 个 data-uop 已被 DUT sample 前不推进下一个主表 UID 的 admission。每拍最多发送一个 vector data-uop。

**理由：** V2 顶层 `enqLsq` 没有 ready/response，每个 valid 拍都是一次真实 allocation。一次驱动一个 vector
uop 可直接复用现有“launch 后 reservation、下一采样边界才开放”模型，并避免第一阶段处理同拍 scalar/vector
slot 混合、部分 macro reservation 或 vector range 跨 slot 的复杂回退。代价是吞吐较低，但它不影响 MemBlock
功能覆盖，也不会改变纯标量 testcase 的 candidate/slot 行为。

### D4. 在整条 macro admission 后才开放 vector issue

**决策：** `enq_done=1` 前所有 vector data-uop 都不进入 `vector_issue_q[0/1]`；全部 range 已确认后，才把 D 个
轻量 queue item 一次性投入其绑定 lane 的队列。

**理由：** 需求文档只要求验证 MemBlock，不要求复现 Backend dispatch 与 VecMem IQ 的重叠性能。整体开放让
redirect 时没有“部分已 issue、部分尚未 admission”的两段生命周期，也保证 FOF 串行链从完整静态 uop 集合开始。

### D5. lane 绑定

**决策：** 普通 non-segment macro（包括 FOF）在建表时按下列权重固定 `queue_id`，其全部 data-uop、replay
和动态 tail 都使用同一 issue lane：

```text
MEMBLOCK_VEC_ISSUE_VLDU0_WT = 1
MEMBLOCK_VEC_ISSUE_VLDU1_WT = 1
```

只有存在可选的 non-segment macro 时才要求两权重至少一项大于零；若当前 testcase 只生成 FOF 且某 lane 权重为
零，不因无关 lane 被禁用而 fatal。`v_form=fof` 不再强制 `queue_id=1`；segment 当前不生成，后续启用时固定
lane 0。

**理由：** lane 不是事务身份，writeback lane 也不保证与 issue lane 一致。固定 binding 只降低测试框架调度状态，
不限制 DUT 内部 VLSU 的实际流动。V2 的 `VfofBuffer` 从两个 issue 输入择一接收 FOF，而 fix-VL writeback
固定仲裁到 `writebackVldu_1`，所以不能用 writeback lane 反推 issue lane。两个新权重可用于单 lane bring-up、
双 lane 压力和回归覆盖；若后续确认无需定向 lane 覆盖，可退化为固定轮询而不改变向量生命周期。

### D6. FOF 仅使用可观测顺序，不猜测内部 flow

**决策：** 直接驱动顶层时，一个 FOF macro 必须满足：

```text
data-uop 0 fire -> data-uop 0 writeback -> data-uop 1 fire -> ... ->
data-uop D-1 writeback -> fix-VL tail fire -> tail writeback
```

FOF data-uop 和 tail 不采用普通 uop 的 valid-hold。`MemBlock` 将原始 `issueVldu.valid` 直接送入
`VfofBuffer.io.in`，该路径不使用顶层 issue lane 的 `ready` 作为入队门控。因此测试框架只能在目标 lane 已观察到
`ready=1` 时创建 `fof_send_reservation` 并发出一个单拍 FOF `valid`；`ready=0` 时 reservation 与 valid 都必须为 0，
原候选保持 pending。如果已经创建 reservation 的拍出现 `valid=1 && ready=0`，才报告协议错误并停止该尝试，不能
保持 valid 或把同一个脉冲当作普通握手重试。全局同时只允许一个活动 FOF。

“活动 FOF”不能只在 fire 后才限制：在同一调度拍，两个尚未 active 的 FOF macro 也不能分别被两个 lane 选中。
因此 scheduler 先在全局 FOF 候选中按 `{uop_send_pri, UID/ROB, kind, vuopIdx}` 仲裁一个
`fof_send_reservation={uid,dynamic_epoch,kind,lane,vuopIdx}`；其中 `kind=DATA` 的 `vuopIdx` 是真实索引，
`kind=TAIL` 的 `vuopIdx` 固定为 canonical `0` 且不参与 tail 身份比较。两个 lane 的候选选择都读取该保留位，只有其绑定 lane 可以驱动这个
FOF，另一 lane 必须排除所有 FOF 候选。该保留位仅覆盖当前单拍发送：成功 fire 后转成
`active_fof_owner={uid,dynamic_epoch}`，未 fire
则报告协议错误，不保留为普通 pending payload。普通非 FOF uop 仍可在另一 lane 竞争，不需要为了简单性冻结全部
向量 issue。

运行表不把 `suppressed` 当作正常 terminal 条件。V2 `VMergeBuffer` 对 FOF 非首元素异常会在内部
缩短 `vl`、不把异常传播为顶层 data-uop exception；测试框架无法仅凭普通 data-uop writeback 确认某些后续 uop
已被 DUT 抑制。因此正常路径仍按 D 个 data-uop 顺序发射并等待其 writeback，不能自行少发 uop。

若任一顶层 data-uop writeback 的 `exceptionVec` 非零，这是可观测的真实 fault（典型是 FOF 首元素异常）。
FOF fault 必须先按旧 `{uid,dynamic_epoch}` 清理 issue/FOF 所有权、取消 tail，再报告 fatal 并停止 testcase；它
不等待 redirect 或 re-admission。只有 multi-uop 非 FOF fault 才在初版保留 fault 等待独立真实 redirect；不能把旧实例
标为 suppressed terminal。保留 `suppressed` 字段仅作为调试/未来 RTL 明确输出的预留字段，当前不会由普通 WB 推导。

**理由：** V2 顶层没有“FOF 后续 uop 已被内部抑制”的独立输出。`VMergeBuffer` 对非首元素异常只在内部
缩短 `vl`，而首元素异常保留真实 exception 并应进入 fault-head；测试框架无法从普通 data-uop WB 区分这两种
情况。因此不把 `suppressed` 当作正常完成依据，避免在 DUT 仍需要接收某个 data-uop 时提前发 tail。

### D7. replay 与迟到事件

**决策：** 首次 issue 的 replay 三字段固定为 0。vector store feedback 的 `hit=0` 表示该 uop 需要重发：
`isVecPartReplay=0` 时为完整 replay，按原 payload 重发且三字段仍为 0；`isVecPartReplay=1` 时要求非零
`vecReplayMask`，保存 mask/merge-buffer index 后作 partial replay。两类重发都不新建 enq、range、UID 或 ROB 项。

`writebackVldu` 没有外露 `issue_epoch`；因此向量不伪造标量式 epoch 匹配。测试框架内部仍为每个动态实例分配
`dynamic_epoch`，并要求每个 `{uid,dynamic_epoch,vuopIdx}` 始终最多只有一个 outstanding 尝试；重发前必须已收到该
uop 的明确 replay feedback。状态不匹配的 writeback/feedback
在未 redirect 时报告协议错误，在 redirect 覆盖后按现有 flush 规则丢弃。

**理由：** 这是 V2 顶层可观察字段所允许的最小正确模型。增加环境内部 epoch 不能让一个没有 epoch 的 DUT output
具备可验证来源，反而会制造假的过滤保证。

### D8. redirect 后同 UID re-admission

**决策：** 对 redirect 覆盖的 vector macro，先按旧 `{uid,dynamic_epoch}` 清除 driver pending、FOF reservation
和 issue queue item；对已 fire 未写回的 FOF tail 置 canceled 并以完整 `rob_key` 写独立 tail tombstone；再删除旧动态
range owner，并将尚未释放的 entry 总数纳入现有 redirect epoch 的 `cancel_record`。通过统一 active-map API 调用
现有 `retire_active_uid(uid)` 删除旧 `uid_by_active_rob[rob_order_util::rob_to_map_key(rob_key)]` 后，必须调用
`clear_uid_dispatch_result(uid)`，清除
`active_instance_flush_epoch_valid` 和其它旧 activation 结果；最后才执行与
`common_data_transaction::prepare_uid_for_redirect_reissue()` 等价的公共状态转换：`flushed=1`、
`redirect_pending=1`、`active=0`、`success=0`、`terminal_done=0`、`rob_commit=0`、`lsq_deq=0`，并调用公共状态
更新边界只递增一次 `status_by_uid[uid].dynamic_epoch`。UID、ROB 快照和静态向量表保留，redirect 完成且 tombstone 排空后由同一 UID 重新走
`activate_uid` 和普通 vector admission，重新分配 range。

**理由：** 直接把旧向量实例标为 terminal 会让统一 commit cursor/prefix 越过尚未重新执行的 UID，且与现有
`prepare_uid_for_redirect_reissue()` 的标量语义不兼容。保留同 UID 只模拟 MemBlock 需要的重新 admission、资源
回退和事件隔离，不要求测试框架重建完整 Backend rename/VecMem IQ；scalar 的原 reissue 逻辑完全不变。

### D9. terminal 的宏观定义

**决策：** 正常 vector macro 只有同时满足下列条件才 `terminal_done`：

```text
全部 data-uop 已 writeback
无 replay_pending 或 issue outstanding
FOF 已收到 tail writeback（若适用）
公共 ROB commit 已记录
全部 vector range 已从真实 LQ/SQ deq sideband 释放
```

`rob_commit` 与 `lsq_dequeued` 独立记录，不能假设二者一定同拍或严格先后。V2 vector store 的 RTL 注释明确
`scommit` 只用于 scalar store，因此 vector commit 不得增加 `io_ooo_to_mem_lsqio_scommit`；vector range 的实际
释放以 DUT deq sideband 为唯一依据。

vector 正常终态必须通过 vector 专用 helper 显式写入公共 `status.success=1` 和 `status.terminal_done=1`，并在
确认 owner map 为空后再调用公共 active-UID retire。该 helper 不调用 scalar `required_targets_done()`；向量异常若
走 redirect/reissue，旧实例保持 `success=0`、`terminal_done=0`，不能被 terminal prefix 跳过。

**理由：** 这保留了测试框架最有价值的资源回收检查，同时不复制 VLSU 内部 flow、TLB、DCache、merge-buffer 状态。

### D10. 控制参数边界

**决策：** 向量 flow 复用已有的 `MEMBLOCK_LSQENQ_SEQ_EN`、`MEMBLOCK_LSQENQ_READY_TIMEOUT`、
`MEMBLOCK_LSQCOMMIT_SEQ_EN`、`MEMBLOCK_REDIRECT_SEQ_EN`，以及需求文档已定义的 op class、VTYPE、地址、stride、
`MEMBLOCK_VEC_UOP_SEND_PRI_EN` 等权重。`MEMBLOCK_SEND_PRI_MODE_EN` 保持标量主表 priority 的既有语义，不能用来
改变向量 data-uop 的顺序；向量只使用自己的 `MEMBLOCK_VEC_UOP_SEND_PRI_EN`。仅建议新增 D5 的两个 lane 选择权重。

不新增“每拍 vector range 数”“FOF 顺序开关”“replay 次数上限”“flow/TLB/DCache 跟踪开关”。这些要么会破坏协议，
要么只是内部实现细节，不提高 MemBlock 层验证价值。

### D11. LQ/SQ 指针是运行期 allocation fact

**决策：** `activate_uid` 阶段先建立统一
`uid_by_active_rob[rob_order_util::rob_to_map_key(rob_key)]=uid` 并初始化 vector runtime；静态
`vec_static` 和 `vec_uop[]` 只保存由 VTYPE 派生的 `F=numLsElem=flowNum`、load/store 方向和 `vuopIdx`。真实
`lqStart/sqStart`、完整 range、entry owner 和 allocation epoch 仅在 `enqLsq` launch 已确认后写入
`vec_runtime_table[uid].uop[vuopIdx]`。

**理由：** ROB owner 是激活阶段就必须可见的公共事实，否则尚未分配第一个 range 的向量 UID 会漏掉 redirect scan。
LQ/SQ enqueue pointer 由先前已被 DUT sample 的 scalar/vector admission、实际 deq 与 redirect cancel
共同决定。主表生成阶段尚不知道这些运行期事实；提前在静态表分配会在 redirect、idle cycle 或不同 admission
交错后与真实 pointer 偏离。需求文档中“初始化时填写 LSQ 起始指针/范围”的表述因此细化为：初始化只产生
`F` 和空的 range descriptor，admission 成功后记录真正分配结果。此调整不改变 `F` 的静态合法性，也保留人可查的
起始指针和范围，只是把它们放到正确的生命周期所有者中。

### D12. tombstone 与 raw event 排空

**决策：** redirect 处理 vector macro 时，在删除每个 SQ/LQ/ROB owner 前写入短期 tombstone；正常 range
dequeue/terminal 回收也为已完成的 SQ range 保留一个更短的 success tombstone，以吸收 `VMergeBuffer` 的
`RegNext` 成功反馈：

```text
vec_tombstone_by_sq[sqKey] = { uid, dynamic_epoch, expire_sample_seq }
vec_tombstone_by_rob[{robKey, vuopIdx}] = { uid, dynamic_epoch, expire_sample_seq }
vec_tombstone_by_fof_tail[robKey] = { uid, dynamic_epoch, expected_pdest, expire_sample_seq }
vec_success_tombstone_by_sq[sqKey] = { uid, dynamic_epoch, expire_sample_seq }
```

redirect tombstone 的 `expire_sample_seq` 至少覆盖 redirect 的 LSQ flush sample 和随后一个 monitor drain sample；
success tombstone 至少覆盖一次 feedback drain。store feedback 没有可靠 ROB 身份，只能通过 SQ tombstone 过滤；
普通 data-uop writeback 可通过 `{robKey,vuopIdx}` tombstone 过滤，FOF tail 则以 `robKey + vlWen + pdest` 查 tail
tombstone。新 vector 动态实例在同一 key 的 tombstone 排空前不得复用该 key；这只约束 vector 专用 owner，不改变
标量 map。这里的“只约束 vector”只指 `vec_tombstone_by_sq/rob` 和 success tombstone 的 feedback/writeback 保护；
D44 新增的 `redirect_deq_tombstone` 是不同的物理资源 quarantine，mixed/vector redirect 时必须同时约束 scalar/vector
allocation。`hit=1` 命中 success tombstone 时只记日志，不重新激活 uop；`hit=0` 命中旧 redirect tombstone 时直接丢弃。

### D13. V2 count-only 出队与联合预检

**决策：** V2 `sqDeq` raw 只有 count，起点固定取软件 `lsq_ctrl.sq_deq_ptr`；只有 pointer-capable 版本才读取
DUT 指针。每个 raw batch 先展开所有 LQ/SQ key，并同时检查 scalar owner、vector per-entry owner、重复物理 key
和 range 剩余数；任一检查失败时不修改任何一侧 pointer/map。预检完整通过后，再统一删除 owner、递减计数和推进
软件指针。

### D14. FOF suppression 的边界

**决策：** FOF scheduler 保证单 macro 单 outstanding、按 `vuopIdx` 顺序发送。普通 data-uop WB 不提供可可靠
区分“内部 VL 缩短”和“后续 uop 被抑制”的独立标志，因此当前不根据 `vl` 或普通 WB 推导 `suppressed`，也不
允许在未完成 D 个 data-uop 时提前发送 tail。全部 D 个 data-uop 正常 writeback 且无 replay 后才发送 tail。

若 data-uop WB 带非零 `exceptionVec`，按真实 fault 处理：停止后续发射、先清除旧 issue pending/FOF owner、取消 tail；
普通非 FOF 的 D=1 模板进入 D15 的 fault-head 路径，多 uop 非 FOF 保留 fault 并等待真实 redirect；FOF fault 在初版
直接报告 fatal 并停止 testcase，不继续等待 tail 或 redirect，也不会自动 re-admission。只有未来
RTL 明确提供“非 trap 的后续 uop 抑制”可观测事件时，才可新增独立 suppressed 分支并重新评审 tail 条件。

### D15. fault 与 redirect 是两条不同的恢复路径

**决策：** 顶层 `writebackVldu.exceptionVec != 0` 按 `v_form/D` 分流，不能由测试框架凭空构造 redirect，也不能
无条件复用 D8 的 re-admission。仅 D=1、非 FOF 专用模板在公共 ROB cursor 到达该 UID 时走 vector fault-head 提交流程：

```text
vector data-uop exceptionVec
-> macro.fault_pending + 公共 status.fault/exception_pending
-> vector fault-head ROB commit
-> 等待真实 LQ/SQ deq 清空该宏已分配 range
-> success=0、terminal_done=1、回收 UID
```

fault-head commit 的 `isStoreException` 仅由 `op_class==V_STORE` 派生；不能调用会把向量解释成标量
LOAD/STA/STD 的 `derive_op_behavior()`。它也不能调用 scalar `try_retire_committed_uid()`，因为后者不知道
vector range map，会在 range 尚未真实 deq 时过早回收。

FOF fault 在初版先调用 issue kill 清除旧 pending/reservation/FOF owner，置 `fof_tail_canceled=1`，然后 fatal 停止 testcase；
多 uop 非 FOF fault 先清理旧 issue pending，保留 fault，等待真实 redirect。只有现有 redirect agent/monitor 已经接受一个真实 redirect 时，才进入 D8：写 tombstone、取消旧 range、
保留同一 UID，然后重新 activation/admission。redirect 在同一 sample 中优先于 fault/writeback；已被 redirect
覆盖的异常 event 直接丢弃。

**理由：** 当前标量框架也把 fault-head 与 redirect 分开：fault 在 ROB head 以异常提交收尾，redirect 才清理旧
动态实例。把顶层异常直接翻译为 reissue 会在地址或 VTYPE 仍然相同的情况下形成无限重试，并掩盖 `exceptionVec`
本身的功能错误。

### D16. 初版直接 fault 只覆盖安全的 D=1 模板

**决策：** 初版不尝试在没有后端 squash 可见事件的情况下，推导一个多 data-uop macro 在中途 fault 后哪些已入队
range 应被取消。因此直接 `exceptionVec` fault 只允许专用的 `D=1`、非 FOF vector fault 模板；该模板只有一个
range，不存在未发 data-uop 的取消歧义。普通随机向量生命周期要求 `vtypeIllegal=0`，默认
`MEMBLOCK_VEC_VTYPE_ILLEGAL_0_WT=100`。`vtypeIllegal=1` 只有在对应专用异常模板已经实现并明确选择时才放行；
否则在主表构造期报配置错误或筛除。当前 V2 standalone `issueVldu` 没有可驱动的 `vill` 输入，且 `src_4`
仅承载 VL，因此 builder 必须始终保持 `src_4[7:0]=VL、src_4[127:8]=0`，不能把 illegal 元数据编码到 `src_4`。

对不在该模板内却收到的 multi-uop 非 FOF 顶层 fault，框架先调用 issue kill 清理旧 issue pending，报告不受支持的
激励组合并等待真实 redirect；它不将未完成 uop 伪造为 terminal，也不自行回收其 range。FOF 顶层 fault 按 D14 的
policy 清理旧 FOF owner 后直接 fatal。后续若需要扩大 fault 覆盖，必须先加入可以观察到的
squash/cancel 协议，再重新评审该边界。

**理由：** 这保留有效的单 uop 异常和所有正常、replay、redirect 覆盖，同时避免测试框架为了模拟 Backend
内部异常恢复而添加不可验证的多 uop 状态机。该限制符合“验证 MemBlock 可见行为而非完整重建 Backend”的范围。

### D17. Admission 必须镜像 V2 `canAccept` 保留量

**决策：** 向量 admission 在生成 `enqLsq` 前执行一个向量专用 `vector_lsq_can_accept()` 预检。对本拍有效
请求分别累加 `batch_lq_need` 和 `batch_sq_need`，并采用：

```text
lq_guard = lq_free_count >= batch_lq_need + LSQLdEnqWidth
sq_guard = sq_free_count >= batch_sq_need + LSQStEnqWidth
can_accept = lq_guard && sq_guard && !redirect/t2_update
```

当前初版一拍只有一个 vector data-uop，因此对应方向的 `batch_*_need=F`，另一侧仍需满足 width 保留量。
软件模型用 pending-sample token 对齐 `LsqEnqCtrl` 的 `RegNext` 延迟；如果未来直接接出 DUT `canAccept`，该
信号只能作为最终 gate，不能被软件预检绕过。

**理由：** `LSQWrapper.scala` 同时要求 load queue 和 store queue 可接受，并预留
`LSQLdEnqWidth/LSQStEnqWidth`。只比较向量方向的 free count 会在边界状态下产生 DUT 不会接受的 launch，且
会破坏与标量 admission 共用的 pointer/count 对账。保守镜像只增加一个检查函数，不改变标量路径。

### D18. Monitor 先分域，再做 scalar normalization

**决策：** `partition_raw_event_domains()` 先按 `vector_ls`/来源和 redirect 标志把 raw event 分成 scalar、
vector、redirect 列表。redirect 先以 raw ROB key 做 oldest/覆盖仲裁；剩余 scalar event 才调用现有
`normalize_event_batch()`/`normalize_feedback_event()`，vector event 只调用向量专用 normalizer。

**理由：** 现有 scalar normalizer 要求 scalar target、active LQ/SQ mapping 和 issue epoch。vector writeback
与 SQ-only feedback 不满足这些前提，若晚分流会在 vector handler 之前被 drop/fatal。分域入口让标量列表和
处理顺序保持不变。

### D19. Issue route 采用一次性原子提交

**决策：** `route_all_vector_issue_queues()` 只消费 `enq_done` 的上升沿队列项。它先在局部列表预检 D 个
`{uid,dynamic_epoch,vuopIdx,replay_seq=0}`，确认 queue、driver pending 和 outstanding 中没有重复；全部通过后一次性追加，
再同步置各 uop 的 `issue_pending` 与 macro 的 `initial_issue_routed`。replay 也必须先检查相同身份是否已排队。

**理由：** service loop 可能在同一状态被多次调用；先改标志或先写部分 queue 都会产生重复/半组候选。一次性
预检和提交只维护向量队列，不触碰标量 scheduler。

### D20. Dequeue 以物理 entry token 为粒度

**决策：** 展开 LQ/SQ sideband 时，为每个物理 key 保存
`{domain,key,uid,vuopIdx}`。联合预检同时查询 scalar `uid_by_lq/sq`、vector per-entry range map、重复 key、
剩余数和 tombstone；全部通过后按 domain 删除 owner、递减对应 range，并统一推进 pointer/free count。

**理由：** 一个 vector UID 可以有多个 data-uop，每个 uop 又占多个 entry。UID-only 列表既无法知道应递减哪个
`vuopIdx`，也会误用 scalar 的“同 UID 重复”防护。联合预检还保证 LQ 通过而 SQ 失败时不会半提交。

### D21. 同拍 fault 优先于 replay

**决策：** 同一 service sample 的向量事件优先级固定为：已有/更老 redirect、vector fault、正常 writeback、
replay miss、success feedback。对同一 `{uid,dynamic_epoch,vuopIdx}`，fault+replay 取 fault 并丢弃 replay；正常 terminal
writeback+replay miss 属于矛盾协议，报告错误并冻结该 uop；`hit=1` 可与 writeback 共存，只记录确认。

**理由：** `exceptionVec` 是唯一明确的异常结果，不能被 port 收集顺序掩盖后重新发射。把矛盾组合报告出来比
猜测 DUT 内部时序更符合“只模拟可观测行为”的准则。

### D22. Tombstone 是新 allocation 的 key guard

**决策：** redirect 或正常回收写入的 ROB/LQ/SQ tombstone 在过期前视为暂时占用。vector admission 预览 key
时同时查询 active owner、pending token 和 tombstone；命中本 UID 旧 tombstone 时等待 flush/drain/过期，命中
其它 active owner 时报告重复，不能覆盖或立即复用。新实例重新 admission 后使用递增 `dynamic_epoch`。

**理由：** V2 store feedback 没有可靠 ROB 身份，且 writeback/feedback 可能跨一个或多个采样边界到达。tombstone
为旧动态实例提供最小保护窗口；把检查放在 allocation 前不会改变标量 map，也避免迟到事件误绑定新 vector 实例。

### D23. standalone writeback valid 与零活动 uop

**决策：** RTL 内部 `writebackVldu` 虽然是 `Decoupled`，但当前 standalone MemBlock 顶层交接和 UVM
`io_mem_to_ooo_vec_wb_agent_agent_interface` 只暴露 `valid/bits`，没有独立的 writeback `ready`。因此当前 monitor
在 `valid=1` 的采样拍发布一个 writeback event；不能等待或读取不存在的 ready。若未来顶层新增 ready，才把 event 边界
收紧为 `valid && ready`，并在未 fire 时保持 pending。另一方面，`VL=0`、`vm=0` 且 mask 全关、或某个末尾 data-uop
的内部 `flowMask=0`，不改变 `F`、LSQ range 或 uop 生命周期。VSplit/VMergeBuffer 仍可为该宏观 uop 产生一次零活动
writeback；框架按普通 valid writeback 收尾，不能依据内部活动数为零提前 terminal 或跳过 FOF 的后续屏障。

**理由：** 当前 standalone 交接没有 writeback backpressure 信号，`valid` 是测试框架可见的完成边界；把一个不可见的
ready 当成输入会让 monitor 永远无法完成。`F` 是保守 reservation 容量而不是活动元素数量，提前释放会破坏 LSQ owner
对账；保留正常宏观 writeback 路径可覆盖零活动场景而无需模拟每个 flow。

### D24. launch token 与 DUT-visible range 分离

**决策：** `enqLsq` driver 发出 valid 时先建立一个 `visible=0` 的 launch token。token 保存预测的起始指针、完整
F-entry key、enqueue pointer 的 before/after 边界和 `reserved_entries=F`，并对软件镜像做临时 reservation，避免
同一采样窗口重复使用 key。下一采样边界确认 DUT 已看到请求后，才 promotion 为 `visible=1` 的正式 vector range
owner；promotion 不重复扣减 pointer/free count。若 redirect 发生在 promotion 前，只删除 token：确认当前 enqueue
pointer 仍在 token 的 after 边界后回退到 before，并对当前 free count 加回该 token 自身的 `reserved_entries`；不回写
历史 free-count 快照，不写 range map、tombstone 或 cancel record。promotion 后才按真实 remaining entry 写 tombstone/cancel。

初版每次只 launch 一个 data-uop，并复用全局单深度 `pending_sample_valid`，所以全系统至多有一个
`visible=0` vector token；redirect coordinator 持有 writer gate 后先撤销该尾部 token，再独立扫描已 promotion 的
正式 range。前序 uop 的正式 owner 与当前 uop 的临时 token 不能通过一个合并的“是否可见”标志处理。

**理由：** `enqLsq` 没有顶层 ready/response，但 driver launch 与 DUT sample 仍是两个软件时序边界。显式区分这两个
阶段可以避免把尚未进入 DUT 的请求错误计入 LSQ cancel，同时保留对未来同拍/延迟采样的防重复保护。

取消 provisional token 不能把 token 建立时保存的 free-count 快照整体写回。该 helper 只能由持有 redirect_epoch
writer gate 的 coordinator 调用；gate 会先暂停同 domain 的 dequeue/foreign cancel/admission writer。`cancel_vector_launch_token()`
必须先校验当前 pointer==token.after；校验失败时报告 fatal/返回失败，token、pointer 和当前 free count 均保持不变，并停止
整个 redirect transition。只有校验成功才撤销 token 自身 delta、回退 enqueue pointer，并按当前 free count 加回 reservation。

### D25. 终态 helper 必须在 commit 与 dequeue 两侧重检

**决策：** 正常 `mark_vector_rob_commit()`、异常 `mark_vector_fault_rob_commit()`、真实 range dequeue 成功、
FOF tail writeback 都调用相应的幂等 terminal helper。helper 只在所有条件满足时写终态，重复调用不改变已经写入的
状态。这样无论 ROB commit 先于还是晚于 LSQ dequeue，都能在最后一个条件到达时完成 terminal。

**理由：** ROB commit 和 LSQ dequeue 是独立可见事件，不能假设固定先后。只在 dequeue 路径检查会遗漏“deq 已先完成、
之后 commit 再无其它事件”的情况。

### D26. replay 入队与 fault 清理采用单一原子边界

**决策：** full/partial replay handler 先验证当前 live outstanding、下一 replay 序号以及 queue/driver pending
中不存在重复，再追加 replay item；追加成功后一次性更新 `replay_pending/issue_pending/issue_accepted` 和
snapshot。顶层 feedback 没有 replay 序号，因此本地 `replay_seq` 只用于 queue item 去重/诊断，不用于识别迟到
feedback。fault handler 是 `issue_accepted` 清理的唯一写者，writeback 上层只负责把异常快照传给它，不先清同一字段。

**理由：** 先改 runtime 再入队可能在队列满或重复反馈时留下无法驱动的孤儿 pending；两个 handler 同时清 outstanding
则会掩盖状态错误。把状态更新收敛到单一成功边界可保持 queue membership 与 runtime 一致。

### D27. FOF 与 recovery 必须释放旧 issue 所有权

**决策：** 向量 scheduler 的普通 pending payload、issue queue item、`fof_send_reservation` 和
`active_fof_owner` 统一视为动态实例所有权，均带 `{uid,dynamic_epoch}`。redirect handler 在递增 epoch 前调用
`kill_vector_driver_pending(uid,dynamic_epoch)`；该 helper 同时删除匹配旧 epoch 的 queue item，并通过
`release_active_fof_owner(uid,dynamic_epoch)` 进行带键校验的 FOF owner 释放；FOF data-uop 的异常路径也先调用
该 helper，再按初版策略处理异常。helper 只清匹配旧 epoch，不清新实例状态；它不负责 LSQ range 回退，range
仍由 admission/redirect handler 管理。初版 FOF fault 没有可验证的中止协议，因此清理完成后直接报告 fatal 并停止
testcase；不会留下等待 tail 或 redirect 的悬挂 FOF owner。

**理由：** 普通 valid 在 ready=0 时会跨拍保持，删除 queue item 并不能自动删除 driver 已锁存 payload；FOF 的
原始 valid 直接进入 `VfofBuffer`，重复或迟到 tail/owner 会造成重复 enqueue 或永久阻塞。按 UID+epoch 做单一 kill
边界，并为已 fire 未写回的 tail 保留独立 tombstone，能在不改变标量 driver 语义的前提下保证旧动态实例不会继续驱动
或误更新新实例。

### D28. 规划期 flow 直接表达目标调用边界

**决策：** 本组向量 `flow 逻辑文档` 和 `flow 描述文档` 是后续 coding 的设计/plan，而非 coding 完成后的
现状总结。因此详细逻辑文档可以把规划新增或扩展后的 `vector_*()`、`*_handler()`、`*_helper()` 直接画为函数
调用节点，并用伪代码定义调用时序、输入、输出和状态副作用。已有源码函数名和源码位置继续保留，但用途是指出接入点、
复用边界和标量不受影响的范围，不要求它们覆盖每一个规划 helper。

**理由：** 这类文档的主要作用是让 coding 前的 review 能准确检验状态所有权、调用顺序与异常处理。若因为 helper
暂未落地而强制把它写成“某函数中的向量分支”，会丢失后续需要实现的 API 边界，也会使 lifecycle 图无法表达真实的
设计依赖。相反，文档明确标识“拟新增”即可区分当前状态和目标状态；它不是对当前源码实现情况的声明。

### D29. provisional token 只回滚自身 reservation

**决策：** `visible=0` token 只保存 `enq_pointer_before/after` 和 `reserved_entries`。建立 token 时从当前 free count
扣除该自身 delta；只有持有 redirect_epoch writer gate 的 coordinator 能取消它。取消时必须检查当前 enqueue pointer
仍位于该 token 的 after 边界，再回退到 before；free count 按当前值加回 `reserved_entries`，不把历史
`free_count_before/after` 写回共享模型。若 pointer 边界不匹配，说明存在未建模的后续 allocation，报告模型错误并保留现场。

**理由：** launch 到 sample 的窗口内，旧实例可能遇到 redirect。取消时 gate 会先暂停同 domain 的 dequeue、其它 cancel
和 admission writer；即使未来调整该范围，按当前值增减自身 delta 也不会覆盖无关状态，整体恢复历史计数则会造成后续
admission 看到错误的剩余容量。

### D30. 用显式合法组合表约束随机入口

**决策：** 主表先从唯一合法 `{op_class,v_form,v_mode}` 表中抽样，再回填 `fuType/fuOpType` 并计算 D/F；候选表
为空时报配置错误。当前只支持普通 load/store 的四种 mode、whole-register 的 unit-stride、mask load 的
unit-stride 和 FOF load 的 unit-stride。

**理由：** form 和 mode 并非正交。独立抽样会生成 store FOF、store mask-load 或 whole-register indexed 等无法由
当前 payload/RTL 解释的组合；在源头过滤比事后修补 D/F 更简单可靠。

### D31. replay 只依据可观测 outstanding 协议

**决策：** V2 顶层 store feedback 不携带 issue/replay 序号，因此 `hit=0` 的接受条件固定为当前 uop
`issue_accepted=1 && !replay_pending && !terminal`。条件不满足时，命中旧 redirect tombstone 的事件直接丢弃；其余
事件报告协议错误，不用本地 `replay_seq` 推断来源。成功接受后才创建下一 replay item 并递增本地计数。

**理由：** 本地序号只能标记 framework 自己创建的 queue item，不能证明 DUT output 属于哪一次尝试。收敛为“一次
outstanding 一次反馈”的协议前提，避免错误过滤新尝试或把旧反馈投给新实例。

### D32. fault terminal 清除 pending、保留 fault 诊断

**决策：** vector fault terminal helper 在确认 tagged fault-head commit、真实 range deq 和 owner 清空后，先清
公共 `exception_pending`，保留 `fault=1` 与异常快照，再写 `success=0、terminal_done=1` 并回收。该规则只适用于
D=1、非 FOF 专用 fault 模板。

**理由：** `exception_pending` 表示“异常仍等待 commit/deq 收尾”，不能在 terminal 后继续为 1；`fault` 和快照则是
最终结果，必须保留供检查和 debug。

### D33. cancel record 应用完成是 re-admission 的必要条件

**决策：** redirect handler 为正式 range 产生非零贡献后，将当前 redirect 的**共享 aggregate cancel record**引用
保存到 `redirect_cancel_record_ref`；多个 vector UID 可以保存相同引用。activation/re-admission 除了检查旧 owner、
active map 和 tombstone，还必须确认该 record 已由 redirect gate owner 的
`apply_guarded_lsq_cancel_record()` 标记 `software_applied=1`；没有正式未释放 range 时引用为 invalid，可直接跳过该条件。

**理由：** tombstone 只保护旧事件，不代表共享 LQ/SQ pointer/free count 已完成回退。先等待完整 aggregate 的软件
回退再重分配，才能避免新实例在旧 reservation 尚未归还时产生容量或 key 冲突。

### D34. tail-shaped writeback 不能落入普通 data-uop 路径

**决策：** `writeback_lane=1 && vlWen=1 && vecWen=0 && v0Wen=0` 先定义 FOF tail shape，`exceptionVec` 不参与
shape 判定。tail-shaped event 先查完整 `rob_key` 的 tail tombstone，再尝试 live tail match；两者都不命中时只报告并
丢弃，绝不使用接口占位 `payloadVuopIdx=0` 索引 `uop[0]`。正常 tail writeback 先调用
`release_active_fof_owner(uid,dynamic_epoch)`；只有 keyed release 返回成功后，才写
`fof_tail_written_back=1/fof_tail_pending=0` 并重检 terminal。tail exception 则先 keyed kill、置 canceled 后 fatal。

**理由：** FOF tail 不具有可靠的 data-uop 数组身份，而顶层 output 也不携带 dynamic epoch。把 tail 回落为普通
data-uop 会污染新实例或错误结束 `uop[0]`；以完整 ROB key、tail shape 和 owner release 形成唯一闭环，状态更少且
可由顶层可见字段检查。

### D35. re-admission 必须原子复位公共状态

**决策：** redirect transition 只递增一次 `dynamic_epoch`。旧 owner、ready item、tombstone 和非零 cancel record
均满足清理门控后，新的 activation 使用该新 epoch，并原子设置 `active=1`，清除
`flushed/redirect_pending/enq/issue_ready/success/rob_commit/lsq_deq/terminal_done/fault/exception_pending/issue_killed`，
同时将 `redirect_old_epoch_valid=0`、旧 epoch 快照和 `redirect_cancel_record_ref` 置为 invalid，清 vector runtime 的
fault、replay、pending、issue-killed 镜像与 route-once 状态；随后才建立新的 `enq_pending` uop[]。

**理由：** 向量和标量共享 admission/commit prefix。仅重建向量私有 runtime 会遗留旧公共状态，使同 UID 的新实例被
错误当作 flushed、已入队或异常待提交。显式原子重置只作用于已完成旧实例清理的同一 UID，不改变任何标量规则。

### D36. issue-kill 是旧实例的统一停止门

**决策：** `status_by_uid[uid].issue_killed` 是旧动态实例禁止继续发射和正常收尾的公共真源；向量 issue candidate、
`mark_vector_issue_fire()` 的 fire 前复核、正常 data-uop writeback 和 store feedback 都必须检查该位。runtime 中的
`macro.issue_killed` 只作镜像。命中 kill 的残留 item/payload 由 keyed kill 删除或丢弃；正常 writeback 不得置
`terminal`、清 outstanding 或推进 FOF cursor，除非它命中已登记的 redirect tombstone 并按旧事件丢弃。新的
re-admission 在原子 activation reset 中同时清公共位和 runtime 镜像。

**理由：** redirect/fault 清理与 issue 选择可能跨 sample 边界，单靠删除 queue item 不能覆盖已锁存 payload 或同拍
竞态。统一门控能阻止旧 epoch 再 fire，同时不改变 scalar scheduler。

### D37. 完整 ROB key 与唯一 epoch 真源

**决策：** 所有 active ROB map 访问先将 `rob_key={flag,value}` 传给
`rob_order_util::rob_to_map_key()`；文档中的 `robIdx` 仅表示 DUT 字段，不可直接作为 map key。动态实例的可变
`dynamic_epoch` 只由公共 `status_by_uid[uid]` 在 redirect transition 中递增一次；vector runtime、queue item、token
和 tombstone 只能保存快照或镜像，不能自行递增/覆盖公共值。re-admission 读取公共新 epoch 后再建立 runtime。

**理由：** ROB wrap 和同 UID re-admission 同时存在时，裸 value 或多处递增会把旧事件绑定到新实例。把转换和递增收敛
到公共 API 可与 scalar active map 共存，并让所有向量 flow 使用同一身份规则。

### D38. provisional token 批量取消的原子边界

**决策：** 初版将“一个 macro 一次一个 data-uop”收紧为复用全局单深度 `pending_sample_valid`：任一 vector
`visible=0` token 在 promotion/cancel 前，整个 LSQ dispatcher 不再 launch 任意 scalar/vector allocation。因此全系统
最多一个 vector provisional token，且它必定位于对应 enqueue pointer 尾部。

redirect 的串行 owner 是 `redirect_epoch`，不是 UID。`domain_mask` 由 token 和所有将由 scalar/vector 正式 owner
计入 aggregate record 的 LQ/SQ domain 联合派生，不能只看 token。`run_redirect_lsq_transition()` 先确认
`redirect_lsq_sample_seq` 及更早的 raw deq batch 已完成联合资源提交；这些 batch 只更新实际 owner/remaining/pointer/free
count，不允许让 redirect 覆盖 UID terminal/recycle。随后才以 `{redirect_epoch,domain_mask}` 取得 LQ/SQ writer gate，
在 gate 内对 token 做 after/before 链、current pointer 和 owner 的整体预检；成功后取消 token、扫描全部 scalar/vector
覆盖 UID、汇总同一个 aggregate cancel record、应用完整 software rollback、提交 redirect status，最后释放 gate。gate
期间同 domain 的 admission/reservation、dequeue commit 和 foreign cancel apply 均保留 raw batch 并延期；联合 LQ/SQ
batch 整体延期。缓存 deq 必须晚于上述资源边界，释放 gate 后先按 capture provenance 对每个完整 domain 分类：整侧
matching redirect tombstone 允许 `STALE_DROP`，不推进资源；live/tombstone 混合、空 owner 或身份不匹配才报告时序
mismatch，不能再次释放。gate 不可取得、存在更早 foreign pending record 或资源排空未完成时返回 DEFER，
保留 active redirect/freeze；只有 token/owner/pointer 预检不一致才 fatal。

这个 writer-gate transaction 只在 `vector_involved=1` 时建立。若当前 redirect 覆盖范围内没有 active vector macro、
也没有旧 epoch 的 `visible=0` vector token，则必须完整保留既有 scalar-only
`apply_redirect_flush_range() -> prepare_uid_for_redirect_reissue() -> apply_pending_lsq_cancels()` 快路径；不创建
transition plan、不取 gate、不执行 vector token/provenance 预检。这样新增的向量串行边界不改变纯标量 redirect 的时序。

未来多 slot 不能仅按每个 macro 局部逆序取消。必须先建立覆盖 scalar/vector 的统一 allocation ledger，按每个 domain 的
全局逆 allocation 顺序预检和回退；在该 ledger 完成前，不允许同时存在多个 `visible=0` vector token。

**理由：** `cancel_lq/sq()` 同时改 enqueue pointer 与 free count，而现有 `cancel_record_q` 是一个 redirect 的聚合账本。
若先按单 UID 取消、或让 `apply_pending_lsq_cancels()` 在 aggregate finalized 前扫描，后续 scalar/vector 计数会遗漏且
pointer 顺序会失真。全局单深度边界是对现有 scalar dispatcher 的最小复用；redirect_epoch gate 只在 recovery 的短暂
资源事务内暂停 writer，不改变 scalar UID、queue 或 reissue 语义。

### D39. Redirect 必须清理旧 vector fault 状态

**决策：** 向量 D=1 direct-fault 已记录 `vector_fault_pending_q`（或等价 per-macro pending record）但尚未到 ROB head，或已经登记
`fault_head_waiting={kind=VECTOR, uid, dynamic_epoch}` 后，只要收到覆盖该实例的真实 redirect，
`vector_redirect_reissue_handler()` 都必须先调用 `cancel_vector_fault_head(uid, old_dynamic_epoch)`。该 helper
始终先删除匹配 UID/旧 epoch 的 pending fault record；随后仅在 `fault_head_waiting`、UID、旧 epoch 和
`kind=VECTOR` 全部匹配时清除 `fault_head_waiting`、`fault_head_uid`、`fault_head_dynamic_epoch`、对应的
`latched_is_store_exception`，并把 `fault_head_kind` 回填为 NONE。没有匹配 shared token 时 pending-record 删除仍
生效；若共享 token 属于 scalar 或其它 UID/epoch 则保留原 token，并交由下一次 commit service 重新选择当前 head。
它绝不能清除其它类别或其它 epoch 的 fault-head。

取消 fault-head 只解除旧异常 token 对 commit cursor 的阻塞，不把旧 UID 标记为 terminal，也不跳过 redirect 的
tombstone、range cancel 和同 UID re-admission。随后 `clear_uid_dispatch_result(uid)` 清除旧公共
`exception_pending`，新的 activation 还必须确认同一 `{kind=VECTOR,uid,old_epoch}` token 已不存在，才按既定规则
原子复位 fault/issue-kill 等状态。

**理由：** `fault_head_waiting` 是共享的单 token 状态，普通 runtime 清理和 active ROB map 删除不会自动清除它；
`vector_fault_pending_q` 同样会在 fault-head 建立前保留旧异常。若 redirect 只清已建立 token，早到的 redirect 会让
旧 pending record 在 re-admission 后继续被选择；若只清 queue 又不清匹配 token，公共 cursor 仍可能被阻塞。带
UID+epoch+kind 的两阶段取消边界可保持标量 fault 路径不变，并与已有 `sync_modeled_head_after_fault_terminal()` 的
旧实例检查保持一致。

### D40. VECTOR fault-head 不把 issue-kill 当作 redirect

**决策：** `vector_fault_handler()` 对 D=1 direct-fault 调用 `kill_vector_driver_pending()` 后，公共
`status.issue_killed=1` 用于停止所有旧 queue/pending/FOF 发送路径，正常 writeback 也继续受此门控。但后续
`select_vector_fault_head_candidate()` 允许这个已登记 `fault_pending=1` 的实例进入异常提交；扩展后的
`sync_modeled_head_after_fault_terminal()` 必须按 `fault_head_kind` 分支：

```text
kind=SCALAR：保留现有 issue_killed => stale/cancel 规则。

kind=VECTOR：issue_killed 仅表示已停止 issue，不能单独清 fault-head。
  epoch 不匹配、flushed/redirect_pending、active ROB owner 已被 redirect 失效，或 keyed redirect cancel：旧实例取消；
  terminal_done=1 && lsq_deq=1 && success=0 && fault=1：正常 fault terminal，清 token 并推进 cursor；
  其它状态：保留 token，等待真实 deq/terminal，不能凭 issue_killed 越过异常 UID。
```

最小时序例子：data-uop fire 后收到 `exceptionVec`，fault handler 先置 `issue_killed=1` 与 `fault_pending=1`；
ROB head 到达后建立 `kind=VECTOR` fault token；即使此时尚未观察到 LQ/SQ dequeue，sync 也必须保持 token 和
cursor。只有随后真实 deq 清空唯一 range、fault terminal 写入 `success=0/terminal_done=1` 后，才解除 token 并推进。

**理由：** 标量 `sync_modeled_head_after_fault_terminal()` 当前将 `issue_killed` 解释为 redirect 已杀掉旧 fault
实例。向量 D=1 direct-fault 则在没有 redirect 时也必须置同一公共位，防止迟到 issue/writeback 继续改变状态；若不
按 kind 区分，异常 commit 后的首次 sync 会立即清掉 vector fault-head，公共 cursor 可能在唯一 range 尚未 deq 时前进。
使用 tagged sync 保持已有 scalar 语义，同时只为 vector fault-head 增加必要分支。

### D41. redirect aggregate cancel record 必须在 writer gate 内一次应用

**决策：** 一次真实 redirect 只拥有一个公共 aggregate cancel record；scalar 和全部被覆盖 vector UID 的实际
`lq_count/sq_count` 都在公共 redirect scan 中累加到该 record。vector runtime 的
`redirect_cancel_record_ref` 只是指向这个 shared record，允许多个 UID 持有相同引用，不得把它解释为“一 UID 一 record”。

上述 aggregate/gate 规则仅适用于 `vector_involved=1` 的 mixed/vector redirect。`vector_involved=0` 时不把既有 scalar
record 改造成 vector aggregate，也不以 `apply_guarded_lsq_cancel_record()` 取代现有 `apply_pending_lsq_cancels()`；纯标量的
record 顺序、queue 和 apply 时机保持原样。

`run_redirect_lsq_transition()` 在 record `software_count_finalized=1` 后、释放 `redirect_epoch` writer gate 前，通过
`apply_guarded_lsq_cancel_record()` 只应用这一个指定 record 并置 `software_applied=1`。通用
`apply_pending_lsq_cancels()` 在 gate 期间不得遍历/应用 foreign record；任何触及被 gate domain 的 scalar/vector
admission、dequeue 或 cancel raw batch 都暂存，联合 LQ/SQ batch 不允许拆开。开始 gate 前必须先排空
`redirect_lsq_sample_seq` 及更早的 deq，因此被暂存的 deq 只能是更晚 sample；gate 释放后先按 capture provenance 对
每个 LQ/SQ domain 分类：整侧全部 live owner 才进入普通预检；逐 key 全部命中当前 redirect、且每个旧 UID 属于
`covered_uid_set` 的 matching tombstone 则 `STALE_DROP`，不推进 pointer/free count；同一 domain 可以跨多个 covered UID。
mixed live/tombstone、空 owner 或 epoch/cutoff 不匹配仍 fatal。只有 aggregate software rollback 成功后，
才提交 vector 的 active-map/status/epoch 更新并释放 gate；`apply_redirect_flush()` 随后才清全局 freeze。

**理由：** 现有 `apply_pending_lsq_cancels()` 会逐 record 调用 `lsq_ctrl.cancel_lq/sq()`，后者直接改 enqueue pointer
和 free count。若单个 vector callback 先调用它，当前 record 尚未收齐其它 UID 的 count 就会被标为 applied；若 foreign
record 同时写同一 domain，则 token 的 after 边界和 aggregate rollback 都可能失真。把 apply 收敛到 redirect 级 owner，
只为资源写者增加短暂 gate，既复用 scalar 的计数/对账逻辑，也不改变标量的生成、issue 或 reissue 规则。

### D42. redirect 先排空已采样 deq，再统计剩余 cancel

**决策：** 每个 redirect 的 resource transaction 以既有 cancel record 的 `redirect_lsq_sample_seq` 为 cut line。
在 `run_redirect_lsq_transition()` 取得 writer gate 前，所有 `sample_seq <= cut line` 的完整 raw LQ/SQ dequeue batch
必须先按现有“联合预检后一次提交”规则更新 owner、`range_remaining_entries`、dequeue pointer 和 free count。若 batch
尚未排空，coordinator 只保持 redirect freeze/plan 并返回 `DEFER_RESOURCE_DRAIN`；它不取消 token、不删除 range owner、
不累计 cancel、也不更新 vector lifecycle。redirect plan 必须在 drain 前保存 `covered_uid_set`，因为此时尚未写入
`flushed/redirect_pending`。对该集合中的 scalar/vector UID，deq 只允许资源更新，不能触发 normal/fault terminal、
scalar retire、terminal prefix 或 recycle；全局 fault-head sync 对整个 drain batch 延后至 redirect public state 提交后统一重检，
不能被同批非覆盖 UID 的局部 deq 提前触发。排空后重新读取 owner/domain，cancel record 仅统计仍然未释放的 entry。

writer gate 内遇到的 raw deq batch 仍需整体缓存，但它们必须晚于 cut line，并携带 capture 时冻结的
`{capture_order,sample_seq,lq_keys[],sq_keys[]}`。gate 释放后按原顺序先做 provenance 分类：某一完整 domain 的所有
key 都逐项命中本 redirect 的 matching tombstone（各 UID 可不同但都在 covered set）时是合法 `STALE_DROP`，只消费该侧 raw，不推进 pointer/free count；只有
mixed live/tombstone、空 owner、其它 redirect tombstone 或 epoch/cutoff/owner 不匹配才是 DUT/monitor 时序错误，整批报告
mismatch，绝不能逐 key 静默丢弃或再次增加 free count。若 LQ/SQ 一侧 stale、另一侧 live，剔除 stale 侧后仅提交 live
侧；两侧都 live 仍按原联合预检，不能把分类后的过滤误解为普通事务的部分提交。

**理由：** 若先在 gate 内删除 range owner 并把 `range_remaining_entries` 全量记入 cancel，再重放一个已经由 DUT
采样的旧 deq，软件一方面已通过 cancel 释放 entry，另一方面又会因 provenance 不明而无法区分合法 stale 和真正的
pointer 漂移。逐 key 静默丢弃会隐藏 free-count/pointer 错误，而把合法 stale 一律 fatal 又会把 DUT 已采样的旧资源误判为
协议错误。利用当前标量 flow 已有的“先处理 deferred ctrl/deq，再进入 exception/redirect recovery”顺序，增加按 domain
的完整 tombstone 分类和 effective batch，不引入按 entry 的新释放账本，也不改变标量随机、issue 或普通 cancel 语义。

### D43. resource drain 必须使用 capture 时的 sample 序号

**决策：** 每个含 `lqDeq` 或 `sqDeq` 的 `dispatch_raw_ctrl_t` 都必须携带 monitor capture 时由
`wait_for_l2tlb_sample_anchor()` 取得的不可变 provenance：至少包括非零 `sample_seq`、capture 顺序和已经展开的
`lq_keys[]/sq_keys[]`；V2 count-only SQ 还要保存 capture 时的 `sq_deq_ptr` 快照。若不直接扩展既有 struct，则
`deferred_raw_ctrl_q` 必须以等价 envelope 保存 `{raw_ctrl, capture_order, sample_seq, lq_keys[], sq_keys[],
sq_deq_ptr_at_capture}`。从 raw queue 移到 deferred queue、以及之后的任意重试，都只能携带原始序号和 key 快照。
`cycle=$time` 仅保留诊断用途，绝不能与 `redirect_lsq_sample_seq` 混用；缺失或为 0 的 deq sample/key provenance 属于
模型错误，资源排空检查必须 fatal，而不是按当前 service sample 或当前 SQ head 猜测。

LQ raw pointer 在当前接口表示 deq 后的 next pointer，因此 `lq_keys[]` 必须复用现有
`lq_deq_start_key(raw_lq_ptr,count,ptr_is_next=1)` 先还原起点后展开，不能把 raw pointer 本身误当作第一个被释放 key。

**理由：** `redirect_lsq_sample_seq` 是由 DUT sample anchor 和固定延迟派生的序号，而 `$time` 是仿真时间单位。
两者没有可证明的大小关系。若 deferred raw 在消费时再用当前 sample 打标，一个原本应在 cut line 以前先结算的 deq
会被误当成 gate 后 batch，随后在 range 已 cancel 后命中 tombstone/空 owner。保存 capture provenance 是 D42 能够
稳定判断资源先后的最小新增状态，不改变标量 deq 的 owner、pointer 或 free-count 规则。

### D44. gate 后 deferred deq 的完整 domain 分类

**决策：** writer gate 释放后，缓存的 raw dequeue 不直接复用普通 owner 预检，而是按 capture 时冻结的物理 key 对 LQ、SQ
分别做 provenance 分类。每个非空 domain 只有两种合法结果：

```text
LIVE_COMMIT：该 domain 的全部 key 都命中唯一 live scalar/vector owner。
STALE_DROP：该 domain 的全部 key 都没有 live owner，且每个 key 都命中当前 redirect 的 matching tombstone：
             redirect_epoch/cut line/domain 相同；该 key 自己的 old_uid 属于 covered_uid_set，
             old_dynamic_epoch 与该 key 的旧 owner 快照一致。各 key 的 UID/epoch 可以不同。
```

`STALE_DROP` 只消费该侧 raw sideband，不推进该侧 dequeue pointer/free count，不删除 owner、不递减 vector range，也不触发
terminal、fault-head、terminal prefix 或 recycle。LQ/SQ 同一 raw 中一侧 stale、另一侧 live 时，先剔除完整 stale domain，
再仅对 live domain 形成 effective batch；两侧都 stale 时只消费 envelope；两侧都 live 时继续原有联合预检/提交。
这不是普通事务允许部分提交，而是 redirect cancel 已完成后的 provenance 分类边界。

V2 count-only SQ 的 `STALE_DROP` 不推进真实 `sq_deq_ptr`。若后续缓存 SQ envelope 被分类为 `LIVE_COMMIT`，其第一个
冻结 key 必须仍与真实 SQ head 相等；不相等说明 shadow capture cursor 已不能与真实资源状态收敛，初版直接 fatal，不能以
shadow cursor 覆盖真实 pointer 或用重放时当前 head 重新推导旧 key。

同一 domain 出现 live owner 与 tombstone 混合、空 owner、success tombstone、其它 redirect epoch/cut line 或 owner 身份
不匹配，都必须报告 fatal；不能逐 key 静默 drop，也不能把 stale key 再计入 cancel。redirect-deq tombstone 至少保留到
覆盖它的 gate-owned deferred FIFO 段全部分类/消费且达到既有 output-drain 过期边界，之后才允许删除 tombstone 或复用物理 key。
在此之前，它还是共享 physical-key quarantine：所有 scalar/vector allocation 的共用 key 预检都必须拒绝命中的 key，
保持 cursor/pointer/free count，不得因 cancel 已加回 free count 而覆盖旧 key。该 quarantine 仅由
`vector_involved=1` 的 mixed/vector redirect 建立，不改变 pure-scalar fast path。

**理由：** redirect 的 aggregate cancel 已经回退被取消 owner；gate 期间 DUT 仍可能产生一个此前已采样、但直到 gate 释放
才被软件观察到的 deq。完整 domain tombstone 可证明这是同一旧实例的 stale 事实，避免双重释放；同时对 mixed/unknown 情况
保持 fatal，避免把真实 pointer 漂移伪装成正常迟到事件。按 domain 而非逐 key 过滤还保留了 LQ/SQ 联合 raw 的原子语义，
并允许一侧旧资源 stale、另一侧新 live 资源仍正确完成提交。

## 5. 后续 review 关注点

1. range map 是否在每个 entry deq/cancel 时恰好删除一次。
2. vector event 是否始终经完整 `rob_key` 或 range owner 反查，绝不扫描主表。
3. FOF tail 是否仅在所有 data-uop terminal 后发送、满足 pending/issued/written_back/canceled 门控，且同一时刻至多一个活动 FOF。
4. vector store 是否保持 `scommit=0`，而仍通过实际 deq 关闭 range。
5. redirect/cancel 是否不影响标量 queue、标量 status 或 scalar reissue 规则。
6. 新增 plus 是否只控制 runtime 行为，并按 `plus.sv -> seq_csr_common -> default.cfg` 规范实现。
7. redirect re-admission 是否保留同 UID、清除旧 range、等待 tombstone 排空后再复用 key。
8. vector terminal 是否显式写 success，且不调用 scalar required-target 检查。
9. fault 是否只走 fault-head，redirect 是否只由真实 redirect 驱动，二者没有被错误合并。
10. 初版 direct-fault testcase 是否满足 D=1、非 FOF 和专用模板约束。
11. 当前 standalone writeback 是否按 `valid` 采样，`VL=0`/全 mask-off 是否仍等待正常宏观 writeback；若未来新增 ready，是否同步收紧为 fire。
12. commit、dequeue、FOF tail 和 fault commit 是否都触发幂等终态重检。
13. replay 是否先完成唯一性预检和 queue 入队，再更新 runtime pending 状态；fault 是否由单一 handler 清理 outstanding。
14. admission redirect 是否区分 `visible=0` token 与 `visible=1` range，并只对后者计入 cancel。
15. FOF/redirect 是否按旧 UID+epoch 清除 driver pending、send reservation 和 active FOF owner；FOF fault 是否清理后明确 fatal。
16. issue candidate、fire 和正常 writeback 是否都受公共 `status.issue_killed`/`fault_pending` 门控，旧 item 不再 fire 或 terminal。
17. active map 是否始终使用完整 `rob_key` 的规范化 key，且只有公共 status 更新边界递增 `dynamic_epoch`；runtime 只作镜像。
18. 多 provisional token 是否先整体预检再逆序取消，任何边界失败都不发生部分回退。
19. D=1 VECTOR fault-head 是否在 `issue_killed=1` 时仍等待真实 deq/terminal；只有 tagged redirect stale 或
    vector fault terminal 才能解除对应 token，不能套用 scalar 的 issue-kill cancel 规则。
20. re-admission 是否同时确认旧 `{kind=VECTOR,uid,old_epoch}` fault-head 已清除；不能只检查 FOF owner 或 tombstone。
21. redirect 是否复用全局单深度 pending-sample，使 `visible=0` vector token 保持在 enqueue 尾部；未实现统一 allocation ledger 时不得开启 multi-slot。
22. redirect_epoch writer gate 是否覆盖 aggregate cancel record 的 finalize/apply，且 gate 期间 scalar/vector admission、dequeue、foreign cancel 都只缓存原 batch。
23. 多个 vector UID 是否允许引用同一个 redirect aggregate cancel record，并只在该 record `software_applied=1` 后 re-admission。
24. redirect 是否先排空 `redirect_lsq_sample_seq` 及更早 deq；该阶段是否只更新资源而不让覆盖 UID terminal，gate 后 deq
    是否先完成 provenance 分类再进入有效 live batch 的 owner 预检。
25. gate 后 deferred raw deq 是否先按 capture provenance 对 LQ/SQ 整侧分类；matching tombstone 是否只产生
    `STALE_DROP`，且不推进 pointer/free count；V2 SQ 是否使用 capture 时冻结的 key，而不是重放时当前 `sq_deq_ptr`。
26. raw ctrl/deferred deq 是否携带 capture 时的不可变 `sample_seq`，并且没有以 `$time` 或当前消费 sample 替代。

## 6. 多轮 review 记录与最终结论

本轮 flow 文档经过多轮独立 subagent review，并在每轮发现问题后回到对应文档修正：

1. 首轮 review 发现 terminal 判定可能遗漏 commit/dequeue 先后关系、writeback 被错误当作带 ready、FOF tail
   的识别和 redirect/replay 分流边界不够明确；已补充 valid-only writeback、FOF tail match、幂等 terminal helper
   和 fault/redirect 分离。
2. 第二轮 review 发现需求文档仍把 launch 直接视为正式 range、replay 先改 pending 再入队；已统一改为
   `visible=0` provisional token -> sample/promotion，以及“预检 -> queue append -> runtime 原子更新”。
3. 第三轮 review 发现 redirect 对 `visible=0` token 的 cancel record 记账不严谨，且多 uop 场景可能同时存在
   前序正式 range 和当前 provisional token；已改为先逐 token 撤销 provisional reservation，再独立统计正式 owner，
   仅对实际未释放 entry 写 cancel record。
4. 后续 review 发现 commit flow 图的顺序与真实 `send_lsqcommit_cycle()` 不一致，以及 launch token 的字段/术语
   未在需求和各 flow 首章完整落点；已改为“构造 transaction -> `start_item/finish_item` -> mark commit”，并补齐
   `launch_token`、`promotion`、`provisional reservation` 和状态快照定义。
5. 最终独立复核发现 provisional token 取消的 pointer-mismatch 语义仍可能被读成“先修改计数再检查边界”；已统一为
   “先校验 pointer，失败时 token/pointer/free count 原样保留并停止该 UID transition，成功后才回退 pointer、加回自身
   reservation、删除 token”，并同步到需求、admission、monitor/recovery、commit/dequeue 和生命周期摘要。
6. 复核发现 D=1 vector fault 已登记公共 `fault_head_waiting` 后若被 redirect 覆盖，单纯清理 vector runtime 会遗留
   共享 fault token 并阻塞 commit cursor；进一步确认 redirect 也可能早于 fault-head commit，此时旧 pending-fault
   record 仍会残留。已增加 `cancel_vector_fault_head(uid,old_epoch)` 的 keyed 两阶段清理：总是删除匹配的 pending
   record，仅在 shared token 同时匹配 kind/UID/epoch 时清 token，并同步到需求文档、monitor/recovery、commit/dequeue
   和生命周期摘要；不影响 scalar/其它 epoch。
7. 随后复核现有 scalar fault sync 发现其把 `issue_killed` 直接解释为 redirect 旧实例；而 D=1 vector fault 也会为
   停止旧 issue 置该公共位。已增加 `fault_head_kind` 分支：VECTOR token 仅在 redirect/epoch stale 或真实
   fault terminal 后解除，不能因 `issue_killed=1` 在真实 deq 前提前放行 commit cursor；scalar 规则保持不变。
8. 最后一轮复核补充了旧 issue 对 store feedback 的同样门控，并明确 `status.rob_commit=0` 是 direct-fault 等待提交时的
   正常状态，不能单独触发 fault-head 清理；同时将 provisional token 的整体预检置于所有 redirect 清理动作之前，避免
   fault-head、issue owner 与 pointer 回退出现部分提交。
9. 最后一轮交叉检查补充了 re-admission 对旧 `{kind=VECTOR,uid,old_epoch}` fault-head token 的存在性门控，并修正
   需求 activation 伪代码中的 ROB map 规范化写法；四份 flow、生命周期摘要和决策记录的 token/epoch/ROB key 表述已
   一致，Markdown fence、链接和空白检查通过。
10. 本轮复核发现 gate 内仅缓存 raw deq、随后删除 range owner 的描述缺少资源顺序边界；已增加 D42 的
   `redirect_lsq_sample_seq` resource drain fence：cut line 以前 deq 先联合结算且抑制覆盖 UID 的 terminal，gate 后
   batch 进入独立 provenance 分类。matching redirect tombstone 的完整 domain 可 `STALE_DROP`，mixed/空 owner/身份不符
   仍 fatal；该修正避免 deq/cancel 双重释放，同时保留标量现有 deferred ctrl/deq -> redirect recovery 的调用顺序。
11. 随后源码交叉检查发现当前 `dispatch_raw_ctrl_t` 只保存 `cycle=$time`，没有可与
    `redirect_lsq_sample_seq` 比较的 deq sample provenance。已增加 D43：后续实现必须固化 capture 时的
    `sample_seq` 到 raw ctrl 或等价 envelope，deferred 重试不得重新打标；这避免资源排空栅栏混用时间戳和 sample 序号。
12. 进一步复核发现仅保存 `sample_seq` 仍不足以重放 V2 count-only SQ：gate 期间当前 `sq_deq_ptr` 可能已因其它事件
    改变。已增加 D44，要求在 capture 时冻结 LQ/SQ physical key，并按完整 domain 将缓存 batch 分类为 `LIVE_COMMIT` 或
    matching-tombstone `STALE_DROP`；一侧 stale、一侧 live 时只提交 live 侧，不能逐 key 静默丢弃。
