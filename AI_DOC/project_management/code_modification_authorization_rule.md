# 代码修改授权规则

本文约束本项目中所有会改变实现、测试行为或构建结果的文件修改。目的是真正区分“分析/方案阶段”和“coding 阶段”，避免仅因 Codex 自行推断出解决方案而提前修改代码。

执行本规则时，还必须遵循：

- `AI_DOC/project_management/ai_doc_language_rule.md`
- 与目标模块对应的 agent、参数、sequence、plan 执行或 RTL 规则。

## 1. 代码修改的范围

本文中的“代码修改”包括但不限于：

- RTL、Scala/Chisel、SystemVerilog/UVM、C/C++、Python、Shell 等源码或测试源码。
- testcase、sequence、driver、monitor、transaction/xaction、interface、reference model、scoreboard、脚本。
- Makefile、filelist、编译宏、`.cfg`、`.svh`、`plus` 参数、连接文件及其他会影响编译、运行或测试行为的配置。
- 直接修改生成 RTL、自动生成脚本的输入或会改变生成结果的文件。

`AI_DOC`、`AGENTS.md`、分析、草案、plan、flow、review 等说明性文档不是代码修改；但只有用户明确要求创建、修改或同步文档时，才可以修改这些文档。

## 2. 唯一授权条件

只有用户在当前任务中明确表达以下任一类意图后，才可以开始代码修改：

1. 明确要求“开始代码修改”“开始改代码”“开始 coding”“可以修改代码”或语义等价且对象明确为代码的表达。
2. 明确要求“按照/执行某个 plan 修改代码”“按 plan coding”“执行 plan 实现代码”，并给出 plan 路径、明确 plan 名称或无歧义地指向当前已确认 plan。
3. 明确要求实现、修复、新增或删除某项**代码**，例如“修复这个函数的代码”或“现在实现该 plan 中的源码修改”。

已有草案、已有 plan、此前讨论过的实现方向、用户说“无问题”“继续”“最小改动”或 Codex 自行判断“应该实现”，均不构成代码修改授权。

授权不因一次分析、一次文档修改或已有 plan 自动生效到后续独立任务。只有同一项尚未结束且已明确进入 coding 的任务，用户后续无歧义的“继续”才可延续该 coding 授权；一旦任务切换为分析、方案、文档或 review，必须重新获得明确代码修改授权。

## 3. 默认只读任务

以下请求默认只允许读取代码、日志、波形、配置和文档，并输出结论、风险、草案或建议；不得修改代码：

- “分析”“解释”“检查”“定位”“比较”“结合现有框架分析”。
- “给方案”“写草稿”“修改方案”“完善 plan”“写入文档”“修改 flow/review/analysis”。
- “review”“评审”“给出问题”“确认理解”“继续讨论”。
- 用户只要求运行只读检索、查看 diff、查看日志或报告状态。

在默认只读任务中，可以写出建议的函数名、伪代码、文件清单或未来修改点，但不得对这些文件应用 patch、格式化、批量替换、生成或其他写操作。

## 4. 开始 coding 前的强制确认

收到明确代码修改授权后，在第一次修改代码前必须：

1. 在工作进展消息中说明已收到的明确授权，以及本轮准备修改的代码范围。
2. 运行 `git status --short`，识别用户已有修改；不得擅自回滚、覆盖、暂存或提交无关内容。
3. 如果用户要求按 plan 执行，先读取对应 plan 和 `AI_DOC/project_management/mem_ut_test_framework_plan_execution_rule.md`（适用时），确认 plan 已可执行。
4. 明确本轮代码范围、相关配置/文档同步范围和验证范围；只在该范围内修改。

编译、仿真、查看波形、阅读源码、生成方案或运行静态检查不构成代码修改授权，也不能在其间自动转入 coding。

## 5. coding 范围控制

获得授权后，仍只能修改用户明确授权或已确认 plan 覆盖的范围。

- 不得因为“顺手优化”“名称更准确”“历史文档不一致”或“看起来应当一起修改”而扩展到未授权源码。
- 计划内明确需要的调用点、filelist、参数入口和文档同步可以一并处理，但必须服务于该 plan 的既定行为。
- 实现过程中若发现需要新增计划外的行为、状态机、接口、参数或跨模块改动，必须停止在该边界，说明发现、影响和建议，等待用户明确批准后再修改。
- 用户仅要求修改方案或文档时，不得提前把方案中的函数改名、字段改名或状态机改动落实到源码。

本规则是所有模块专项规则和 plan 执行规则的前置授权门槛：专项规则说明“获准 coding 后如何修改”，不替代用户对“是否开始 coding”的明确决定。

## 6. 误修改处理

如果发现未取得本规则所需授权却已修改代码：

1. 立即停止后续代码写操作。
2. 向用户明确报告已改文件、改动性质和产生原因。
3. 不得使用 `git reset --hard`、`git checkout --` 或其他方式自动撤回；恢复/保留同样需要用户明确决定，避免误伤用户工作区。
4. 在用户明确指示后，才执行保留、撤回或将改动转入正式 coding 的后续动作。

## 7. 检查要求

新增或修改本规则后，至少执行：

```bash
git diff --check -- AI_DOC AGENTS.md
rg -n "代码修改授权规则|明确代码修改授权|默认只读任务" AGENTS.md AI_DOC/project_management
```

人工确认本规则已同时写入 `AGENTS.md` 的规则入口和触发条件，确保后续任务在任何模块开始代码修改前都能先看到该约束。
