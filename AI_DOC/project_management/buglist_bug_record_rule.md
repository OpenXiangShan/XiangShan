# Buglist 缺陷记录与分析规则

## 1. 适用范围与术语

本文规定 `AI_DOC/buglist` 中仿真缺陷记录的版本路由、周文件唯一性、重复问题处理、内容格式和
review 门禁。

- **RTL 问题**：由 DUT/RTL/Chisel 内部逻辑、状态机、队列或接口时序导致的缺陷。
- **RM 问题**：参考模型、scoreboard、RM 数据维护或比较逻辑导致的缺陷。
- **测试框架问题**：UVM monitor、driver、responder、sequence、adapter、收尾/检查逻辑等验证环境
  导致的缺陷。测试框架问题与 RM 问题都归入 `rm` 目录，但必须在记录中单独标注。
- **当前周**：按 ISO-8601 周计算，以周一为周起始日；文件名使用 `YYYY-Www_YYYYMMDD`，其中
  `YYYYMMDD` 是该周周一日期。

用户需求首处出现了 `rtl/ver` 与后文 `rm` 的目录命名冲突。本规则以后文明确的“RM 问题放在
`rm` 文件夹”为准，第二类目录统一命名为 `rm`，不建立含义重复的 `ver` 目录。

## 2. 触发条件与版本路由

满足以下条件时，才建立或更新 buglist 记录：

1. 缺陷来自仿真测试过程，而不是仅凭静态猜测。
2. 已经过多轮 review，能够判断责任边界属于 RTL、RM 或测试框架之一；若仍无法判断，先放入
   `AI_DOC/analysis`，不得提前登记为确认缺陷。
3. 已保留可复现所需的 testcase、配置/临时 plusarg、日志和波形信息。

版本路由按以下顺序确定：

1. 用户显式指定 V2/V3 时，以用户指定版本为准。
2. 未显式指定时，按当前分支 profile 路由；`mem_ut_uvm_v2` 默认使用 `v2`，`mem_ut_uvm` 默认
   使用 `v3`。
3. 分支与用户指定版本冲突时停止登记并请求确认，不得把记录放入错误版本目录。

目录固定为：

```text
AI_DOC/buglist/
  rtl/v2/    # V2 RTL 缺陷
  rtl/v3/    # V3 RTL 缺陷
  rm/v2/     # V2 RM 或测试框架缺陷
  rm/v3/     # V3 RM 或测试框架缺陷
```

## 3. 每周文件唯一性与重复问题检查

每个“类别 + 版本 + ISO 周”最多建立一个周文件：

```text
rtl_buglist_YYYY-Www_YYYYMMDD.md
rm_buglist_YYYY-Www_YYYYMMDD.md
```

例如 V2 在 2026 年第 37 周的文件分别是：

```text
AI_DOC/buglist/rtl/v2/rtl_buglist_2026-W37_20260907.md
AI_DOC/buglist/rm/v2/rm_buglist_2026-W37_20260907.md
```

登记前必须先扫描目标版本和类别目录的当前周文件：

```bash
rg --files AI_DOC/buglist/rtl/v2 AI_DOC/buglist/rm/v2 | rg '2026-W37|20260907'
```

实际使用时将命令中的版本、周号和日期替换为当前值，并同时检查文件内容中的 bug 标题、测试场景、
错误 ID、首个异常时间和根因签名。

- 当前周没有对应文件：建立唯一周文件，并按本规则添加首个章节。
- 当前周已有对应文件但现象不同：只向该文件追加新章节，不新建第二个周文件。
- 当前周已有相同现象：更新原章节的证据、review 或修复状态，不新增重复章节，也不新建文件。
- 发现同周存在多个历史文件：停止新增，先合并或明确保留一个权威文件，再继续登记。

“相同现象”至少以以下信息组合判断：错误 ID/报错文本、首个可观察异常信号、testcase/config 场景、
根因模块和责任类别。仅时间或 seed 不同不能把同一根因拆成多个 bug。

## 4. 通用记录要求

每个 bug 必须独立成章，章节标题使用简短、可检索的自然语言描述；标题中建议包含模块和现象，避免
只写“bug1”“仿真失败”。章节正文必须使用中文解释，代码标识符、路径、命令、日志原文和固定术语可
保留英文。

所有路径必须写绝对路径，不得只写相对路径。源码位置至少包含文件绝对路径、类/函数或信号名和行号；
若源码行号随生成版本变化，需同时写出稳定的类/函数名。时间应标明仿真时间单位和来源（日志或 FSDB）。

## 5. RTL 周文件章节格式

RTL 周文件中的每个 bug 使用以下字段顺序；可按实际情况增加字段，但不得删除复现和修复信息。

```markdown
## <bug 简述>

**问题类别**：RTL
**版本/分支/核验 commit**：
**发现时间**：<仿真时间；现实日期可另列>
**测试用例**：<tc、VSEQ、seed、请求数>
**复现配置**：<cfg 绝对路径>
**临时配置/plusarg**：<完整关键选项>
**日志绝对路径**：<path>
**波形绝对路径**：<path>

### Bug 现象

用自然语言说明预期行为、实际行为、首个异常时间和错误影响；明确说明这是 RTL 输出/内部状态
问题，不把 monitor 报错文本直接当作根因。

### 源码与波形定位

- 源码：`<绝对路径>:<行号>`，说明需要关注的逻辑和上下游关系。
- 波形：`<层次信号>`，列出首个异常点、关键握手/状态信号及后续传播时间点。

### RTL 修复方法

RTL 修复方法必须分成“源码修改具体逻辑”和“自然语言修改说明”两部分，不能只写抽象建议，例如
“补一个保护”“增加默认值”或“处理 X 态”。修改建议应优先选择根因所在的 RTL/Scala 逻辑，不能用
简单强制常量、monitor 屏蔽或下游吞掉错误来掩盖首个 RTL 异常。

#### 源码修改具体逻辑

对每个建议修改点必须给出以下内容：

1. 源码绝对路径、行号和稳定的模块/类/函数/状态机名称。
2. 现有控制条件、寄存器更新或组合选择中导致问题的具体分支。
3. 修改后的具体控制逻辑：应新增、收紧或拆分的条件，涉及的 valid/ready、状态、队列、寄存器或
   payload 字段如何置位、保持或清除。
4. 必要时给出短小的源码级伪代码，明确判断顺序、状态更新和禁止发生的副作用。
5. 需要保持不变的相邻合法路径和边界条件，例如 reset、flush、backpressure、无效 payload、异常
   分支或多拍传输。

推荐格式如下：

````markdown
#### 源码修改具体逻辑

- `<源码绝对路径>:<行号>`，`<模块/函数>`：
  - 修改位置：<当前错误分支或赋值点>。
  - 修改逻辑：<新增/调整的条件、状态和信号更新>。
  - 伪代码：
    ```text
    if (<触发条件>) begin
      <更新或隔离动作>
    end else begin
      <原有合法路径>
    end
    ```
  - 保持边界：<不得改变的正常路径、reset/flush/握手或异常语义>。
````

#### 自然语言修改说明

在源码级修改之后，用自然语言按运行时顺序解释：触发条件出现时修改前为何会产生错误、修改后的
判断和状态更新如何阻断错误传播、为什么合法路径仍保持原语义，以及该修改为何不会把 RTL 缺陷
伪装成正常完成。说明必须能让不直接阅读源码的读者理解具体修改逻辑，而不是重复伪代码字段名。

### Review 与状态

记录 reviewer、日期、结论、关联 review 路径和当前状态（待修复/已修复待验证/验证通过）。
```

RTL 记录应优先记载“首个 RTL 信号异常”，后续 monitor/RM 报错作为传播结果；若存在多个独立根因，
必须拆成不同章节并分别给出证据。

## 6. RM/测试框架周文件章节格式

RM 周文件可以记录 RM 或测试框架问题，但必须首先填写责任子类型，禁止把两者模糊写成“环境问题”。

```markdown
## <bug 简述>

**问题类别**：RM / 测试框架（只能选择一个主类别；必要时注明关联类别）
**版本/分支/核验 commit**：
**发现时间**：<仿真时间；现实日期可另列>
**测试用例**：<tc、VSEQ、seed、请求数>
**配置选项**：<cfg 绝对路径及关键 plusarg/临时选项>
**日志绝对路径**：<path>
**波形绝对路径**：<path；没有波形时说明原因>

### RM/测试框架问题描述

用自然语言说明预期的 RM/测试框架行为、实际行为、首个错误点、是否改变 DUT 激励或仅错误判定，
并说明为什么排除 RTL。测试框架问题必须明确标注“测试框架问题”，不能只在正文中暗示。

### 源码定位

- `<源码绝对路径>:<行号>`：说明相关 monitor、driver、RM、scoreboard、sequence 或状态表逻辑。
- 如需引用 DUT 信号，只作为排除/对照证据，不能把 RM 逻辑和 RTL 逻辑混为同一责任项。

### RM 修改方案

结合当前 RM/测试框架实现，给出保证功能前提下改动最小的方案。用自然语言详细说明数据流、状态
所有权、队列/表项变化、去重和时序边界；说明为什么不会漏比较、重复比较、误清理或改变 DUT 激励。

### Review 门禁与状态

RM 或测试框架修改方案在进入“可实施/已修复”状态前，至少完成一轮独立 review。必须记录 reviewer、
review 日期、review 结论和 review 文档/issue 绝对路径；若 review 发现问题，先修订方案并再次 review，
不能以未 review 的草案作为最终方案。状态取值：待分析、方案待 review、已 review 待 coding、已修复
待验证、验证通过。
```

RM 与测试框架若在同一仿真中同时出现，分别建立章节并各自填写主类别；只有根因确实相同且经过 review
确认时，才允许在一个章节中以“关联类别”说明，不能因为同一时间报错就合并。

## 7. 更新与归档约束

1. 记录 bug 前先扫描当前周文件；完成记录后再次检查同周是否出现重复文件或重复章节。
2. 新增证据、review 结果和验证结果应更新原章节，保留原始发现时间和首次复现配置。
3. 不删除失败日志、波形绝对路径或原始报错；如果文件迁移，必须同步更新引用并保留旧路径说明。
4. buglist 是缺陷事实和复现/修复记录，不替代 plan、implementation review 或长期 RTL flow 文档；需要
   coding 的任务仍按相应 plan 和 code review 规则执行。
5. 提交前至少执行：

```bash
git diff --check -- AI_DOC AGENTS.md
```
