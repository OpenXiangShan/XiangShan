## 1. 版本基线

设计侧对齐摘要默认只展示下面两项：本次验证所依据的设计版本，以及承载验证环境的仓库版本。验证状态、回归、覆盖率、变更影响和遗留问题等章节作为验证内部记录，只有在对齐需要时再摘取结论；DUT 构建、工具、产物 hash 等信息保留在内部追溯区。

### 1.1 设计版本 baseline

| 项目 | 内容 |
| --- | --- |
| 设计主线 + 合入 commit | `kunminghu-v3 @ design_baseline_sha` |
| 最新 PR 编号 + PR 合入日期 | `PR 编号 / 链接；YYYY-MM-DD` |

### 1.2 验证仓库 baseline

| 项目 | 内容 |
| --- | --- |
| 验证仓库/分支 + commit | `frontend-bt / 分支名 @ verification_env_sha` |
| 验证 commit 日期 | `YYYY-MM-DD` |

设计版本必须填写已合入 `kunminghu-v3` 主线的 merge commit；验证版本填写本次回归绑定的 `frontend-bt` commit。不要在对齐材料之外再次独立同步设计主线。对齐证据必须绑定到一个当时已提交且可复现的 clean commit，以及与该 commit 配对的 DUT manifest；回归完成后工作树出现新的未提交改动，不影响已经记录的这份历史对齐结果。若版本、DUT 构建或 registry 签名变化，必须新建回归证据集。

### 1.3 验证内部追溯信息（不要求在设计对齐会上展示）

| 项目 | 内容 |
| --- | --- |
| DUT 构建 manifest | `build-frontend/frontend_build_manifest.<sim>.json` |
| 仿真工具及版本 | `Verilator/VCS 版本` |
| DUT 构建命令/脚本 | `命令或路径` |
| DUT/RTL/signal-contract hash | `manifest.artifacts 中的 hash` |
| manifest 生成时间 | `YYYY-MM-DD HH:MM:SS UTC` |
| 测试点主表版本/签名 | `路径 + sha256/commit` |

| 回归配置与证据根目录 | `配置文件 / data/runs/...` |

manifest 中三个代码 SHA 都是 Git commit ID：`dut_source_sha` 是生成 DUT 的源码 commit，`implementation_sha` 是生成 manifest 时验证仓库的 HEAD，`design_baseline_sha` 是语义上的设计基线；未显式指定时后两者可能与源码 SHA 相同。`artifacts` 下的 `*_sha256` 才是编译产物、生成 RTL 和接口文件的内容 hash。

## 2. 当前验证状态

### 2.1 测试点与功能覆盖率统计

测试点主表：`路径`；覆盖率模型：`路径`；统计时间：`YYYY-MM-DD HH:MM:SS`。

叶子测试点定义：属于 `condition`、`object`、`checkpoint` 三类字段体系的最小测试点记录；其中部分字段允许暂时缺失，但三者不能全部为空，且非空内容必须能标识一个具体验证目标。抽取规则和人工修订必须记录在备注或证据中。

| 指标 | 数量 | 统计口径/证据 |
| --- | ---: | --- |
| 测试点文档物理行数 | `N` | `文件 / csv.reader 记录数` |
| 叶子测试点数 | `N` | `抽取规则 + 文件` |
| 叶子点对应的 modeled coverage 数 | `N` | `registry 查询` |
| Python 激励用例数 | `N` | `测试目录/清单` |
| `.S` 汇编源用例数 | `N` | `asm_cases 清单` |
| 已编译 `.bin` 可执行文件数 | `N` | `bin 目录/manifest` |
| 逻辑测试场景数 | `N` | 去重后的场景数 |

`.S` 和 `.bin` 通常是同一汇编场景的源文件与可执行产物，报告物理文件数时分别列出，但逻辑场景数不得重复相加。

每个叶子测试点必须且只能有一个主状态；以下五类之和必须等于叶子测试点总数：

| 主状态 | 数量 | 定义 |
| --- | ---: | --- |
| `UNMAPPED` | `N` | 尚未绑定 coverage/testcase/evidence |
| `MODELED` | `N` | 已建模但尚无有效命中证据 |
| `PARTIAL` | `N` | 已有部分条件或部分路径证据 |
| `HIT` | `N` | 自动回归已命中，待人工确认 |
| `CLOSED` | `N` | 已人工 review 并确认闭环 |
| **合计** | **`N`** | 必须等于叶子测试点数 |

`BLOCKED`、`N-A` 等内容作为原因标签或例外清单单独记录，不得悄悄混入五类主状态；若项目决定将其作为主状态，必须同时给出映射规则，使主状态合计仍可审计。

覆盖率必须分别由 `verilator_coverage` 和 VCS/Verdi 工具生成；填写分子、分母、百分比和 waive 数量，不能只报百分比。

## 附：建议保留的统计规则

1. 所有数量都注明统计时间、数据源路径和版本签名；没有证据的数字标记为 `TBD`，不填估算值。
2. 回归 PASS 只表示对应 DUT 运行通过，不等同于功能覆盖率 `HIT`；`HIT` 也不等同于人工确认的 `CLOSED`。
3. 代码覆盖率和功能覆盖率分开汇报；Verilator 与 VCS/Verdi 结果并列展示，差异必须解释。
4. 每周对齐先固定一个已提交的 `frontend-bt` commit 和对应的 design/DUT baseline，再基于该 clean commit 生成独立 run；表格填写该 run 的结果和签名。后续工作树的未提交状态不改变这份已绑定证据的有效性。
5. 证据只允许来自同一版本配对，历史版本结果不能直接提升其他版本的测试点状态。
