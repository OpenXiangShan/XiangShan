# 测试点拆分准则

本文用于各模块的测试点规划。测试点描述需要验证的场景；测试用例、验证环境和覆盖率实现另行设计。

## 从新模块开始拆分

1. **确定边界和依据。** 明确 DUT 的接口、参数、工作模式和需要验证的状态。对照设计需求、接口协议、当前实现及已知问题，记录各项行为的依据；资料冲突或含义不明时标为待确认，不凭信号名称推断行为。
2. **列出行为清单。** 按功能梳理输入或事件发生后，DUT 应如何输出、更新状态或报错。检查正常路径、异常、边界、状态转换和恢复；不要直接从端口列表生成测试点。
3. **确认信号关系。** 查清哪些输入可以独立出现，哪些必须配合，哪些有先后、并发或优先级要求。只分析设计允许的组合；常一起出现的信号不一定存在必然关系。
4. **组织层级并写叶子。** 上层按功能和行为归类，叶子写一个可独立验证的场景。为每项设计要求找到对应叶子；有独立要求的输入类别、状态转换或信号交互分别列点，不要求每项都拆到第五级。
5. **双向检查。** 从行为清单逐项找测试点，查遗漏；从每个叶子反查设计依据和上层归属，查无依据、重复或互相包含的点。设计关系未确认的部分保留待确认项，不按猜测补齐。

## 叶子测试点怎么写

- 名称写清对象、输入或事件，以及必要的前置状态和时序关系。使用准确、平实的语言，不用“合法情况”“恢复时”“优先级正确”等笼统说法，也不把预期结果当作场景名称。
- `Condition` 写 DUT 输入、可达到的前置状态及必要的时序关系；`Checkpoint` 写可观察、可判断的预期结果。不要把激励生成组件或其他模块的内部过程写成 DUT 的输入条件。
- 同级叶子不重复、不互相包含。不能仅因最终输出相同就合并独立的设计要求；也不因取值、出现次数或同周期与跨周期的差异机械拆分。只有差异改变处理行为、检查重点或明确的覆盖要求时才单列。
- 测试点与当前验证环境分开考虑。环境暂时无法构造或检查某个必要场景，应记录能力缺口，不删除该测试点。

## 完备性检查

对照设计要求和接口协议，确认输入类别、正常与异常行为、状态变化、边界条件，以及有独立语义的信号交互均有对应场景。逐项检查叶子能否在 DUT 边界形成条件、能否观察和判断结果。完备性针对已明确的设计行为，不以现有测试用例数量或覆盖率命中数替代。
