### 2.2 旧 Frontend BT 方案：从测试点走向最小闭环

2026 年 3 月至 4 月，旧目录形成了：

### 2.3 新环境：Python/toffee 真实 DUT 主线

新环境将工作重心从“规划文档”转为可执行闭环：

`测试点 -> testcase -> funcov -> 真实 DUT 回归 -> artifact -> 自动反标 -> 人工 CLOSED`

主要变化包括：

- Python/toffee 黑盒验证取代旧 UVM 方案口径。
- 测试点主表扩展并增加 `status/testcase/evidence` 回标字段。
- coverage registry 与 `env/funcov.py`、`env/functional_coverage.py` 形成唯一采样链。
- waveform、代码覆盖率、funcov 和日志按唯一 `run_id` 归档。
- build manifest、源码哈希、测试输入哈希和 artifact 路径共同参与证据门禁。
- 当前 checker、monitor、trace 和真实 DUT 结果决定是否验收，文档或 Bin 存在本身不构成闭环。

## 3. 哪些内容被继承

### 3.1 可以继续作为验证输入

- Frontend 的 BPU、FTQ、IFU、ICache、ITLB/PTW、PMP、IBuffer 模块边界。
- reset、顺序取指、redirect、MMIO/uncache、地址翻译、权限、异常和反压等场景类别。
- 历史 Bug 的触发条件、根因和曾经漏测的边界。
- JalrFault、预测检查优先级、跨页/跨块、RVC/RVI 混排和错误传播等风险导向测试思路。
- 旧 Bin ID 对来源追溯的价值。

### 3.2 只能作为历史背景

- 当时 V2/V3 对比得到的具体 RTL 行为。
- `bosc_IFU_spec*.md` 中的接口、位宽、状态机和优先级描述。
- 旧测试点的信号路径、观察对象和 testcase 建议名。
- 阶段性 coverage 命中结论或验收判断。

这些内容在复用前必须重新对照当前 RTL、生成接口和当前测试环境。

### 3.3 不应继续复用

- 旧 UVM 环境架构和资源排期。
- `node033`、旧 worktree 和旧数据目录路径。
- 旧 coverage recorder、并行 CovGroup 模型或全局 `data/funcov/` 写法。
- 以 FakeDut、模型单测、历史波形或旧 schema artifact 证明当前闭环。
- 把旧阶段汇报中的“已完成”直接回填到当前主表。

## 4. 使用历史结论的复核流程

复用本历史包中的任何技术结论时，依次完成：

1. 在当前分支找到对应 Scala RTL 和设计变更记录。
2. 对照 `build-frontend/rtl/`、`signals.json` 和 build manifest，确认实际接口。
3. 将历史触发条件翻译成当前 DUT 可驱动、可观察的场景。
4. 检查当前测试点主表和 coverage registry 是否已有唯一对应项。
5. 如需新增内容，同时更新 canonical registry、`env/funcov.py` 和 testcase。
6. 只使用当前版本、同一 run root 下且通过 checker/trace/哈希门禁的 artifact 反标。
7. 技术行为存在歧义时，由当前 RTL 和设计 owner 结论覆盖历史文档。

## 5. 文档使用决策

| 问题 | 优先来源 | 本历史包的作用 |
|---|---|---|
| 今天如何运行或调试 Frontend BT | `docs/agents/frontend-verification.md` | 不使用 |
| 当前有哪些测试点和状态 | back-annotated canonical 主表 | 仅解释来源 |
| 当前功能覆盖率如何建模 | `skills.md` 和 active registry | 仅解释旧 Bin 语义 |
| 为什么某类场景必须验证 | 历史问题与风险基线 | 提供根因和漏测背景 |
| 某 IFU 模块当时的设计意图 | IFU 历史设计意图文档 | 提供假设，随后核对 RTL |
| 旧表与新主表是什么关系 | 旧测试点来源与当前主表关系 | 提供迁移和审计依据 |
