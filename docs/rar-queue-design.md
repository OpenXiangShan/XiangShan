# RARQueue 压缩设计

S1 预分配并写入 ROB 指针，S2 查违例、对多个端口分组并选定目标槽，S3 返回 S2 的查询结果，同时提交仍需跟踪的成员。本文用 T 表示一批请求处于 S2 的周期。T 拍末锁存目标与各端口元数据，T+1 拍末才更新正式项。

## 1. 表项和流水级职责

| 槽状态 | 有效字段 | 用途 |
|---|---|---|
| Free | 无 | S1 可分配 |
| Reserved | 完整 ROB 指针 | S1 写入申请者的 ROB slot；S2 miss 组可继续持有其最老成员的槽至 S3。参加 redirect 比较，裸预留不参加地址查询 |
| Live | 16 位行哈希、ROB 上界、LQ 上界、released、shared | 参加违例查询、release 和压缩，按 LQ 边界回收 |
| Recovering | 行哈希、恢复 ROB 上界、released | 参加违例查询与 release，按 ROB 回收，新请求另选目标 |

Reserved 的 ROB 字段可与正式项的 ROB 上界共用寄存器。每槽只占用一次；空闲位图只含 Free，正式项计数只含 Live 和 Recovering。LRQ 唤醒水位以实际空槽计，初始沿用至少 `2 × LoadPipelineWidth` 个空槽的约定。

**S1。** 从拍初 Free 槽为有效端口各分一个不同槽号，拍末写入 `Reserved(request.robIdx)`。固定下一拍进入 S2。并行预计算端口之间的 ROB 和 LQ 年龄关系。组内选最老端口以完整 ROB slot 为先，同 slot 比 LQ，再以端口号打破平局。最大 LQ 边界独立选择。比较均保留回绕语义，ROB 还区分 former/latter。

## 2. S2 完成多端口分组和目标选择

S2 并行比较请求与正式表的行哈希，以及各端口之间的行哈希。已有目标的候选由拍初 Live 行产生，屏蔽本拍将被 redirect 冲刷、到达 LQ 回收边界、正由上一批 S3 写入或受 S4 晚撤销保护的行。多项命中时用一致的固定槽号优先级。仅查询、缺槽或本拍已经失效的请求均不参与写入分组。

| S2 结果 | 目标和预留的处理 |
|---|---|
| 请求被冲刷、消失或无需跟踪 | 归还自己的槽。即使 S2 valid 已被清掉，RARQueue 仍能用 Reserved 中的 ROB 指针响应 redirect |
| 一个或多个普通端口命中同一旧项 | 同组目标为该 Live 槽，各端口归还自己的预留 |
| 同哈希的普通端口均无可写旧项 | 可在 S2 合为一组。取最老有效端口的预留槽为共同目标，其余槽在 S2 拍末归还。单个 miss 直接保留自己的槽 |
| 非对齐 head 可能被 S4 晚撤销 | 单独使用自己的槽，保护窗口内禁止其他成员合入 |
| 需要跟踪但 S1 无槽 | 沿用 RAR nack / LRQ 重放约定；有效查询仍在 S3 收到响应 |

两个同哈希端口如有同一可写旧项，均选择它。组内选最老只用于决定新组借用哪个槽；旧项命中直接使用其槽号。S2→S3 为各端口保留有效位、目标槽、ROB/LQ 和初始 released；新建或合入的选择、同组关系及 S1 的年龄比较与这批请求对齐。每个新组只持有一个 Reserved 槽。S2 选定的旧目标本拍不会释放或被上一批写者换掉，下一拍 S1 也无法将它分配给其他地址。

同拍 miss 是否共用槽是可独立衡量的时序选择。本稿列出共用槽的完整路径；若综合显示该路径过长，沿用先前允许的“同拍 miss 各用自己的槽”即可。命中同一旧项的多端口仍然在 S2 分组。两种方案的定向测试按各自的预期占用分别判定。

## 3. S3 过滤撤销并提交

每个端口独立产生是否写入的条件：

```
survives[p] = intentValid[p]
           && !revokeLastCycle[p]
           && !robIdx[p].needFlush(redirect)
           && isAfter(lqIdx[p], ldWbPtr)
```

`revokeLastCycle` 包含 LoadUnit 的 S3 replay 或异常等撤销原因，在没有 redirect 时也可拉高；`needFlush` 比较的是提交这一拍的 redirect。两者分别屏蔽相应成员。[LoadUnit 撤销信号](../src/main/scala/xiangshan/mem/pipeline/NewLoadUnit.scala#L1494)

对 S2 已定的每个目标，令 W 为该组中 survives 为真的成员。每个目标每拍只有一次状态更新：

- 新建组 W 为空，释放保留的槽；W 非空，在既定槽建项。即使提供槽号的端口 replay 或已被 `ldWbPtr` 追上，仍由 W 使用该槽。按组决定是否释放。若 Reserved 中最老成员被 redirect 冲刷，则组内所有同龄或更年轻的成员也被该 redirect 冲刷。
- 命中已有项且 W 为空，旧项只处理本拍本来就有的 redirect、退休和 release。W 非空且旧项仍存活时，分别取旧项及 W 中最年轻 ROB、最靠后 LQ、released 的或，并置 shared。仅用 W 建项时按 W 初始化，shared 取成员数是否大于一。若旧项本拍退休或被刷，按下一节合成该槽的更新。
- 用 S1 的两两年龄和 W 选择贡献者。例如 ROB/LQ 为 8/16、14/12 的两个端口命中旧项 10/10，均存活时结果为 14/16；若前者 replay，结果为 14/12。S3 无需重做行哈希匹配或重新选槽。只从幸存者收集 released，避免撤销端口留下标记。

S4 晚撤销只针对确实在 S3 建项的非对齐 head，用有效位和私有槽号定位。提前退休或冲刷时同步清除晚撤销资格，防止误清下一位使用者。

## 4. Redirect 每拍处理，退休按两个边界处理

Redirect 对所有有效槽生效，与 LoadUnit 端口是否有请求独立。S2 选目标时已屏蔽本拍要刷的项，S3 则可能遇到下一拍新到的 redirect。对旧目标及已逐端口过滤的 W，使用以下规则：

| 旧目标在 S3 当拍的情况 | 拍末动作 |
|---|---|
| 普通项未被刷且 `ldWbPtr` 已到达 LQ 上界 | 旧项退休。W 非空时在同槽仅用 W 初始化，否则回到 Free |
| 单成员项的 ROB 上界被冲刷 | 丢弃旧成员。W 中可能还有更老的请求，在同一槽仅用 W 初始化；W 为空则回收 |
| 共享项的 ROB 上界被冲刷 | 进入 Recovering，以 redirect 的完整 ROB slot 作上界。旧项可能幸存的成员及 W 均被此上界覆盖。保留旧 released 并与 W 的 released 取或，旧 LQ 上界停用 |
| Recovering 遇到更老 redirect，或 ROB 已推进至边界 | 先按 `needFlush` 收紧边界；无新冲刷时，`robUpper.isNotAfterSlot(robPendingPtr)` 即回到 Free |

首次进入恢复、连续收紧边界均优先于当拍退休。使用 `needFlush` 的 flush-self 和 former/latter 语义。槽在拍末转为 Free，下一拍拍初进入空闲位图；S1 实际取得该槽的时刻还取决于分配器的候选寄存器，见第 6 节。哈希碰撞、多个成员的 released 取或和恢复上界可能使违例检测多报，以逐 load 模型检查漏报及单列多报。

例如 ROB 18 的 load 在 T 拍选中 ROB 10 的旧项。若 redirect(15) 在 T 到达，释放 Reserved(18)，不生成写入请求；若在 T+1 才到达，该成员在 S3 被过滤，原槽仍代表 ROB 10。反过来，ROB 12 在 T 选中了单成员 ROB 18 的项，T+1 才来 redirect(15)，旧成员被刷、ROB 12 幸存，直接在原槽留下 ROB 12。此前归还的预留槽不再引用。

## 5. 背靠背查询和 cache release

S2 查询拍初的 Live/Recovering 行，同时旁路上一批在 S3 的有效意图。查找同哈希、已观察到 release、ROB 位置严格晚于查询者的记录，匹配取或，下一拍返回 nuke。查询响应有效位跟随有效 S2 查询，独立于是否拿到预留、是否最终写表。旁路保留单个成员的 ROB 和 released，沿用当前查询时序，允许相对逐 load 模型多报。仅供查询的旁路不会使正在 S3 新建的槽成为当前 S2 的旧合并目标。

初始 released 在 S2 取 `nc || (dataValid && (上拍同哈希 release || 本拍同哈希 release))`。S3 同拍出现的 cache release 还需匹配所有正式行，以及 W 中成员的最终目标，合并为延迟标记。仅由请求 S3 的 release 引起的标记，沿用广播后第二拍的 S2 查询可见、第三拍返回的时序。标记只跟随同一生命周期：旧行恢复时继承，旧行整体回收时丢弃，W 接替旧行时以 W 的初值及属于 W 的 release 初始化。重复哈希行全部参与比较。

## 6. S3 回收与 S2 查询在同一拍如何工作

以下用 K 表示同一个物理时钟周期：请求 A 已到 S3，下一批请求 B 正在 S2，更下一批在 S1。三者读取 K 拍初的寄存器。A 在 K 拍末提交或归还，B 在这个沿锁存查询命中位和写目标。B 的违例响应在 K+1 返回，B 的正式写入最早发生在 K+1 拍末。

### 同拍读写与释放的可见性

| K 拍的事件 | B 在 K 拍做违例查询 | B 在 K 拍选合并目标 | K 拍末及以后 |
|---|---|---|---|
| Live 行 i 正常退休、被冲刷或被 S4 晚撤销 | 仍可看到行 i 的拍初 ROB 上界和 released；满足条件可产生额外 nuke | 退休、冲刷、私有保护分别屏蔽 i，B 选其他可写旧项或使用预留 | 正常退休/单项冲刷变 Free；共享项冲刷进入 Recovering。若上批已有幸存写者接替，按第 4 节保持占用 |
| A 组占有 Reserved 槽 i，K 拍发现全组撤销 | 裸槽没有地址记录；A 的已寄存意图可经 S3 旁路被查到。若其中年轻成员带有 released，B 仍可能报 nuke | i 拍初为 Reserved，不可选；B 无预留且需跟踪时仍 nack | i 在 K 拍末变 Free。B 或同拍 S1 均不能消费这次归还 |
| A 正在新建或合入 i，至少一名成员幸存 | 同时比较拍初正式行和 A 各成员的已寄存元数据。成员贡献的 ROB 与 released 按同一成员配对 | 不选 A 已占用的写目标 i。同哈希的 B 可以选另一可写旧项；没有时使用自己的组预留 | A 拍末更新 i，K+1 的请求可从正式表看到新边界。B 已经选好的目标不再更改 |
| K 拍首次出现同哈希 DCache release | 对此前 released 为零的旧记录，K 拍的查询还看不到新标记 | 单纯的 cache release 不影响合并资格 | 事件在 K 拍末登记，到 K+1 拍末写表，K+2 的 S2 首次可查，K+3 返回。B 自己的 `dataValid` 与本拍 release 产生的初值按第 5 节单独随 B 前进 |

以第一行为例，假设旧行 i 的 `released=1, robUpper=18`，B 查询 ROB 12 的同哈希行，恰好 `ldWbPtr` 本拍追上 i。违例查询从拍初记录得到命中；合并选择同拍屏蔽 i；若无其他成员接替，i 拍末回收。这三个结果可以同时成立。允许这种额外 nuke 的前提是继续按逐 load 模型验证无漏报，并记录实际额外 rollback。现分支的违例比较同样使用正式项与 S3 预留的拍初有效位，命中位在 S2 拍末寄存，OR 归约放在响应拍。[现有违例比较和响应寄存](../src/main/scala/xiangshan/mem/lsqueue/LoadQueueRAR.scala#L160)

### S3 的释放路径与 S1 的复用延迟

新建组的释放条件是 `(groupMembers & survives).orR == false`。最老端口只提供槽号，它独自 replay、异常或到达 LQ 写回边界，都不能单独释放这个组的槽。成员是否幸存与旧项的 LQ 到界、ROB 到界、redirect 比较可并行计算；拍末为每个槽选择唯一下一状态。命中旧项的请求已经在 S2 归还自己的预留，S3 全组撤销时旧项仍按自身的退休条件处理。

若复用现有 `BitMapFreeList` 并把**拍初** Free 位图接到 `freeBitmap`，一个刚释放的槽有两个可观察时刻：

| 时刻 | 槽 i 的位置 |
|---|---|
| K 拍 | i 已占用；S3 决定释放。S1 仍从先前准备好的候选分配 |
| K+1 拍 | i 已在 Free 位图中，分配器可以选择它补入候选寄存器 |
| K+2 拍 | 如果 i 在 K+1 被选中，S1 此时最早能从候选输出取得它；候选顺序或其他空槽可使它更晚被选中 |

S2 归还多余预留也遵循这个时序。位图中已有空槽而候选尚未补齐时，端口仍可能拿不到预留。六组回归的满队列场景要分别采样 Free 位图、`canAllocate` 和实际发放槽号。若为了提早一拍复用而把 S3 的 next-free 接回分配器，组合路径会从撤销/退休判定延伸到位图前缀计数与候选选择。本设计采用拍初位图。[候选补充及输出寄存器](../src/main/scala/xiangshan/mem/lsqueue/FreeList.scala#L39)

### S2 查违例与选目标的组合路径

两路共用物理行哈希相等比较，但使用不同掩码。按当前 96 项、三个 load 端口估算，每个查询端口最多比较 96 个正式行和三个在途成员；三个 S2 端口两两同哈希只需三对比较。大扇出、全表选槽和走线延迟需要用实现后的时序报告判断。[默认 RAR 容量](../src/main/scala/xiangshan/Parameters.scala#L103)

| 路径 | 起点 → 终点 | 时序处理 |
|---|---|---|
| S2 违例查询 | B 的物理地址 → 行哈希相等；与拍初有效、released、ROB 严格更年轻的比较结果相与 → 命中位寄存器 | 哈希和年龄比较并行；沿用 S2 寄存命中位、S3 OR 归约的分拍方式。S3 意图旁路取寄存的 valid/hash/ROB/released，无需等待 K 拍 `revokeLastCycle` 或 S3 写回后的边界 |
| S2 命中旧项 | 表哈希相等位图与本拍可写掩码 → 固定优先选槽 → 各端口目标寄存器 | 用**所有有效 S3 意图的已寄存目标**形成占用掩码，即使某组当拍将全撤销也先屏蔽。redirect 和 LQ 到界直接与拍初表项比较，S4 使用已寄存的保护槽号。可写掩码按行共享，独立于 S3 的最终写使能和回收结果 |
| S2 同拍 miss 合并 | 端口间同哈希、有效、普通 load 和 S1 年龄关系 → 最老成员及其预留槽 → 目标寄存器 | 和旧项查找并行产生组候选。普通端口对同一哈希使用同一套可写掩码，可先算最老预留槽，再用旧项是否命中作末级选择；非对齐 head 及无预留端口先从组内移除 |
| S3 提交或释放 | 撤销、redirect、写回指针 → 组内幸存位 → 空组释放或成员边界归约 → 行状态寄存器 | 组内无人幸存只需小宽度 OR。更新已有行还要比较旧边界与幸存者上界并选择下一状态。两条路径应分别取报告，不能用释放路径的延迟代表写表路径 |

这里有一条刻意切断的依赖：如果 S2 用 S3 的**实际写使能**屏蔽目标，路径会变成“LoadUnit S3 撤销 → 组内幸存归约 → 每行写使能 → S2 全表优先选择”。使用已寄存的目标号或其译码即可在上一拍确定要屏蔽哪些槽，代价是上批恰好撤销时少一次合并机会。S2 的 `ready`/nack 只取本请求是否需要跟踪及 S1 的预留有效位，避免再把全表选槽接到 LoadUnit 的 replay 判定。

以上是数据依赖分析。实现后分别取 S2 命中位寄存器、S2 目标槽寄存器、S3 响应到 LoadUnit 违例处理、S3 行状态寄存器及 freelist 候选寄存器的最差路径，报告时钟约束、slack、逻辑及连线延迟。特别比较“同拍 miss 共用槽”和“各用自己的槽”两版的 S2 目标路径。当前未取得该重构 RTL 的 STA 数值。

## 7. 实现与验收

LoadUnit S1 提供预分配有效位及完整 ROB/LQ；S2 保留地址查询、数据状态、nack；S3/S4 沿用响应及撤销。LoadQueue 提供 redirect、`ldWbPtr`、`robPendingPtr` 和 cache release。无需为 S3 replay 保存任何正式项的写前副本。

### 旧 RAR 设计的六组模块定向回归

以 16 项、三端口执行。以下默认同拍 miss 共用最老端口的槽。[现有模块测试](../src/test/scala/xiangshan/mem/RarMergeTest.scala)

| 组 | 激励 | 重构版通过条件 |
|---|---|---|
| 1. 已有同行，一路或三路命中 | 三路选中同一旧项；S3 分别撤销最老、两个或全部端口 | S2 归还预留，正式项边界保持。S3 每行最多写一次；仅幸存者贡献边界和 released。全撤销时不产生合并写 |
| 2. 空表，同拍或连续拍同行 | 三路同拍 miss；令提供槽的端口无 redirect 而在 S3 replay，再试全撤销。另测背靠背访问、哈希碰撞 | 一组持有一个槽；提供槽的端口被撤销，其他成员仍可在同槽建项；全撤销释放。背靠背查询看到 S3 旁路；后批仅命中在建行时独立预留。若采用同拍 miss 分开方案，以幸存端口各用自己的槽验收 |
| 3. 目标消失、取消、无槽 | S2 冲刷输入或旧目标；S3 才冲刷旧目标或请求；复用已归还槽；表满 | S2 即使 valid 已低也能回收被刷预留；旧目标被屏蔽则选其他可写项或保留自己的槽。S3 按旧行与 W 分别处理。无槽且需跟踪则 nack，有效查询照常响应 |
| 4. 老 load 紧邻查询年轻 load | 年轻 A 在 S2 接受时有 released，老 B 在下一拍查询；对照仅在 A 的 S3 才发生 release | B 从 S3 意图旁路看到 A，在 B 的 S3 返回 nuke。仅有后到 release 时按第 5 节核对首次可见拍 |
| 5. 非对齐 head/tail、撤销、写回推进 | S3 replay、S4 晚撤销、提交拍 redirect 或写回追上，覆盖接近满队列 | S3 取消者不建表；S4 仅清相应私有 head。相邻成员和已复用槽不受影响，阻塞解除后能继续推进 |
| 6. Release、redirect、回绕、排空 | 已 released 的旧项合入新请求，加入 S3 同拍 release、新路径同行、连续 redirect、flush-self、former/latter 与指针回绕 | 按拍对照 nuke，防止漏报、旧 release 泄漏和提前退休；恢复边界只收紧。排空后无正式项、Reserved 项或有效写入意图 |

额外检查 S2 查询无效但 `Reserved(18)` 遇 redirect(15)、S3 无 redirect 但 `revokeLastCycle=1`、所有端口空闲时旧共享项收到 redirect，以及 ROB/LQ 交叉和提供槽的端口独自到达 LQ 写回边界。断言每个有效意图有唯一目标、每槽每拍最多一次写、组内无人存活时在建槽归还。逐 load 模型逐拍检查应报 nuke 与 release 窗口。

同拍时序验收对第 6 节的四行逐一观测。用例中同时记录 B 的查询匹配位、选择的写目标、拍末槽状态和下一拍的响应。再把队列填满，使候选池为空，仅释放一个槽，核对 K 拍回收、K+1 位图可见、K+2 最早发放的三个边沿。

时序评估分别量 S1 预分配与年龄比较、S2 的表命中/端口同哈希比较至目标槽寄存器、S3 的存活筛选至双上界写回。S2 中端口间比较可以和表查询并行，但“旧项命中还是选最老预留槽”的最终选择仍在该拍末端，需用综合/STA 确认余量。性能对照固定 LRQ 容量、checkpoint、seed 和窗口，记录同批 miss 共用槽次数、RAR nack、额外 nuke、ROB 等待 load 周期和 IPC。本文为设计与验收规格。


## 实现验证记录

当前实现按 S1 预分配、S2 查询与分组、S3 提交、S4 私有 head 撤销分别组织，级间寄存器以所属流水级为前缀。表项下一状态在单独一段汇总各拍的事件。

16 项、三端口模块回归已通过六组定向场景，包括 ROB/LQ 年龄交叉的两种先后顺序。25 组随机逐 load 对照的 607 次必需违例均在对应响应拍报告，另有 51 次额外 nuke。DefaultConfig 的整核 GSIM 编译完成，CoreMark 在 NEMU difftest 下运行至 HIT GOOD TRAP。milc、wrf、bwaves 的配对短窗口均以相同 seed、检查点、NEMU、DRAM 配置运行，预热 100,000、总计 400,000 指令；三点正式窗口的周期及 IPC 均与旧合并版一致，RAR nack 均为零。

S2 屏蔽 S3 正在写的目标，使短窗口的合入已有项次数下降、新建次数上升，同拍少建次数保持一致。该结果反映当前实现的目标屏蔽规则。完整 20M/40M 性能窗口与 STA 尚待执行。
